# Batch Control

CI 서버가 아니라 **배치 실행 관리 도구**로 운영되는 Jenkins 인스턴스를 위한 실행 승인,
적시(just-in-time) 변경 권한, 추가 전용(append-only) 감사 이력.

플러그인을 설치해도 달라지는 것은 없습니다. 모든 통제는 관리자가 켤 때까지 꺼져 있으며,
두 통제는 서로 독립적으로 켜집니다.

---

## 문제

많은 조직이 야간·주기 배치 작업 — Spring Batch 잡, 데이터 적재, 정산 실행, 대조 스크립트 —
을 Jenkins로 돌립니다. 그 잡들은 운영 시스템입니다. 일정 밖에서 사람이 손으로 하나를
시작하거나, 하나가 하는 일을 바꾸는 것은 운영 변경이며, 그 뒤에 따라오는 질문은 어떤 운영
변경에든 따라오는 질문과 같습니다. *누가 이걸 시작했나, 어떤 파라미터로, 누가 동의했고,
왜?*

Jenkins 자체는 그 질문에 부분적으로만 답합니다. `Item/Build`를 가진 사용자는 어떤 잡이든
아무 때나 시작할 수 있고, `Item/Configure`를 가진 사용자는 어떤 잡이든 영구히 바꿀 수
있으며, 무슨 일이 있었는지의 기록은 빌드 안에 살기 때문에 빌드가 로테이션으로 사라지면
함께 사라집니다.

Batch Control은 빠진 부분을 채웁니다. 보호된 잡을 수동으로 실행하는 것은 지정된 결재자가
승인해야 큐에 들어가는 **요청**이 되고, 설정 변경에는 스스로 만료되는 **기간 제한 권한**이
필요하며, 모든 실행, 승인 결정, 설정 변경, 실패는 빌드 보존 정책과 무관한 저장소에
기록됩니다.

---

## 두 종류의 통제

이 플러그인에는 스위치가 두 개 있고, 둘은 서로 다른 문제를 해결합니다. 둘을 한 가지로
읽는 것이 가장 흔한 오해입니다.

### 실행 통제 — 실행 단위 승인

*빌드를 시작하는 것*을 통제합니다. 이것이 켜져 있고 잡에 "실행에 승인 필요"가 표시되어
있으면, 그 잡을 실행하려는 사람은 파라미터와 사유를 담은 실행 요청을 제출합니다. 지정된
결재자는 바로 그 파라미터를 보고 승인하거나, 사유를 달아 반려합니다. 승인되면 저장된
파라미터 그대로, 변경 없이 플러그인이 빌드를 큐에 넣습니다 — 승인 후에 파라미터를 수정하는
경로는 없으며, 바꾸려면 새 요청을 만들어야 합니다.

승인은 잡이 아니라 **하나의 실행 요청**에 붙으며, **한 번의 큐 투입으로 소비**됩니다. 재생,
재큐잉, 재빌드를 할 수 없습니다. 시도하면 차단되고 `MARKER_REUSE_BLOCKED` 기록으로 감사
이력에 남습니다.

### 변경 통제 — 적시 권한 창

*잡을 바꾸는 것*을 통제합니다. 이것이 켜져 있으면 잡을 생성·설정·삭제해야 하는 사용자는
임시 권한을 요청합니다. 범위(잡 하나 또는 폴더), 동작 집합(`CREATE` / `CONFIGURE` /
`DELETE`), 기간, 사유. 결재자가 승인하면 요청자는 그 창 안에서 **자기 계정으로** 작업하며,
평소의 Jenkins 안전장치가 모두 그대로 적용됩니다. 창의 만료 시각이 지나면 그 권한은 다음
권한 검사부터 사라집니다 — 타이머도, 회수 절차도 없고, 컨트롤러 재시작을 넘어서도 계속
사라진 상태입니다.

기록은 두 스위치와 무관합니다. **어느 쪽이든** 하나가 켜져 있으면 실행, 변경, 승인, 실패가
기록됩니다.

## 무엇이 차단되고 무엇이 차단되지 않는가

이 부분은 두 번 읽을 만합니다.

실행 통제는 **큐 진입 시점**에 빌드를 가로채며, *사람이 버튼을 누른 것*과 *자동화가 발동한
것*을 구분합니다. 실행 통제가 켜져 있고 잡에 "실행에 승인 필요"가 설정된 상태에서:

| 빌드가 시작된 방식 | 결과 | 잡별로 조정 가능? |
|---|---|---|
| UI의 "Build Now" | **차단** — 사이드바 링크가 "Request Run"으로 바뀝니다 | 아니오 |
| `POST /job/<name>/build`, `/job/<name>/buildWithParameters` (REST) | **차단** | 아니오 |
| `jenkins-cli build <name>` (CLI) | **차단** | 아니오 |
| Pipeline **Replay** | **차단** | 아니오 |
| 승인된 실행 요청(플러그인이 큐에 넣음) | **허용**, 요청당 한 번 | 아니오 |
| cron / `TimerTrigger` | **허용** | 예 — `Block cron (timer) triggers` |
| 상위 잡 (`build` 스텝, 빌드 후 트리거) | **허용** | 예 — `Block upstream triggers`, 그리고 `Allowed upstream jobs` |
| SCM 트리거 | **허용** | 아니오 |
| 그 외 인식되지 않는 원인 | **허용** (통과가 로그로 남습니다) | 아니오 |

여기서 두 가지 결론이 따라오며, 그것이 이 표가 존재하는 이유입니다.

> **실행 통제를 켜도 일정에 따라 도는 배치 잡은 계속 일정대로 돕니다.** 승인은 *사람*이
> 정규 절차 밖에서 개입하려 할 때 필요한 것입니다. 야간 실행은 요청이 아니고, 누구의 승인도
> 받지 않으며, 소비되지도 않습니다 — 그냥 무기한 통과합니다. 주기 잡도 함께 멈추게 하려면
> 그 잡에 `Block cron (timer) triggers`를 설정하거나 잡을 비활성화하십시오.

> **차단은 큐 진입 시점에만 일어납니다.** 플러그인이 하는 어떤 일도 이미 실행 중인 빌드를
> 중단시키지 않습니다 — 전역 스위치를 뒤집는 것도, 잡 속성을 토글하는 것도, 잡 설정을
> 바꾸는 것도, 빌드 도중 권한 창이 만료되는 것도 마찬가지입니다.

*사람이 시작한* 실행이 차단되면 요청 화면 링크가 있는 "승인 필요" 페이지나 CLI 메시지를
받습니다 — 조용한 실패는 없습니다. 자동화가 시작한 실행이 차단되는 경우(`Block cron
(timer) triggers`, 허용되지 않은 상위 잡)는 조용히 거부되고 로그에 남습니다.

## 기능

실행 통제

- 실행 단위 요청과 승인. 요청과 반려 양쪽 모두 사유가 필수입니다. 요청자는 누가, 언제, 왜
  반려했는지 볼 수 있습니다.
- 결재자는 전역 설정에 있는 명시적인 사용자 ID 목록이며, 요청자가 그중 하나를 고릅니다.
  지정된 결재자만 그 요청을 결정할 수 있습니다 — 목록에 있는 다른 누구도, 관리자도, 대신
  결정할 수 없습니다. 결정이 내려지기 전까지 요청자는 결재자를 바꿀 수 있고, 그 변경은
  기록됩니다.
- 잡은 결재자 목록을 더 좁힐 수 있습니다(`Job-level approvers`).
- 요청은 만료됩니다. 대기 중인 요청은 `pendingTimeoutHours` 후, 승인되었으나 시작되지 않은
  요청은 `approvedRunTimeoutMinutes` 후에 만료됩니다. 요청자는 아직 대기 중인 요청을 취소할
  수 있습니다.
- 요청이 열려 있는 동안 대상 잡의 이름이 바뀌거나 이동되면, 그 요청은 다른 잡에 대해
  실행되는 대신 `INVALIDATED`로 끝납니다.

변경 통제

- 잡 또는 폴더로 범위가 한정된 기간 제한 권한 부여. `CREATE`, `CONFIGURE`, `DELETE`의 임의
  조합이 가능합니다.
- 만료는 권한 검사마다 시각을 비교해 판정하므로 재시작을 견디고 스케줄러가 필요 없습니다.
- `BatchControl/Manage` 보유자는 활성 권한을 즉시 회수할 수 있습니다.
- 어떤 권한 부여에도 속하지 않은 상시 `Item/Configure`, `Item/Create`, `Item/Delete`를
  사용자가 보유하고 있으면 관리 모니터가 경고합니다. 그것이 변경 통제를 무의미하게 만드는
  상황입니다.

감사 이력

- 모든 빌드가 기록됩니다 — Freestyle과 Pipeline 모두 — 잡, 원인(`USER` / `TIMER` /
  `UPSTREAM` / `APPROVED_REQUEST` / `SCM` / `OTHER`), 사용자, 파라미터, 결과, 소요 시간,
  그리고 Jenkins가 기록한 경우 누가 중단시켰는지까지.
- 모든 잡 생성 / 설정 / 삭제 / 이름 변경 / 이동이 어떤 경로로 왔든(UI, REST `config.xml`,
  CLI, Job DSL) 기록되며, 설정 변경에는 unified diff와 그 작업을 인가한 권한 부여로 가는
  링크가 — 또는 권한 부여가 없었다면 명시적인 "no grant"가 — 함께 남습니다.
- `FAILURE`와 `UNSTABLE` 결과는 마지막 콘솔 100줄을 첨부한 **오류 건(incident)**을 자동으로
  엽니다. 오류 건의 각 상태 전이에는 사용자, 시각, 코멘트가 따릅니다. 오류 건에서 바로
  재실행을 요청할 수 있고, 성공한 재실행은 그 오류 건에 다시 연결됩니다. (오류 건 상태
  표기: `OPEN`, 다음 `ACKNOWLEDGED`, 다음 `RESOLVED`. 되돌아가는 길은 없습니다.)
- 기록은 빌드와 분리된 `$JENKINS_HOME/batch-control/`에 살기 때문에 빌드 로테이션보다 오래
  남습니다. 추가 전용입니다. 수정·삭제 API는 없고 보존 기간 만료만 있습니다.
- 기간, 잡, 사용자, 결과, 상태로 필터링. 월간 집계. 모든 목록에 대한 CSV 내보내기.

## 요구 사항

| | |
|---|---|
| Jenkins | 2.568.3 이상 (플러그인이 컴파일되는 기준선) |
| 플러그인 의존성 | `structs`, `cloudbees-folder` — 플러그인 관리자가 자동으로 해결합니다 |
| 권한 전략 | 실무상 matrix 계열 전략이 필요합니다. [설정](#2-래핑-권한-전략-선택) 참고 |

Batch Control의 다섯 권한은 권한 매트릭스를 그려 주는 권한 전략에 노출됩니다. Jenkins 내장
"Logged-in users can do anything"이나 "Anyone can do anything"에서는 이들을 할당할 화면
자체가 없으므로, 먼저 **Matrix Authorization Strategy**(또는 동등한 것)를 설치하십시오.
변경 통제는 추가로 이 플러그인 자체의 래핑 전략이 선택되어 있어야 합니다 — 아래 참고.

## 설치

플러그인이 공개된 뒤에는 업데이트 센터에서. **Manage Jenkins → Plugins → Available**에서
*Batch Control*을 검색해 설치합니다.

직접 빌드한 것을 설치하려면 `.hpi`를 빌드해 **Manage Jenkins → Plugins → Advanced settings
→ Deploy Plugin**에서 업로드합니다.

```sh
mvn clean package          # target/batch-control.hpi 생성
mvn hpi:run                # http://localhost:8080/jenkins 에 로컬 Jenkins
```

소스에서 빌드하려면 Maven과, CI 빌드가 쓰는 버전에 맞는 JDK(JDK 21)가 필요합니다.

설치 후에도 달라지는 것은 없습니다. 두 스위치 모두 기본값이 꺼짐이고, 꺼진 상태에서
플러그인은 아무것도 차단하지 않으며 잡 수준 UI도 전혀 보이지 않습니다.

## 설정

### 1. 필요한 것을 켠다

**Manage Jenkins → System → Batch Control.** `BatchControl/Manage`가 필요합니다
(`Overall/Administer`가 함의합니다). 어느 스위치를 토글하는 것 자체도 `CONFIG_TOGGLE` 변경
기록으로 남습니다.

| 항목 | 기본값 | 의미 |
|---|---|---|
| Enable run control | 꺼짐 | 큐 진입 시점의 승인 게이트를 켭니다 |
| Enable change control | 꺼짐 | 적시 권한 창과 삭제 거부를 켭니다 |
| Approvers | 비어 있음 | 결재자로 지정될 수 있는 사용자 ID |
| Allow administrators to approve their own requests | 켜짐 | 끄면 직무 분리가 관리자에게도 적용됩니다 |
| Pending request timeout (hours) | 72 | 대기 중인 요청이 이 시간 후 만료됩니다 |
| Approved-but-not-run timeout (minutes) | 60 | 승인되었으나 큐에 들어가지 않은 요청이 이 시간 후 만료됩니다 |
| Grant duration options (minutes) | 15, 30, 60 | 권한 요청 폼에서 제시되는 선택지 |
| Maximum grant duration (minutes) | 240 | 직접 입력한 기간의 상한 |
| Results that open an incident | FAILURE, UNSTABLE | `ABORTED`를 추가할 수 있습니다 |
| Retention period (months) | 24 | 이보다 오래된 월 파일이 삭제되며, 그 삭제도 기록됩니다 |

요청은 지정된 결재자가 Approvers 목록에 있고 **또한** 결정 시점에
`BatchControl/Approve`를 보유하고 있지 않으면 생성될 수 없습니다 — 둘 다 검사되며, 두 번째는
결정 시점에 다시 검사됩니다.

### 2. 래핑 권한 전략 선택

**이것을 하기 전까지 변경 통제는 아무 일도 하지 않습니다.** 가장 놓치기 쉬운 단계입니다.
권한 부여가 승인되는데 아무 효력이 없는 상태가 됩니다.

**Manage Jenkins → Security → Authorization** → **`Batch Control (wrapping)`**을 선택하고,
실제 전략(예: Project-based Matrix Authorization)을 그 delegate로 선택합니다. 기존 매트릭스
설정은 delegate 안에 그대로 유지됩니다. 래퍼는 승인된 권한 창이 열려 있는 동안
`Item/Create`, `Item/Configure`, `Item/Delete`를 *추가*할 뿐이고, 그 외 모든 판단은 바꾸지
않고 위임합니다. 활성 권한 부여가 없으면 delegate 단독과 정확히 동일하게 동작합니다.

변경 통제가 켜져 있는데 이 전략이 선택되어 있지 않으면, 관리 화면의 관리 모니터가 그렇다고
알립니다.

> **delegate 없이 래핑 전략을 저장하지 마십시오.** delegate가 없으면 닫힌 쪽으로 실패하여
> 관리자를 포함한 모든 사람의 모든 권한을 거부하며, 돌아오는 유일한 방법은 디스크의
> `$JENKINS_HOME/config.xml`을 편집하는 것입니다.

실행 통제와 기록에는 이 전략이 **필요하지 않습니다**.

### 3. 권한 할당

권한 매트릭스에 **Batch Control** 그룹으로 다섯 권한이 나타납니다.

| 권한 | 허용하는 것 |
|---|---|
| `BatchControl/Request` | 승인 보호된 잡에 대한 실행 요청 생성 |
| `BatchControl/Approve` | 실행 요청과 권한 요청의 승인 또는 반려 |
| `BatchControl/RequestGrant` | 임시 변경 권한(적시 권한 부여) 요청 |
| `BatchControl/ViewHistory` | 이력 화면, 대시보드, CSV 내보내기 조회 |
| `BatchControl/Manage` | 전역 설정 관리와 권한 부여 회수 |

`Manage`는 `Overall/Administer`가 함의하고, 나머지 넷은 `Manage`가 함의하므로 관리자는 모든
검사를 통과합니다.

요청자에게 유용한 조합은 `Overall/Read`, `Item/Read`, `Item/Build`,
`BatchControl/Request`, `BatchControl/RequestGrant`이며, `Item/Configure`는 의도적으로 **주지
않습니다**. 그것이 바로 `CONFIGURE` 권한 부여가 존재하는 이유이기 때문입니다. 결재자는
보통 `BatchControl/Approve`와 `BatchControl/ViewHistory`를 받고, `BatchControl/Request`는
받지 않습니다. `ViewHistory`는 이름이 시사하는 것보다 넓다는 점에 주의하십시오 —
[알려진 제약](#알려진-제약) 참고.

### 4. 잡 설정

잡 설정에 **Batch Control** 블록이 나타납니다.

| 항목 | 기본값 | 의미 |
|---|---|---|
| Require approval to run | 아래 주석 참고 | 사람이 시작하는 실행에 승인된 요청이 필요합니다 |
| Block cron (timer) triggers | 꺼짐 | `TimerTrigger` 빌드도 멈춥니다 |
| Block upstream triggers | 꺼짐 | 상위 잡이 트리거한 빌드도 멈춥니다 |
| Allowed upstream jobs | 비어 있음 | 위가 켜져 있을 때만 의미가 있습니다. 그래도 이 잡을 트리거할 수 있는 상위 잡. 비어 있으면 *어떤* 상위 잡도 할 수 없습니다. |
| Job-level approvers (optional restriction) | 비어 있음 | 이 잡에 대해 전역 결재자 목록을 좁힙니다 |

**기본값에 관한 주석.** 실행 통제가 켜져 있는 동안에는 **새로 생성되는 모든 잡이 "Require
approval to run"이 활성화된 상태로 시작합니다.** 누가 만들었는지, 어떻게 만들었는지는
상관없습니다. 스크립트로 잡을 생성하는 인스턴스에서 실행 통제를 켜기 전에
[알려진 제약](#알려진-제약)의 자동화 주의 사항을 읽으십시오.

동작하는 참조 설정 — Dockerfile, 플러그인 목록, 보안 부트스트랩, 전역 설정 — 이
[`e2e/`](e2e/) 아래에 있습니다. 배포 템플릿이 아니라 종단 간(end-to-end) 스위트를 돌리기
위한 것이지만, 실제로 동작하는 진짜 설정이며 초기화 스크립트가 위 네 단계를 각각
보여 줍니다.

## 화면

모든 것이 왼쪽 사이드바의 **Batch Control**(`/batch-control/`) 아래에 있습니다. 각 절은
권한으로 제한되므로 사용자는 자기가 할 수 있는 것만 봅니다.

**Run Requests** — 요청 목록과 각 요청의 상세: 잡, 저장된 그대로의 파라미터, 사유, 요청자,
지정된 결재자, 상태, 결정 이력. 결재자는 여기서 승인하거나 반려하며, 반려에는 사유가
필요합니다. 요청자는 요청이 대기 중인 동안 결재자를 바꾸거나 취소할 수 있습니다. 보호된
잡에서는 사이드바에 Build Now 대신 **Request Run**이 있고, 그것이 그 잡의 파라미터를 담은
같은 폼을 엽니다.

**Grants** — 권한 요청과 활성 권한: 요청에는 범위, 동작, 기간, 사유. 활성 창에는 남은 시간,
만료된 창들의 이력, 새 권한을 요청하는 링크. `Manage` 보유자는 활성 권한을 회수할 수
있습니다.

**Run Dashboard** — 인스턴스 전체의 모든 빌드. 원인 분류, 사용자, 파라미터, 결과, 소요 시간,
누가 중단시켰는지. 승인된 실행은 그것을 인가한 요청으로 되돌아가는 링크를 갖습니다. 기본은
최근 7일, 페이지당 50건입니다.

**Incidents** — 자동으로 열린 실패들과 콘솔 로그의 끝부분. 확인(acknowledge), 해결, 코멘트,
또는 원래 파라미터가 미리 채워진 재실행 요청.

**History** — 실행, 오류 건, 변경 기록, 요청이라는 네 종류 기록에 대한 기간·잡·사용자·결과·
상태 필터. 각각 CSV 내보내기(`runs.csv`, `incidents.csv`, `changes.csv`, `requests.csv`)가
있으며, 스프레드시트 수식으로 읽힐 수 있는 값은 무력화됩니다. 월간 집계는 실행 수, 성공 /
실패 / 불안정 수, 오류 건 수, 승인 / 반려 수를 줍니다.

**Change Records** — 생성 / 설정 / 삭제 / 이름 변경 / 이동의 궤적. 설정 변경에는 unified
diff가, 권한 부여가 있었던 경우에는 그 변경이 어느 권한 부여 아래에서 이루어졌는지가
함께 나옵니다.

## 알려진 제약

여기에 숨긴 것은 없습니다. 그러지 않으면 이 각각이 운영에서 발견될 것이기 때문입니다.

### 통제의 범위

1. **관리자는 모든 통제를 우회합니다.** `Overall/Administer`는 모든 Batch Control 권한과 모든
   Jenkins 권한을 함의합니다. 이 플러그인은 관리자를 막으려 하지 않습니다. 관리자가 한 일을
   기록합니다.
2. **플러그인이 인식하는 원인만 분류됩니다.** 자체 `Cause` 타입을 가진 트리거 플러그인이
   — 예를 들어 범용 웹훅 트리거가 — 시작한 빌드는 사람이 시작한 것으로 인식되지 않으므로
   승인 게이트를 **통과합니다**. 통과는 로그로 남습니다. 이것은 타이머·상위 잡 정책과 같은
   기본 개방(default-open) 태세입니다. 게이트에 의존하기 전에 자신이 쓰는 트리거 플러그인이
   어떻게 동작하는지 확인하십시오.
3. **cron, 상위 잡, SCM 트리거는 기본적으로 통과하며**, 권한 창 동안 설치된 것은 그 창이
   닫힌 뒤에도 계속 발동합니다. 만료는 *권한*을 제거하는 것이지, 그 권한으로 설정된 자동화를
   제거하는 것이 아닙니다.
4. **Pipeline `build` 스텝에서 호출된 차단된 잡은 호출자를 실패시킵니다.** 보호된 잡이 큐
   진입에서 거부되면 상위 잡은 `FAILURE`로 끝납니다. `wait: false`여도 그렇습니다. 이것은
   Jenkins의 동작이며 이 플러그인의 선택이 아닙니다.
5. **Jenkins 밖에서 이루어진 변경은 기록되지 않습니다.** 디스크의 `config.xml`을 편집한 뒤
   "Reload Configuration from Disk"를 쓰면 `CONFIGURE` 기록이 남지 않습니다. Jenkins가 그것을
   변경이 아니라 로드로 보고하기 때문입니다.
6. **Multibranch와 organisation folder의 하위 잡은 변경 통제되지 않습니다.** 그 설정은 생성된
   것이므로 실행과 실패만 기록됩니다.

### 권한 전략

7. **적시 변경 통제는 matrix 계열 권한 전략에서만 동작합니다.** **Role-Based Authorization
   Strategy**가 전략인 경우 **실행 통제와 기록만** 동작하고 권한 창은 동작하지 않습니다. Role
   Strategy를 감싸면 권한 판단은 올바르게 남지만 그 자체의 역할 관리 화면이 깨지므로
   지원하지 않습니다. Role Strategy를 쓰고 있으면 관리 모니터가 그렇다고 알립니다. 지원은
   가능한 향후 항목이고, 현재의 것은 아닙니다.
8. **변경 통제는 권한 기반이며 저장 기반이 아닙니다.** Jenkins는 잡 설정의 "Save" 자체를
   가로챌 방법을 제공하지 않으므로, 래핑 전략이 선택되지 않으면 변경 통제는 아무 효력이
   없습니다 — 모니터 경고만이 그것을 알려 줍니다.
9. **delegate 없이 저장된 래핑 전략은 관리자를 포함해 모두를 잠가 버리며**,
   `$JENKINS_HOME/config.xml`을 편집해야만 복구할 수 있습니다.
10. **권한 부여는 구체적인 잡이나 폴더를 지정해야 합니다.** 인스턴스 전체 권한 부여는
    없으므로, 권한 부여는 이름이 지정된 폴더 안에서만 `Item/Create`를 줄 수 있고 Jenkins
    루트에서는 결코 줄 수 없습니다.
11. **"상시 변경 권한" 모니터는 최선 노력(best-effort)입니다.** 그 판정은 최대 5분까지
    캐시되고 관리자는 의도적으로 무시하므로, 이는 경고이며 결코 집행 지점이 아닙니다.

### 자동화와 생성된 잡 — 실행 통제를 켜기 전에 읽으십시오

12. **실행 통제가 켜져 있는 동안 새로 생성되는 모든 잡은 `approvalRequired=true`로
    시작합니다** — 생성 경로가 무엇이든(UI, REST, CLI, Job DSL, 시드 잡), 생성자가 누구든
    마찬가지입니다. 생성 페이로드에 명시된 `approvalRequired=false`는 덮어써집니다. 나중에
    통제를 끄려면 잡을 편집해야 하고, 그 편집 자체가 기록되는 변경입니다. 그 기록되는 경로가
    의도된 출구입니다.

    **인스턴스가 스크립트로 잡을 생성한다면 이것을 계획에 넣으십시오.**
    `approvalRequired: false`를 고정하는 Job DSL이나 JCasC 정의는 *새* 생성에 대해
    멱등적이지 않습니다. 첫 시드 실행은 통제된 상태로 잡을 만들고, 두 번째 실행(생성이 아니라
    갱신)에서만 그것이 해제됩니다. 무인으로 실행되어야 하는 생성된 잡에는 그 두 번째 패스가
    필요하며, 그 패스는 기록됩니다.

    이것은 이론적인 이야기가 아닙니다. 이 저장소 자체의 e2e 환경에 있는 시드 잡들이 이
    기본값이 들어온 첫날 조용히 빌드를 멈췄습니다 — 무인 실행이 존재 목적 그 자체였던 잡들까지
    포함해서 — 그리고 해결책은 시드 스크립트가 잡을 만든 직후 그 속성을 해제하게 만드는
    것이었습니다. 깨지는 것은 자동 빌드가 아니라는 점에 주의하십시오. 타이머, 상위 잡, SCM
    원인은 여전히 통과합니다. 멈추는 것은 사람이 눌러야 하는 모든 것입니다.

13. **multibranch 프로젝트가 생성한 브랜치 잡은** 그 기본값에서 **면제됩니다.** 설정 화면이
    없으므로 통제를 끌 방법이 없을 것이고, 재인덱싱이 어차피 그 설정을 다시 생성합니다. 그
    실행은 여전히 기록됩니다.

### 비밀값

14. **콘솔 로그 마스킹에는 탐지 한계가 있습니다.** 오류 건의 로그 끝부분이 저장될 때, 그
    빌드 자신의 민감 파라미터 값과 Jenkins `Secret` 평문은 마스킹됩니다. **그 외에 비밀값이
    출력되는 모든 경로 — 스크립트가 echo한 토큰, 스택 트레이스, 서드파티 도구 — 는 탐지되지
    않으며 그대로 저장되어** `ViewHistory` 보유자 누구에게나 **그대로 표시됩니다.** 범용 비밀값
    패턴 탐지는 의도적으로 기각되었습니다. 잘못된 안심을 주면서도 여전히 놓치기 때문입니다.
15. **비밀 파라미터가 있는 잡은 충실하게 재실행할 수 없습니다.** 요청 파라미터는 저장 전에
    마스킹되므로 평문 비밀값이 기록되는 일은 결코 없지만, 그렇기 때문에 승인된 실행과 오류
    건에서 미리 채워진 재실행은 원래 값이 아니라 마스크를 제출합니다. 패스워드 파라미터가 있는
    잡의 승인 기반 실행은 현재 사용할 수 없습니다.
16. **저장된 설정 스냅샷은 마스킹되지 않습니다.** 변경 기록에 보이는 diff는 마스킹되지만
    `batch-control/snapshots/<job>.xml`은 원본 `config.xml`을 보관합니다. 그 안의 비밀값은
    `$JENKINS_HOME/jobs/*/config.xml`에서와 정확히 같이 Jenkins가 암호화한 상태입니다 — 같은
    디스크 위의 같은 보호이며, 그 이상은 아닙니다.
17. **비밀값만 건드린 변경에는 diff 대신 설명 주석이 붙습니다.** 양쪽이 동일하게 마스킹되어
    실제 diff는 비어 있을 것이기 때문입니다.

### 가시성과 권한

18. **`BatchControl/ViewHistory`는 인스턴스 전체 감사 읽기이며, 잡별로 필터링되지
    않습니다.** 이력 화면, 대시보드, CSV 내보내기는 **모든** 요청과 실행을 — 잡 이름, 파라미터
    값, 사유, 요청자, 결재자, 결정 코멘트를 — `Item/Read` 검사도 소유자 필터도 없이 보유자
    누구에게나 보여 줍니다. 이는 객체별로 필터링*되는* Run Requests와 Grants 화면과는 다른
    규칙입니다. `ViewHistory`를 그것인 바대로 취급하십시오. 감사 궤적 전체에 대한 가시성입니다.
19. **`ViewHistory`는 오류 건 상태 변경도 인가합니다.** 오류 건의 확인, 해결, 코멘트가
    `ViewHistory`로 제한되므로 읽기 전용 감사자 계정도 오류 건을 닫을 수 있습니다. 재실행
    요청은 올바르게 `Request`를 필요로 합니다.
20. **요청의 가시성은 잡 자신의 읽기 경계를 따릅니다.** 실행 요청은 `Manage` 보유자, 그
    요청자, 지정된 결재자, 그리고 대상 잡에 `Item/Read`를 가진 누구에게나 보입니다.
    `Item/Read`가 널리 부여된 인스턴스에서는 사유와 파라미터 값이 널리 보입니다.
21. **지정된 결재자가 아닌 `Approve` 보유자는 그 요청에 대해 아무것도 보지 못합니다** — 지정된
    결재자만 그것을 결정할 수 있으므로 일관된 동작입니다. 결재자 부재는 결정이 내려지기 전에
    요청자가 결재자를 바꾸는 것으로 처리합니다. 위임이나 대리 체인은 없습니다.
22. **권한 요청에는 결재자 변경이 없습니다.** 실행 요청과 달리, 대기 중인 권한 요청의 결재자를
    바꾸는 것은 그것을 취소하고 새로 만드는 것을 뜻합니다.
23. **활성 권한 부여는 그 보유자 자신과** `Manage` **보유자에게만 보입니다.**
24. **결재자 계정은 실제 사람과 일대일로 대응해야 합니다.** 플러그인은 사용자 ID만 비교할 수
    있습니다. 한 사람이 두 계정을 가지고 — 하나로 요청하고 다른 하나로 승인하면 — 2인 규칙을
    만족시키며 정상적인 비-자가 승인으로 기록됩니다. 계정과 결재자 목록을 정직하게 유지하는
    것은 조직의 통제이며, 플러그인이 집행할 수 있는 것이 아닙니다.

### 기록과 화면

25. **폴더 이름 변경은 하위 잡마다 `MOVE` 기록 하나씩을 만들고**, 폴더 자체에 대한 `RENAME`을
    더합니다. 이는 정확합니다 — 모든 자식의 전체 이름이 실제로 바뀌었습니다 — 그러나 한 번의
    이름 변경이 많은 수의 기록을 만들 수 있다는 뜻입니다.
26. **만료된 창의 거부 페이지는 Jenkins 자신의 것입니다.** `CONFIGURE` 창이 만료된 뒤 설정을
    저장하면 Jenkins 기본 403 페이지가 나옵니다. 플러그인은 의도적으로 그것을 가로채지
    않습니다. Jenkins가 그것을 확장 지점으로 제공하지 않으며, 가로챈다는 것은 인스턴스의
    *모든* 권한 거부를 떠맡는다는 뜻이기 때문입니다. 만료 안내, 만료된 창의 이력, 재요청
    링크는 대신 Grants 화면에 있고, 만료 전에 갱신할 수 있도록 남은 시간도 거기에 표시됩니다.
    **편집하던 설정은 복원되지 않습니다** — 복원한다는 것은 방금 인가되지 않았다고 판정된
    변경을 저장한다는 뜻이기 때문입니다.
27. **월간 집계의 경계 사례**(현재 동작이며 아직 확정된 것은 아님): `ACKNOWLEDGED` 오류 건은
    열린 열에도 해결된 열에도 집계되지 않으며, 승인되었다가 만료되거나 무효화된 요청은 승인
    열에도 반려 열에도 집계되지 않습니다.
28. **Grants 절은 변경 통제가 꺼져 있어도 보입니다.** 권한 전략이 의도적으로 그 스위치와
    독립적이기 때문입니다. Role Strategy 알림도 마찬가지로 두 스위치가 모두 꺼져 있어도
    나타납니다.
29. **속도 제한이 없습니다.** 사유(4,000자)와 각 문자열 파라미터 값(10,000자)에는 크기 상한이
    있지만, 사용자별 요청 속도 제한도 동시 대기 요청 수 상한도 없습니다. 대량으로 생성된
    요청은 대기 타임아웃이 정리할 때까지 쌓입니다. 마찬가지로 설정 변경 속도를 제한하는 것도
    없으므로, 한 창 안에서 저장을 몰아치면 단일 저장소 락에 대해 diff와 스냅샷 쓰기가 몰아칩니다.

### 설계상 범위 밖

`Overall/Administer`에 의한 우회, 디스크에서 직접 이루어진 편집의 탐지, 배치 애플리케이션
*내부*의 스텝 재시작이나 재개, Git에 있는 Pipeline 스크립트 변경의 통제. 이 플러그인은
이들 중 어느 것도 시도하지 않습니다.

## 로드맵

이번 릴리스에는 없으며, 그것은 의도된 것입니다.

- 요청 생성, 결정, 임박한 권한 만료, 실패에 대한 **알림** — 이메일이 먼저, Slack 등을 위한
  확장 지점과 함께.
- **REST API와 외부 연동** — HTTP로 요청·결정·이력, JCasC를 통한 전역 설정, Audit Log
  플러그인으로 내보내는 승인 이벤트.
- **다단계 승인 체인** — 단일 지정 결재자를 확장하는 것.
- **Role-Based Authorization Strategy를 위한 적시 변경 통제** — matrix 계열 전략에 쓰인 래핑
  전략과는 다른 메커니즘이 필요합니다.

## 비슷한 플러그인들과의 차이

- **Pipeline `input` 스텝**은 이미 시작된 실행 *내부*의 한 지점을 게이트하며, Pipeline 잡에서만
  쓸 수 있고, 그 기록을 빌드 안에 남깁니다. Batch Control은 실행의 *시작*을 게이트하고, 모든
  잡 타입에 대해 동작하며, 기록을 빌드 보존과 무관하게 보관합니다.
- **감사 궤적 계열 플러그인**은 무슨 일이 있었는지를 기록합니다. 요청, 지정된 결재자, 결정,
  만료되는 권한이라는 개념이 없습니다. Batch Control은 감사 이력이 부산물인 통제 평면입니다.
- **matrix 및 역할 기반 권한**은 상시 권한을 할당합니다. Batch Control은 당신이 설정한 전략이
  무엇이든 그것을 감싸고, 승인된 창 안에서만 존재하는 권한을 추가하며, 그 외 모든 판단은
  그것에 위임합니다.

## 기여

이슈와 풀 리퀘스트를 환영합니다. **[`CONTRIBUTING.md`](CONTRIBUTING.md)가 안내서입니다** —
빌드, 저장소 구조, 문서와 커밋 메시지가 쓰는 식별자 어휘, 테스트 관례, 종단 간 환경, 그리고
이미 이 프로젝트의 시간을 잡아먹은 함정들을 다룹니다. 첫 변경 전에 읽어 주십시오. 관례 몇
가지는 통상적이지 않습니다.

그전에도 알아 둘 만한 두 가지가 있습니다.

- `docs/SPEC.md`가 기능 계약입니다. 코드와 스펙이 어긋나면 코드가 틀린 것입니다. 동작의 변경은
  먼저 스펙의 변경이며, 확정된 모든 설계 결정의 근거는 `docs/DECISIONS.md`에 기록되어
  있습니다 — 어떤 결정을 뒤집자고 제안하기 전에 해당 항목을 읽어 주십시오.
- `docs/ARCHITECTURE.md`가 확장 지점, 패키지 구조, 디스크 저장 형식을 설명합니다.

새로 클론한 것이 빌드되는지 확인하려면(JDK 21, Maven 3.9.16 이상. 약 10분):

```sh
mvn clean verify   # 컴파일, 전체 테스트 스위트, SpotBugs — 실패 0, 버그 0으로 끝나야 합니다
mvn hpi:run        # http://localhost:8080/jenkins 에 로컬 Jenkins
```

그 이상 — 한 클래스만 돌리는 것, 기대되는 테스트 수, 환경 구성, `e2e/`의 Docker 기반 종단 간
환경, 풀 리퀘스트에 필요한 것 — 은 [`CONTRIBUTING.md`](CONTRIBUTING.md)에 있습니다.

보안 취약점에 대해서는 GitHub 이슈를 **열지 마십시오.** Jenkins 플러그인 취약점은 Jenkins
프로젝트의 이슈 트래커를 통해 **SECURITY** 프로젝트에서, `specific-plugin` 컴포넌트를 쓰고
이슈 요약에 플러그인 이름을 적어 비공개로 신고합니다.

<https://issues.jenkins.io/secure/CreateIssueDetails!init.jspa?pid=10180&issuetype=10103>

`jenkinsci-cert@googlegroups.com`으로 메일을 보내면 보안팀이 대신 이슈를 등록해 줍니다. 전체
정책은 <https://www.jenkins.io/security/reporting/>에 있습니다.

이름을 적으십시오.)*
