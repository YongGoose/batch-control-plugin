# Batch Control

CI 서버가 아니라 **배치 실행 관리 도구**로 운영되는 Jenkins를 위한 실행 승인, 기간 제한
변경 권한, 추가 전용(append-only) 감사 이력.

## 왜 필요한가

야간·주기 배치 작업을 Jenkins로 돌리는 조직이 많습니다. Spring Batch 잡, 데이터 적재, 정산
실행, 대조 스크립트 같은 것들입니다. 그 잡들은 운영 시스템이므로, 일정 밖에서 사람이 손으로
하나를 시작하거나 잡이 하는 일을 바꾸는 것은 운영 변경입니다. 그러면 운영 변경에 늘 따라오는
질문이 따라옵니다. 누가 시작했는지, 어떤 파라미터로 했는지, 누가 동의했는지, 왜 했는지.

Jenkins 혼자서는 여기에 절반만 답합니다. `Item/Build`가 있으면 아무 잡이나 아무 때나 시작할
수 있고, `Item/Configure`가 있으면 아무 잡이나 영구히 바꿀 수 있습니다. 무슨 일이 있었는지의
기록은 빌드 안에 있으니, 빌드가 로테이션으로 지워지면 기록도 함께 사라집니다.

Batch Control은 그 빈자리를 채웁니다. 보호된 잡을 수동으로 실행하는 일은 지정된 결재자가
승인해야 큐에 들어가는 요청이 되고, 설정 변경에는 스스로 만료되는 임시 권한이 필요하며,
실행과 결정과 설정 변경과 실패는 빌드 보존 정책과 무관한 저장소에 기록됩니다. 설치만으로
달라지는 것은 없습니다. 두 통제는 관리자가 켤 때까지 꺼져 있고, 서로 독립적으로 켜집니다.

## 두 가지 통제

**실행 통제**는 빌드를 시작하는 일을 통제합니다. 이것이 켜져 있고 잡에 "Require approval to
run"이 설정되어 있으면, 그 잡을 실행하려는 사람은 파라미터와 사유를 함께 제출합니다(둘 다
필수입니다). 지정된 결재자는 바로 그 파라미터를 보고 승인하거나, 요청자가 읽을 수 있는 사유를
달아 반려합니다. 그 요청을 결정할 수 있는 사람은 지정된 결재자 한 명뿐입니다. 결재자 목록에
있는 다른 사람도, 관리자도 대신 결정할 수 없습니다. 다만 결정이 내려지기 전까지는 요청자가
결재자를 바꿀 수 있고, 그 변경도 기록됩니다. 승인되면 플러그인이 저장된 파라미터 그대로
빌드를 큐에 넣습니다. 승인 뒤에 파라미터를 고칠 수 있는 경로는 없으며, 승인은 큐 투입 한 번에
소비되므로 재생하거나 다시 큐에 넣거나 재빌드할 수 없습니다. 시도하면 차단되고 기록에
남습니다.

**변경 통제**는 잡을 바꾸는 일을 통제합니다. 잡을 생성·설정·삭제할 권한을 **상시로 갖고 있지
않은** 사용자가 대신 권한 창을 요청합니다. 범위(잡 하나 또는 폴더 하나),
`CREATE`·`CONFIGURE`·`DELETE`의 조합, 기간, 사유를 적습니다. 권한 창은 그 사람이 이미 가진 권한에
해당 권한을 **더해 주는** 것이고, 창이 열려 있는 동안만 유효합니다. 무엇을 빼앗지도 않고, 이미
상시 권한을 가진 사람에게 창을 강제하지도 않습니다. 그런 상시 권한 보유자를 찾아 알려 주는 것이
"상시 변경 권한" 모니터의 역할입니다. 삭제만 예외입니다. 변경 통제가 켜져 있는 동안에는 상시
권한으로 삭제가 허용되는 사용자라도 활성 `DELETE` 창이 있어야 잡을 삭제할 수 있고, 거부되지 않는
것은 관리자뿐입니다. 폴더 사이의 항목 이동(folders 플러그인의 `Item/Move`)은 여기서 삭제하고
저기서 생성하는 것으로 취급합니다. 변경 통제가 켜져 있는 동안 `Overall/Administer`가 없는
사용자는 그 항목의 `Item/Delete`와 대상 폴더의 `Item/Create`를 둘 다 가진 경우에만(각각 상시
권한이든 활성 권한 창이든) 항목을 옮길 수 있고, `CREATE` 창의 이름 제한은 옮겨지는 항목의 이름에
적용됩니다. 거부된 이동은 아무것도 바꾸지 않고, 사용자에게 이유를 알리며, `GRANT_VIOLATION`으로
기록됩니다. 실행 통제도 켜져 있으면 관리자가 아닌 사용자가 옮긴 잡은 새로 만든 잡처럼 활성화되지
않은 잠긴 상태로 도착하고 `HELD`로 기록되므로, 다시 무인 실행되려면 새 활성화가 필요합니다. 이
규칙은 folders 플러그인의 Move 동작(UI와 REST)에 적용됩니다. 승인을 받으면 자기 계정으로 작업하며, 평소의 Jenkins 안전장치는 모두 그대로
적용됩니다. 결재자가 결정하는 것은 **누가 무엇을 얼마 동안 바꿀 수 있는지**입니다. 변경 내용
자체를 승인하는 것이 아닙니다. 결재 시점에는 그 변경이 아직 존재하지도 않고 결재자에게 보이지도
않습니다. 실제로 무엇이 바뀌었는지는 나중에 변경 기록과 그 diff가 답합니다. 만료는 권한
검사마다 시각을 비교해 판정하므로, 타이머도 회수 절차도 없이 창이 닫히고 컨트롤러를 재시작해도
닫힌 채로 남습니다. `BatchControl/Manage` 보유자는 창을 미리 회수할 수도 있습니다.

기록은 둘 중 어느 것이 켜져 있는지와 무관합니다. 하나라도 켜져 있으면 실행, 변경, 결정,
실패가 모두 기록됩니다.

## 실행 통제가 막는 것과 막지 않는 것

실행 통제는 큐 진입 시점에 빌드를 가로채고, Jenkins가 그 투입에 붙인 **원인(cause)** 을 보고
판단합니다. 거부되는 것은 "Build Now", REST의 `build`와 `buildWithParameters`,
`jenkins-cli build`, Pipeline Replay, 그리고 빌드 토큰을 실어 보낸 투입입니다(토큰이 붙으면
Jenkins가 그 투입을 어느 사용자의 것으로도 기록하지 않습니다). 통과하는 것은 승인된 실행
요청(한 번), cron 등 타이머 트리거, 상위 잡이 발동시킨 빌드, SCM 트리거, 그리고 플러그인이
인식하지 못하는 원인의 빌드입니다.

여기서 두 가지 결론이 나오는데, 분명히 말해 둘 만합니다.

**승인이 필요한지는 그 잡이 몇 번째로 도는 실행인지가 아니라 무엇이 그 실행을 띄웠는지로
갈립니다.** 실행 통제는 투입마다 한 가지만 묻습니다. 이것을 사람이 시작했는가, 자동화가
시작했는가. 사람이 시작한 실행은 첫 번째든 백 번째든 매번 승인된 요청이 필요합니다. 타이머
트리거는 처음부터 끝까지 한 번도 필요하지 않습니다. 일정에 따라 도는 빌드는 애초에 요청이
아니고, 결재자가 판단할 대상도 없기 때문입니다. 그래서 실행 통제를 켜도 야간 배치 잡은 계속
일정대로 돌고, "처음 한 번 승인받으면 그다음부터는 자유"인 것도 아닙니다. 다음에 사람이 버튼을
누르면 그 사람은 또 승인을 받아야 합니다. 잡별로 더 조일 수는 있습니다. `Block cron (timer)
triggers`와 `Block upstream triggers`가 그 역할을 하고, 뒤쪽 항목에는 그래도 이 잡을 발동시킬
수 있는 상위 잡 목록을 함께 지정합니다. SCM 트리거와 인식되지 않는 원인은 좁힐 방법이
없습니다.

**차단은 큐 진입 시점에만 일어납니다.** 플러그인이 하는 어떤 일도 이미 실행 중인 빌드를
중단시키지 않습니다. 전역 스위치를 뒤집어도, 잡 속성을 바꿔도, 잡 설정을 바꿔도, 빌드 도중에
권한 창이 만료되어도 마찬가지입니다.

"Build Now", REST `build` 호출, CLI에서 거부된 사람은 요청 폼으로 가는 링크가 붙은 "승인 필요"
페이지나 CLI 메시지를 받습니다. 조용히 거부되는 경로는 둘입니다. 메시지를 읽을 화면이 없기
때문입니다. Pipeline Replay 는 그 UI 에 메시지를 띄울 통로가 없고, 빌드 토큰으로 들어온 투입은
호출자가 HTTP 상태 코드만 읽는 스크립트입니다. 둘 다 로그에 남고, 토큰 쪽은 차단된 시도로 감사
이력에도 기록되므로 아무도 못 본 거부를 나중에 확인할 수 있습니다. 잡별 옵션에 걸려 거부된 자동화
실행도 마찬가지로 조용히 돌려보내고 로그에 남깁니다.

## 요구 사항

Jenkins 2.568.3 이상(플러그인이 컴파일되는 기준선), 그리고 필수 플러그인 `cloudbees-folder`,
`ionicons-api`, `caffeine-api`.
의존성은 플러그인 관리자가 알아서 해결합니다.

아래 플러그인과의 연동은 선택 사항이라 없어도 Batch Control은 로드됩니다. 다만 설치되어 있다면
Batch Control이 컴파일된 버전 이상이어야 하며, Jenkins가 플러그인을 로드할 때 이를 강제합니다.

| 선택 플러그인 | 최소 버전 |
|---|---|
| `matrix-auth` | 3.3 |
| `role-strategy` | 927.v9cf5527c4085 |
| `configuration-as-code` | 2121.v86fe99d4b_b_a_b_ |
| `mailer` | 534.v1b_36f5864073 |
| `rebuild` | 338.va_0a_b_50e29397 |

이 중 하나라도 더 오래된 버전이 설치되어 있으면 그 플러그인을 업그레이드할 때까지 Batch Control이
로드되지 않습니다. **Manage Jenkins → Plugins → Available**에서 설치하면 필요한 업그레이드를 함께
제안하지만, **Deploy Plugin**으로 `.hpi`를 직접 올리면 제안하지 않으므로 해당 플러그인을 먼저
업그레이드하십시오.

Batch Control의 다섯 권한은 권한 매트릭스를 그려 주는 권한 전략에서만 보입니다. Jenkins 내장
"Logged-in users can do anything"에서는 이 권한들을 할당할 화면 자체가 없으므로, **Matrix
Authorization Strategy**나 그에 준하는 것을 먼저 설치하십시오. 변경 통제에는 아래에 적은 한
단계가 더 필요합니다.

## 설치

플러그인이 공개된 뒤에는 **Manage Jenkins → Plugins → Available**에서 *Batch Control*을
검색해 설치합니다. 직접 빌드한 것을 쓰려면 `.hpi`를 만들어 **Manage Jenkins → Plugins →
Advanced settings → Deploy Plugin**에서 올립니다. 소스 빌드에는 Maven과 JDK 21(CI 빌드가 쓰는
버전)이 필요합니다.

```sh
mvn clean package   # target/batch-control.hpi 생성
mvn hpi:run         # http://localhost:8080/jenkins 에 로컬 Jenkins
```

## 설정

### 1. 필요한 것을 켠다

설정은 두 곳에 있으며, 항목과 검사는 같습니다.

- **Batch Control → Configuration**(`/batch-control-configuration/`), Batch Control
  사이드바의 항목입니다. `BatchControl/Manage`만 있으면 되므로, 그 권한은 있지만
  `Overall/Administer`는 없는 사용자는 여기서 설정을 열고 저장합니다. Manage Jenkins를 열 수
  있는 사용자에게는 같은 페이지가 **Manage Jenkins**에 **Batch Control**로도 나옵니다.
- **Manage Jenkins → System**의 Batch Control 절. Jenkins 자체 페이지라 `Overall/Manage`가
  필요하므로, `BatchControl/Manage`만 가진 사용자는 여기서 403을 받습니다.

`BatchControl/Manage`는 `Overall/Administer`가 함의합니다. 스위치를 뒤집는 것 자체도 어느
페이지에서 저장했든 기록에 남습니다.

| 항목 | 기본값 | 의미 |
|---|---|---|
| Enable run control | 꺼짐 | 큐 진입 시점의 승인 게이트 |
| Enable change control | 꺼짐 | 권한 창, 삭제 거부, 상시 권한 경고 모니터 |
| Approvers | 비어 있음 | 결재자로 지정될 수 있는 사용자 ID |
| Allow administrators to approve their own requests | 켜짐 | 끄면 직무 분리가 관리자에게도 적용됩니다 |
| Pending request timeout (hours) | 72 | 대기 중인 요청이 이 시간 뒤 만료됩니다 |
| Approved-but-not-run timeout (minutes) | 60 | 승인됐지만 큐에 들어가지 않은 요청이 이 시간 뒤 만료됩니다 |
| Grant duration options (minutes) | 15, 30, 60 | 권한 창 요청 폼에 제시되는 선택지 |
| Maximum grant duration (minutes) | 240 | 직접 입력하는 기간의 상한 |
| Results that open an incident | FAILURE, UNSTABLE | `ABORTED`를 추가할 수 있습니다 |
| Retention period (months) | 24 | 이보다 오래된 월 파일을 삭제하며, 그 삭제도 기록됩니다 |

요청은 지정된 결재자가 Approvers 목록에 있어야 만들 수 있고, 결재자가 실제로 결정하는 순간에
`BatchControl/Approve` 보유 여부를 다시 검사합니다.

**변경 통제를 끄는 것은 기능 자체를 끊는 스위치이고, 그 방식이 단호합니다.** 스위치가 꺼져 있는
동안에는 어떤 권한 창도 아무 권한을 부여하지 않으므로, 모든 권한 판정이 원본 전략 단독의
판정이 됩니다. 플러그인을 설치하기 전과 같습니다. 그리고 스위치를 끄는 순간 그때 열려 있던 모든
권한 창이 **회수**되며, 창마다 회수 기록 하나가 남고 스위치를 뒤집은 계정이 그 기록에 적힙니다.
변경 작업을 하던 중이던 사람은 경고도 없이 마무리할 권한을 잃고, 되돌릴 방법은 새로 요청하는 것
뿐입니다. 이것은 의도한 선택입니다. 다른 쪽 선택지는 통제를 껐다고 생각한 뒤에도 최대 권한 기간
동안 창이 조용히 `Item/Configure`를 계속 부여하는 스위치였습니다. 꺼져 있는 동안에 쌓이는 것도
없습니다. 권한 창을 새로 요청하거나 승인할 수 없고, 두 거부 모두 이유를 알려 주며 기록에 남고,
Grants 화면도 닫힙니다. 그래서 변경 통제를 다시 켤 때 뒤늦게 효력을 발휘할 상태가 남아 있지
않습니다. 그 URL 자체는 의도적으로 응답합니다. 예전 북마크를 따라온 사람이 끊긴 링크가 아니라
무엇이 달라졌는지를 읽도록 하기 위해서입니다. 감사 이력은 이 과정에서 전혀 건드리지 않습니다.
History 와 Change Records 는 실제로 존재했던 창과 그 아래에서 이루어진 변경을 스위치 상태와
무관하게 계속 보여 줍니다.

### 2. Batch Control 권한 전략을 고른다

이 단계를 밟기 전까지 변경 통제는 아무 일도 하지 않습니다. 가장 놓치기 쉬운 단계이기도
합니다. 권한 창이 승인되는데도 효력이 전혀 없는 상태가 됩니다.

**Manage Jenkins → Security → Authorization**에서 matrix-auth를 쓰면(또는 쓰려면) **Batch
Control: Project-based Matrix Authorization Strategy**를, role-strategy(927 이상)를 쓰면
**Batch Control: Role-Based Strategy**를 고릅니다. 각각은 해당 원본 전략의 하위 클래스이므로
폴더·잡·에이전트 권한 속성과 역할 할당이 원본 전략에서와 똑같이 설정 가능하고 유효합니다. 이미
원본 전략을 쓰고 있다면 먼저 변경 통제를 켜십시오. **Manage Jenkins**에 관리 모니터가 나타나고,
그 **Install the Batch Control variant** 버튼이 기존 설정을 모든 항목을 유지한 채 해당 변형으로
한 번에 옮겨 줍니다. Jenkins 내장 전역 "Matrix-based security"를 쓰고 있다면, 권한 창에는
*프로젝트* 매트릭스 변형이 필요하고, 변환하는 순간 잡·폴더·에이전트에 이미 저장된 모든 항목별
권한 속성이 유효해진다는 점에 주의하십시오. 먼저 검토하십시오. 선택된 변형은 승인된 창이 열려
있는 동안 그 창의 행위(`Item/Create`, `Item/Configure`, `Item/Delete` 중 승인된 것)를 그 창의
범위에만 더해 주고 나머지 판단은 손대지 않고 넘기므로, 활성 창이 없을 때는 원본 전략과 똑같이
동작합니다.
권한 판정은 Jenkins 자신이 하는 방식대로 `impliedBy` 사슬을 따라가며 이루어지므로, 창은 승인된
행위가 함의하는 권한들까지 함께 답합니다. 이 프로젝트가 기준으로 삼는 플러그인 구성에서
`CONFIGURE` 창은 `Item/ExtendedRead`, `Credentials/UseItem`, `Run/Replay`도 함께 부여합니다.
창을 승인하기 전에 알아 둘 만한 사실입니다([제약](#제약) 절). 변경 통제가 켜져 있는데 두 변형
중 어느 것도 선택되지 않았으면(예를 들어 Security 페이지에서 원본 전략을 고른 경우) 관리 모니터가
경고하고 한 번의 클릭으로 다시 설치하게 해 줍니다. 최소 버전인 role-strategy 927 이상에서는 **Manage Roles**나
새로 설계된 **Assign Roles**를 저장해도 Batch Control 변형이 유지됩니다. 실행 통제와 기록에는 이 전략이 필요하지 않습니다. 권한 창이 권한을
부여하려면 변형이 선택되어 있고 **동시에** 변경 통제가 켜져 있어야 합니다.

### 3. 권한을 할당한다

| 권한 | 허용하는 것 |
|---|---|
| `BatchControl/Request` | 승인 보호된 잡에 대한 실행 요청 생성(그 잡의 `Item/Read` 필요, `Item/Build`는 필요 없음) |
| `BatchControl/Approve` | 실행 요청과 권한 창 요청의 승인 또는 반려 |
| `BatchControl/RequestGrant` | 임시 변경 권한 요청 |
| `BatchControl/ViewHistory` | 이력 화면, 대시보드, CSV 내보내기 조회 |
| `BatchControl/Manage` | **Batch Control → Configuration**에서 전역 설정 관리, 권한 창 회수 |

`Manage`는 `Overall/Administer`가 함의하고 나머지 넷을 함의하므로, 관리자는 모든 검사를
통과합니다. 요청자에게는 보통 `Overall/Read`, `Item/Read`, `Request`,
`RequestGrant`를 주고 `Item/Configure`는 의도적으로 주지 않습니다. `CONFIGURE` 권한 창이
바로 그것을 대신하기 때문입니다. 결재자에게는 보통 `Approve`와 `ViewHistory`를 주고
`Request`는 주지 않습니다. `ViewHistory`는 이름보다 넓다는 점에 주의하십시오.
[제약](#제약) 절을 보십시오.

실행을 요청하는 데는 `BatchControl/Request`와 그 잡의 `Item/Read`만 필요하고 `Item/Build`는
필요 없습니다. 실행 통제가 켜져 있는 동안 승인이 필요한 잡에서는 직접 실행 경로가 모두 거부되고
승인된 실행은 플러그인이 큐에 넣으므로, `Item/Build`는 그 자체로 아무것도 허용하지 않으며 누가
요청할 수 있는지는 `Request`가 정합니다. **승인이 필요한 잡에는 `Build` 대신 `Request`를
부여하십시오.** 승인이 필요 없는 잡과, 실행 통제가 꺼진 인스턴스에서는 Jenkins 자신의 Build
의미가 그대로 적용되므로 `Item/Build`를 유지합니다. 스스로는 잡을 시작할 수 없는 사람의 실행도
승인으로 인가될 수 있으므로, 요청자가 그 잡의 `Item/Build`를 갖고 있지 않으면 요청 상세 화면과
결재자 알림에 그 사실이 표시됩니다. Build 보유자만 요청할 수 있게 하려면 `Request`를 그들에게만
할당하십시오. `Item/Build`가 없는 요청자가 스크립트로 잡의 `/build` 엔드포인트에 POST하면, 코어가
Batch Control의 게이트보다 먼저 Build를 검사하므로 Jenkins 자신의 403("missing the Job/Build
permission")을 받습니다. 이런 사용자는 build 엔드포인트가 아니라 **Request Run**이나 서비스 API로
실행을 요청합니다.

### 4. 잡을 설정한다

잡 설정에 **Batch Control** 블록이 생기고, 항목마다 인라인 도움말이 붙습니다. `Require
approval to run`, 위에서 설명한 두 트리거 옵션과 그에 딸린 `Allowed upstream jobs` 목록,
그리고 전역 결재자 목록을 좁히는 선택적 잡 수준 결재자 목록입니다. 실행 통제가 켜져 있는
동안에는 **새로 만들어지는 모든 잡이 잠긴 상태로 시작합니다.** `Require approval to run`,
`Block cron (timer) triggers`, `Block upstream triggers` 가 모두 켜지고 상위 잡 허용 목록은 비어
있습니다. 누가 만들었는지, 어떻게 만들었는지는 상관없습니다. 즉 **잡을 만드는 행위가 그 잡을
가동시키지 않습니다.** 가동하려면 잡 설정에서 해당 스위치를 꺼야 하고, 그 변경 자체가 기록되며
변경 통제가 켜져 있다면 권한 창도 필요합니다.

생성 요청에 실어 보낸 값은 이 잠금을 넘지 못합니다. `config.xml` POST, CLI `create-job`, Job DSL
시드, 잡 복사로 `approvalRequired=false` 나 `blockTimer=false` 나 상위 잡 허용 목록을 지정해도
덮어써집니다. 넘어오는 것은 잡 수준 결재자 목록뿐이고, 그것은 결재 가능한 사람을 좁히기만 할 수
있기 때문입니다. 스크립트로 잡을 생성하는 인스턴스라면 첫 실행에서 조용히 걸리므로, 실행 통제를
켜기 전에 [자동화 관련 주의 사항](docs/LIMITATIONS.md#automation-and-generated-jobs)을
읽으십시오.

동작하는 참조 설정이 [`e2e/`](e2e/)에 있습니다. Dockerfile, 플러그인 목록, 보안 부트스트랩,
전역 설정이 들어 있습니다. 배포 템플릿이 아니라 종단 간 스위트를 돌리기 위한 것이지만, 초기화
스크립트가 위 네 단계를 하나씩 실제로 보여 줍니다.

## 화면

모든 것은 `/batch-control/`의 **Batch Control** 페이지에 있습니다. Jenkins 2.568에서는 그 항목이
대시보드의 왼쪽 사이드바에 없습니다. 페이지 머리글의 **☰**(More actions) 메뉴를 열고
**Batch Control**을 고르십시오. 그 페이지 안에서는 절들이 페이지 자체의 사이드바에 나열되고,
절마다 권한으로 제한되므로 사용자는 자기가 할 수 있는 것만 봅니다. Batch Control 권한이 하나도
없는 사용자에게는 항목이 없고 그 URL은 404를 돌려줍니다.

**Run Requests**에는 각 요청의 저장된 파라미터, 사유, 요청자, 결재자, 상태, 결정 이력이 있고,
결재자가 여기서 결정합니다. 보호된 잡의 사이드바에는 **Request Run** 이 있어 그 잡의 파라미터가
담긴 폼을 열어 주고, Jenkins 자신의 빌드 항목은 **Direct Build (needs approval)** 로 라벨이
바뀌어 둘을 혼동할 수 없게 되어 있습니다. 코어 항목을 따라가면 승인 없이 큐에 닿으므로 거부됩니다.
변경 통제가 켜져 있고 그 잡에 대한 `Item/Configure` 를 이미 갖고 있지 않은 사용자에게는 옆에
**Request Change Permission** 이 함께 보이고, 그 잡이 채워진 권한 창 요청 폼을 엽니다.
**Grants**에는 대기 중인 권한 창 요청, 활성 창의 남은 시간, 만료된 창들의 이력, 새 창을 요청하는
링크가 있습니다. **Run
Dashboard**는 인스턴스 전체에서 가장 최근의 빌드 50개를 원인(`USER`, `TIMER`, `UPSTREAM`,
`APPROVED_REQUEST`, `SCM`, `OTHER`), 사용자, 파라미터, 결과, 소요 시간과 함께 보여 주고,
승인된 실행은 그것을 인가한 요청으로 되돌아가는 링크를 갖습니다. 그보다 오래된 빌드는
**History**로 가는 링크를 따라가 보십시오. **Incidents**는 자동으로
열린 실패들을 모아 두며, 각각에 콘솔 마지막 100줄이 붙고 확인·해결·코멘트와 재실행 요청을 할
수 있습니다. 재실행 요청은 실패한 빌드의 원래 파라미터를 패스워드와 파일 값까지 그대로
싣습니다. 파라미터는 고정되어 있어 고칠 수 없습니다. 재실행 양식에는 결재자 체크박스만 있고,
사유는 인시던트에서 자동으로 만들어지므로 입력할 수 없습니다. 빌드에서 더는 복구할 수 없는
값이 있으면(빌드가 끝날 때 지우는 stash 파일, 또는 삭제된 빌드(다시 만든 잡의 같은 번호 빌드 포함)) 거기서 요청을 만들지 않고, 나머지
값을 채운 그 잡의 Request Run 양식이 열립니다. 파일과 패스워드는 다시 넣어야 하고, 그 양식에서
제출한 요청은 서버가 오류 건 참조를 다시 검증한 뒤에만(오류 건이 존재하고, 그 잡의 것이며,
제출자가 `BatchControl/ViewHistory`를 가짐) 오류 건에 연결됩니다. 재실행 요청을 제출하려면 다른 실행 요청과 마찬가지로
`BatchControl/Request`와 그 잡의 `Item/Read`가 필요하고(`Item/Build`는 필요 없음), Incidents
화면 자체에는 `BatchControl/ViewHistory`가 필요하므로 세 가지가 모두 있어야 합니다. 상태는 `OPEN`에서 `ACKNOWLEDGED`, `RESOLVED`로 한
방향으로만 흐르고, 전이마다 사용자와 시각과 코멘트가 남습니다. **History**는 실행, 오류 건,
변경 기록, 요청을 기간·잡·사용자·결과·상태로 걸러 보여 주고, 각각을 CSV로 내보내며(공백을 제외한
첫 글자가 `=`, `+`, `-`, `@`인 셀은 스프레드시트가 수식으로 계산하지 않도록 앞에 따옴표를
붙입니다), 월간
집계를 냅니다. **Change Records**는 생성·설정·삭제·이름 변경·이동의 궤적입니다. 어떤 경로로
들어온 변경이든(UI, REST, CLI, Job DSL) 기록되며, unified diff와 그 변경이 어느 권한 창 아래에서
이루어졌는지가, 창이 없었다면 없었다는 표시가 함께 남습니다.

기록은 빌드와 분리된 `$JENKINS_HOME/batch-control/`에 있어서 빌드 로테이션보다 오래 남습니다.
추가 전용입니다. 수정이나 삭제 API는 없고 보존 기간 만료만 있습니다.

## 제약

아래는 판단을 바꿀 수 있는 것들만 골랐습니다. 전체 목록은
[`docs/LIMITATIONS.md`](docs/LIMITATIONS.md)에 있습니다(영어).

**관리자는 막지 않고 기록합니다.** 관리자를 막는 것은 범위 밖입니다. `Overall/Administer`가
모든 Batch Control 권한을 함의하므로, 관리자는 자기 요청을 스스로 결재하고(*Allow administrators
to approve their own requests*가 꺼져 있지 않다면), 두 통제를 끄고, 잡의 스위치를 풀고, 권한 전략을
바꿀 수 있으며, 이 모두가 기록됩니다. 다만 게이트 자체는 관리자에게도 적용됩니다. 승인이 필요한
잡에서는 관리자의 Direct Build, REST build, Replay도 다른 사람과 똑같이 거부되므로 관리자도 요청을
거쳐 실행하고, 활성화되지 않은 잡의 무인 실행은 누가 시작했든 활성화 게이트가 막습니다.

**변경 통제를 끄면 진행 중이던 작업이 끊깁니다.** 스위치를 끄는 순간 열려 있던 권한 창이 모두
회수되므로, 변경 작업을 하던 중이던 사람은 마무리할 권한을 잃고 통제를 다시 켠 뒤에 새로 요청해야
합니다. 회수는 창마다 기록에 남습니다. 꺼져 있던 기간을 넘어 이어지는 것은 없습니다. 그 동안에는
권한 창을 요청하거나 승인할 수 없고, 감사 이력에서 없어지는 것도 없습니다.

**설정 변경이 거부될 때 뜨는 화면은 여전히 Jenkins 의 순정 403 입니다.** 활성 창 없이 잡 설정을
열거나 저장하면 "missing the Job/Configure permission" 페이지가 뜹니다. 플러그인이 이 화면을
의도적으로 가로채지 않으므로, 그 페이지는 권한 창에 대해 아무 말도 하지 않고 창을 한 번도 받지
않은 사용자와 방금 만료된 사용자가 똑같은 화면을 봅니다. 대신 플러그인이 하는 일은 잡 사이드바에
**Request Change Permission** 을 놓아 403 을 본 뒤가 아니라 그 전에 길을 보여 주는 것이고, 남은
시간과 만료 이력과 재요청 링크는 Grants 화면에 있습니다. 삭제는 예외로, 플러그인 자신의 거부
메시지가 요청해야 할 권한을 알려 줍니다.

**`CONFIGURE` 창은 Jenkins가 `Item/Configure`에서 함의하는 것을 모두 부여합니다.** 이 프로젝트가
기준으로 삼는 플러그인 구성에서는 `Item/ExtendedRead`(`config.xml` 읽기),
`Credentials/UseItem`, `Run/Replay`가 여기에 해당하고, 어떤 플러그인이든 자기 권한을
`Item/Configure`가 함의한다고 선언할 수 있으므로 목록은 더 늘어날 수 있습니다. 매트릭스에
`Item/Configure`를 상시로 주었을 때 부여되는 것과 같은 집합이지만, 출처가 다릅니다. 이쪽은
`CONFIGURE`라는 단어만 본 비관리자가 승인한 창입니다. 특히 알아 둘 것은 `Run/Replay`입니다.
승인이 필요한 잡의 Replay는 실행 통제가 그대로 거부하므로 그 잡에서 실행 게이트를 우회하는
길이 되지는 않지만, 실행 통제가 걸려 있지 않은 잡에서는 창을 가진 사람이 Pipeline 스크립트를
고쳐서 다시 실행할 수 있습니다. 또한 Jenkins는 잡을 구성할 수 있는 사람에게 이름 변경도
허용하므로, `CONFIGURE` 창을 가진 사람은 잡의 이름을 그 폴더 안의 비어 있는 어떤 이름으로든
바꿀 수 있고, 이름 변경은 그 창과 함께 기록됩니다. 이름 제한이 있는 `CREATE` 창에서는 그 창으로
만든 것의 이름 변경이 제한에 맞는 이름으로만 허용됩니다.

**권한 창은 Batch Control의 두 권한 전략 변형에서만 동작합니다.** **Batch Control: Project-based
Matrix Authorization Strategy**와 **Batch Control: Role-Based Strategy**입니다. 다른 전략을
고르면 실행 통제와 기록만 동작하고, 관리 모니터가 그렇다고 알립니다. role-strategy는
**Assign Roles** 화면이 새로 설계된 927 이상이어야 하며, 927에서는 **Manage Roles**와
**Assign Roles** 저장이 변형을 유지합니다. 변형의 디스크립터는 role-strategy의 디스크립터
메서드를 복사하지 않고 그대로 호출하므로 검증이 원본 전략과 똑같이 동작하고, 회귀 테스트가 계속
이 연동을 지켜 연동을 깨는 이후 role-strategy 릴리스는 Batch Control 빌드를 실패시킵니다.

**전역 매트릭스 전략에서 변환하면 항목별 권한이 켜집니다.** Jenkins 내장 전역 "Matrix-based
security"는 잡·폴더·에이전트에 저장된 권한 속성을 무시합니다. **Batch Control: Project-based
Matrix Authorization Strategy**로 변환하면 오래된 것을 포함해 그 속성이 모두 유효해지고, 항목의
`Item/Configure`를 가진 사람은 그 항목의 권한을 고칠 수 있게 됩니다. 변환은 Manage Jenkins의 관리
모니터에 있는 **Install the Batch Control variant** 버튼으로만 하는 명시적인 단계이며, 모니터도
같은 내용을 알립니다. 먼저 항목별 속성을 검토하십시오.

**큐 진입에서 거부된 보호 잡은 자신을 호출한 잡을 실패시킵니다.** Pipeline `build` 스텝이
게이트에 걸리면 상위 잡이 `FAILURE`로 끝납니다. `wait: false`여도 그렇습니다. 이것은 Jenkins의
동작이고 여기서 고른 것이 아닙니다.

**실행 통제를 켜기 전에 새 잡 잠금을 감안하십시오. 이것은 조용히 실패합니다.** 실행 통제가 켜진
동안 만들어지는 잡은 승인 필요와 두 트리거 차단이 모두 켜진 채로 시작하고, 생성 요청에 실어 보낸
값은 덮어써집니다. 그래서 `blockTimer: false` 를 고정한 Job DSL 이나 JCasC 정의는 새로 생성할 때
**무시된 것처럼 보입니다.** 자동 생성된 야간 잡은 첫날 밤에 돌지 않는데, 무인 실행의 거부는 설계상
조용하므로 그 모습이 cron 이 아예 발동하지 않은 것과 똑같습니다. 둘을 구분하는 첫 번째 단서는 잡의
설정 화면입니다. 정의에는 없는 `Block cron (timer) triggers` 가 켜져 있으면 잠금이 원인입니다.
컨트롤러 로그에도 "blocked timer-triggered run" 줄이 작업마다 한 시간에 최대 한 번 남습니다. 이 저장소 자체의
e2e 환경에 있던 시드 잡들이 승인 기본값이 들어온 첫날 빌드를 멈췄습니다.

**비밀값은 탐지가 닿는 범위까지만 지켜집니다.** 저장되는 오류 건 로그 끝부분은 그 빌드 자신의
민감 파라미터 값과 Jenkins `Secret` 평문만 마스킹합니다. 그 밖의 것, 스크립트가 출력한 토큰,
스택 트레이스, 서드파티 도구의 출력은 그대로 저장되고 그대로 표시됩니다. 실행 요청의
파라미터는 사정이 다릅니다. 요청은 제출된 값을 타입과 함께 보관하므로, 승인된 실행은 원래
비밀값과 원래 파일을 그대로 받습니다. 코어 `file`과 file-parameters 플러그인의 `stashedFile`,
`base64File`을 포함해 모든 파라미터 타입이 해당됩니다. 비밀값은 Jenkins의 암호화된 형태로만
저장되고 어디서나 `********`로 표시되며, 파일은 `[file] <원래 파일 이름>`으로만 표시됩니다.
오류 건 재실행은 실패한 빌드에 아직 남아 있는 값만 다시 쓸 수 있습니다. 파일이나 다른 값이
사라졌으면 남은 값을 채운 Request Run 양식이 열리고, 파일과 비밀값은 다시 넣어야 합니다. 실행
요청 제출은 100 MB로 제한되지만 인스턴스 전체의 업로드 한도는 Jenkins 자체의 설정입니다.
[Limitations](docs/LIMITATIONS.md#records-and-screens) 31, 32번을 보십시오.

**`BatchControl/ViewHistory`는 인스턴스 전체에 대한 감사 읽기 권한입니다.** 이력 화면,
대시보드, CSV 내보내기는 모든 요청과 실행을 보유자 누구에게나 보여 줍니다. 잡 이름, 파라미터
값, 사유, 결정 코멘트가 모두 포함되고 `Item/Read` 검사는 없습니다. 오류 건의 확인과 해결도 이
권한으로 인가되므로, 읽기 전용 감사자 계정도 오류 건을 닫을 수 있습니다.

설계상 범위 밖인 것들도 있습니다. `Overall/Administer`에 의한 우회, 디스크에서 직접 고친 것의
탐지, 배치 애플리케이션 안쪽의 스텝 재시작이나 재개, Git에 있는 Pipeline 스크립트 변경의
통제입니다.

## 다른 방식과의 비교

Pipeline `input` 스텝은 이미 시작된 실행 안쪽의 한 지점을 막고, Pipeline 잡에서만 쓸 수 있고,
기록을 빌드 안에 남깁니다. Batch Control은 실행의 시작을 막고, 잡 타입을 가리지 않으며, 기록을
빌드 보존과 무관하게 보관합니다. Audit Trail, AuditFlow, Job Configuration History는 무슨 일이
있었는지를 잘 기록합니다. Job Configuration History는 설정 diff를 누가 바꿨는지와 함께 남기고,
AuditFlow는 검색 가능한 저장소와 내보내기를 더합니다. 그중 어느 것도 기록 앞단에 통제 장치를 두지
않습니다. 요청, 지정된 결재자, 결정, 스스로 끝나는 권한이 그것입니다. 그리고 matrix나 역할 기반
권한은 권한을 "누구인가"로 정하고 "얼마 동안인가"로는 정하지 않는데, Batch Control은 그렇게 설정한
전략을 감싸서 승인된 창 안에서만 존재하는 권한을 더합니다.

## 기여

이슈와 풀 리퀘스트를 환영하며, 안내서는 [`CONTRIBUTING.md`](CONTRIBUTING.md)입니다. 관례 몇
가지가 통상적이지 않아서 첫 변경 전에 읽어 볼 만합니다. 그보다 먼저 알아야 할 것이 두 가지
있습니다. `docs/SPEC.md`가 기능 계약이므로 코드와 스펙이 어긋나면 코드가 틀린 것이고, 확정된
설계 결정의 근거는 `docs/DECISIONS.md`에 있습니다. `docs/ARCHITECTURE.md`는 확장 지점, 패키지
구조, 디스크 저장 형식을 설명합니다.

```sh
mvn clean verify   # 컴파일, 전체 테스트, SpotBugs. 실패 0, 버그 0으로 끝나야 합니다
```

## 보안 취약점 신고

GitHub 이슈는 **열지 마십시오.** Jenkins의
[**SECURITY** 프로젝트](https://issues.jenkins.io/secure/CreateIssueDetails!init.jspa?pid=10180&issuetype=10103)에
`specific-plugin` 컴포넌트로 비공개 신고하고, 요약에 플러그인 이름을 적으십시오. `jenkinsci`
조직에 호스팅되기 전까지는 자체 Jira 컴포넌트가 없기 때문입니다. 그렇게 만든 이슈는 신고자와
Jenkins 보안팀에게만 보입니다. 트래커를 쓸 수 없으면 `jenkinsci-cert@googlegroups.com`으로
메일을 보내면 보안팀이 대신 등록해 줍니다. 전체 정책은
<https://www.jenkins.io/security/reporting/>에 있습니다.
