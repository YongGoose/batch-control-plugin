## MEDIUM
- [S-18-01] `ops/ConfigureWithoutGrantMonitor.java:238` (with `:243`, `:336-387`): the standing-holder monitor no longer reports standing change permissions that come from a group, when the strategy's group entries cannot be read.
  - Problem: DEF-29 changed the user probe to `principalOnly(auth)`, which has no authorities. Group-derived permissions are now reported only through `strategyGroupSids(strategy)`, and that method finds groups only by calling `getAllPermissionEntries()` reflectively. role-strategy has no such method: 898.vc050ed2424ca_ offers only `getGrantedRolesEntries`, `getSidEntries` and `getSIDs`. So with the first-party `BatchControlRoleBasedAuthorizationStrategy` the group list is always empty. Take a global role holding Job/Configure that is assigned to a realm group, such as an LDAP group. Before this change, every known member was listed as a user. Now nobody is listed, and the monitor can even stay inactive. Only `authenticated` is still covered, by the baseline row. A security warning that SPEC item 8 requires now misses a common real setup. This is not a bypass (the monitor is not an enforcement point), which is why it is MEDIUM and not HIGH.
  - Basis: SPEC item 8 (warn when a non-admin holds Item/Create/Configure/Delete directly from the strategy). TEST-MATRIX note 141 says a member is "covered by the group entry", but that holds only when a group entry exists.
  - Fix direction: collect the group probes from the union of (a) the strategy's own entries, when readable, and (b) the authorities that `loadUserByUsername2` returns for every candidate user, which `authenticate()` already loads. Skip `authenticated` and the role/authority prefix conventions of the realm. The rule "reported once, on the group" then holds for every strategy. If no group can be enumerated at all, fall back to the full-authority user probe minus the baseline. That is still one line per member, but nothing goes missing.
  - Regression test: Given change control on, `BatchControlRoleBasedAuthorizationStrategy`, a global role `editors` holding Overall/Read and Job/Configure assigned to group `devs`, and a mock realm where user `u18` is in `devs` and has no role of its own; When an admin GETs `manage/`; Then the monitor is shown and one entry names `devs` (kind "Group") with Job/Configure. (If the fallback is chosen, it names `u18` instead.) It never shows an empty table.

## LOW
- [S-18-02] `listener/ConfigNormalizer.java:97-106, 183-185`: `<configVersion>` is dropped at any depth together with its whole subtree, whatever it contains.
  - Problem: this is a gap in the audit trail. A Configure holder, possibly working under a JIT grant, can POST a `config.xml` that wraps arbitrary content in `<configVersion>…</configVersion>` inside any element. It then never shows in the CONFIGURE diff. If that is the only difference, no record is written at all (`ConfigSnapshotListener.java`, the "normalized equal" branch). Today the hidden content is inert: XStream ignores unknown fields, and the only known `configVersion` field (throttle-concurrents) is a `Long` that only drives its `readResolve` migration. That is why this is LOW. A future plugin with a meaningful field of that name would turn it into an audit bypass that the plugin itself caused.
  - Basis: SPEC item 9 (every configuration change is recorded with its diff); checklist B, "user input … validated".
  - Fix direction: drop only a leaf `configVersion` element whose text is an integer (`\s*-?\d+\s*`), with no child elements, comments or CDATA. Otherwise copy it verbatim. If possible, also limit the rule to known owners, such as a parent element whose name ends with `ThrottleJobProperty`.
  - Regression test: Given a job with a baseline snapshot; When `config.xml` is POSTed with `<configVersion><foo>bar</foo></configVersion>` (and, in a second case, `<configVersion>abc</configVersion>`) added under a builder; Then a CONFIGURE record exists whose diff contains the added lines. And Given an unchanged job whose only difference is a numeric `configVersion` bump, Then no record is written (T-09-21 stays green).

- [S-18-03] `queue/ApprovalQueueDecisionHandler.java:187-209` (the throw is at `:204-206`): the remote-cause branch runs before the retry distinction, and it throws `RemoteRunRefusal` for any submission that carries a `RemoteCause` inside any HTTP request.
  - Problem: (a) On a manual Retry, naginator 1.556 (`NaginatorRetryAction.getCauseAction`) copies every cause of the retried build except `UserIdCause`/`NaginatorCause`, and adds a fresh `UserIdCause`. A user who clicks Retry on a build that was started by a build token (for example before `approvalRequired` was switched on) therefore meets step 3 first. The browser user gets a `text/plain` 403 page instead of the `ApprovalRequiredFailure` page. The attempt is recorded as `REMOTE_RUN_BLOCKED` ("Blocked a remote run submission … a build token does not substitute") and not as `TRIGGER_BLOCKED cause=RETRY` by that user. The account name is right; the type and kind are wrong. This is exactly what DEF-32/D-47 set out to record correctly. (b) The throw is not limited to the two token endpoints. Any other plugin that schedules with a `RemoteCause` on a request thread gets a `RuntimeException` where it used to get a quiet `false`. A loop over several jobs, for example, stops at the first one. The Queue lock is safe: core `Queue.schedule2` (`Queue.java:586-601`) releases it in `finally`. In both cases the run is still refused, so this is not a bypass.
  - Basis: SPEC item 6 (refusals are recorded, and history names who did what; SPEC section 6 usability); D-47; DEF-32.
  - Fix direction: evaluate `isAutomaticRetry(causes) && isUserClickedRetry()` before step 3 and send such submissions down the step-4 path. Throw `RemoteRunRefusal` only when the current request is a token build endpoint, that is when the request's ancestor object is the job being scheduled and the last URL token is `build`/`buildWithParameters`, or when the ancestor is build-token-root's `BuildRootAction` (matched by class name). Otherwise keep the quiet `false`.
  - Regression test: Given an approval-required freestyle job with naginator installed and a completed build whose causes include a `RemoteCause`; When a user with Item/Build requests `<build>/retry/`; Then the answer is the HTML approval-required page, a `TRIGGER_BLOCKED` record with `cause=RETRY` by that user exists, and no `REMOTE_RUN_BLOCKED` record was written.

## INFO
- [S-18-04] `queue/RemoteRunRefusal.java:33-40`, `ApprovalQueueDecisionHandler.java:512-515`: the 403 body names the job's full name, the request-form URL and the configured root URL. It is reached only by someone who already presented a valid token for that job, or who holds Item/Build:
  - core runs `BuildAuthorizationToken.checkPermission` before `schedule2`;
  - build-token-root `project()` answers 404 for an unknown job or a job without a token and 403 on a token mismatch, before scheduling (verified by disassembly);
  - the caller named the job themselves.
  The only new fact is that the job requires approval. No parameter, no `cause` text and no request data is echoed. The body is `text/plain;charset=UTF-8`, and job names cannot contain markup characters (`Jenkins.checkGoodName`). Acceptable; no change needed.
- [S-18-05] `ApprovalQueueDecisionHandler.java:410-421`: DEF-32 puts the account into the coalescing key only for refusals made by a person. Unattended refusals, including automatic retries, are still keyed per job and kind. Where builds run as a user (authorize-project), automatic retries under different identities within one hour merge into the first record's user. This does not let a person avoid attribution: the clicked path is keyed per user, and the user name always comes from `Jenkins.getAuthentication2()`, never from a cause. Consider adding the name to every key when it is not SYSTEM.
- [S-18-06] `action/RunApprovalNoticeActionFactory.java:29-30`: the action is attached to every Run even while run control is off. It renders nothing then (`isShown` needs run control on), but it adds an entry to every build's `api/json` `actions` array. That is a small visible change while the switch is off (CLAUDE.md). Fix direction: return `List.of()` when run control is off.

## Checked and found to be fine
- B1/B2 `do*` methods: the diff adds no web method (`grep "public .* do[A-Z]"` on the diff finds nothing). `RunApprovalNoticeAction` has `getUrlName() == null`, so Stapler cannot route to it. Existing methods are unchanged.
- B4 Jelly output: every new or changed view (`RunApprovalNoticeAction/summary.jelly`, `ConfigureWithoutGrantMonitor/message.jelly`, both refusal pages, `monthly.jelly`) has `escape-by-default='true'`. There is no `escapeXml="false"` and no `<j:out>`. Sids, display names and permission names go through escaping. `${it.job.url}` is core's encoded URL.
- B5 `ACL.SYSTEM2`: there is no new switch. The only new use is the identity comparison in `isUserClickedRetry()` (line 362), the same test as `isHumanSubmission`. The monitor probes use explicitly built `Authentication` objects with `ACL.hasPermission2(auth, p)`, and the thread identity is never changed.
- B6 Secrets: no new flow. The 403 body carries no parameter values. The `REMOTE_RUN_BLOCKED` detail keeps the existing `RemoteCause` short description, which is unchanged by this diff.
- B7 Paths / B10 XML parsing: no new file path. `ConfigNormalizer` is a scanner over the item's own stored file and never parses external XML. Its desync resistance was re-checked: for well-formed input, the normalizer's opaque spans (PI up to the first `>`, comment, CDATA) are never longer than the parser's, so they cannot hide a close tag. Its only gap is S-18-02.
- B8 CSV: no new columns. The new detail texts contain only the job name, the user id and constant text, and go through the existing export unchanged.
- B9 XStream: no new persisted model. `RemoteRunRefusal` is a `Failure` (an exception) and is never stored.
- B13 Delegating strategy: unchanged by this diff.
- Information disclosure (item 9): the build-page notice delegates to `JobActivationNoticeAction`. It is shown only with Item/Read and run control on, and a build page itself needs Item/Read. The form link needs BatchControl/Request plus Item/Build (D-38). A user who has only Item/Discover never reaches a build page. The monitor is an `AdministrativeMonitor` that does not override `getRequiredPermission()`, so only Overall/Administer sees it.
- Throwing from `QueueDecisionHandler` during an HTTP request: the audit record is written before the throw. The Queue lock is released by core's `finally`, and the response is generated by Stapler after the lock is released. The handlers skipped after ours do not matter for a refusal. The CLI (`CLICommand.getCurrent()`) and non-request threads keep their existing paths. The approval marker (step 1) is consumed before step 3, so its single-use guarantee is unchanged (item 10).
- DEF-32 and activation: an automatic retry now skips step 4 and reaches step 5. Step 5 refuses whenever the effective causes contain a `UserIdCause` or `ApprovedCause`. `NaginatorCause` is neither, so every submission step 4 used to refuse is still refused. Everything else goes through `activatedOrRefuse` (steps 6-8). A user-clicked Retry carries naginator's fresh `UserIdCause` (verified in `getCauseAction`) and is refused at step 4 under the user's own key. There is no activation bypass and no way for a user to avoid attribution.
- DEF-30 and the change record: a save is skipped only when the normalized forms are equal. Any other difference still produces the full masked diff. The residual risk is S-18-02.
- DEF-29 scan: the SYSTEM identity is excluded from the candidates. The scan runs in the rendering admin's thread without impersonation. Detection coverage is S-18-01.
- DEF-28 (`JobRequestAction.getDisplayName`): it only changes a label, based on the request URI/ancestor. It has no permission or state effect. Removing the "Back to" links drops no check (the job/item variables were only used by those links).
- B15 SpotBugs: unconfirmed. The instructed `mvn clean verify` was still running and `target/spotbugsXml.xml` did not exist yet at review time; the caller should check the gate log.
