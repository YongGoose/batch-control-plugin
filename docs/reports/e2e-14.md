## FAIL details

**DEF-08 (low): on the activation form, a new-job-page user sees two dead side-panel entries.**
Steps: as admin (or requester, reqonly, manager) with the new job page on (the default under `compose.prefix.yml`),
open `/jenkins/job/batch-pipeline/batch-control-activation/` (or `/job/batch-daily/batch-control-activation/`). Look
at the side panel and click "Permalinks".
Expected: the side panel shows only working tasks, as it does for a classic-page user, or no job side panel at all,
as on `/job/<job>/batch-control/` for a new-job-page user.
Actual (`sidepanel.jsonl`, `SP-true-job_batch-pipeline_batch-control-activation.png`): next to the working "Delete
Pipeline" confirmation link there is a **second "Delete Pipeline"** ("Delete Project" on freestyle jobs) and a
**"Permalinks"** entry. Both are `task-link task-link-no-confirm` with `href=""`. Clicking them does nothing: no
navigation, dialog or menu. With the new job page off, only the working entry is shown. These are core's
new-job-page actions, which have no URL and are rendered by the classic `l:task`. e2e-12's crawl recorded the same
NOTHING rows (`integration6/e2e/r12/out/crawl.jsonl`), but it was not reported then.
Owner: ui-dev, `src/main/resources/io/jenkins/plugins/batchcontrol/action/JobActivationForm/index.jelly` line 8
(`<st:include page="sidepanel.jelly" it="${it.item}"/>` unconditionally). `JobRequestAction/index.jelly` (line 15)
already branches on `NewJobPageUserExperimentalFlag` and renders no job side panel for new-page users. The activation
form could do the same.

## UX observations (for human judgement)

1. **fonly sees an Activations tab it cannot use.** Its empty state says "To file one, open the job: its Batch Control
   notice offers Request activation ...", but fonly (Read, Move, RequestGrant) cannot file activation requests. The
   tab may be correct by the section rule, but the sentence promises an action this user does not have.
2. **"Monthly aggregate as JSON" ignores the History filter.** It follows the `to` month, not `job`/`user`. The label says
   "Monthly aggregate", so this is consistent. Still, a user who filtered to `job=fast` may expect a filtered JSON next to
   the filtered CSVs.
3. **Overlapping windows: the change record names the first covering window.** With two FOLDER_ONLY windows of fonly on
   `ops` open at once, the CREATE/DELETE records carry the older window's id, not the one just approved. This is valid
   (the older window authorised the change), but an auditor following "the window I just approved" will not find it
   on the record.
4. e2e-12 UX 1-3 (Previous/Next vs Newer/Older, mixed 403/404 section refusals, Request again with blank approvers)
   are unchanged.
