## UX observations (for human judgement)

1. Two green buttons (S4c): "Direct Build (needs approval)" and "Request Run" look equally primary. For an approval-required job both lead to the same Request Run form (Direct Build only adds a parameters dialog first), and for a user without Request, Direct Build leads to a refusal. Suggestion: keep only Request Run as the green BUILD control, and either make Direct Build a non-build-colored secondary or move it to the overflow menu.
2. Move refusal text says "Request a permission window that covers both". A window has one scope, so a cross-folder move needs two windows (Delete on the item, Create on the destination) unless one folder contains both. Suggestion: "Request permission windows for Item/Delete on 'prod/x' and Item/Create on 'team'".
3. The folders Move page offers destinations where Create comes only from a window, even though the move will then be refused for lack of Delete. The user finds out only after submitting. This is acceptable, but a hint on the Move page would help.
4. The change records "Grant" column reads "no grant" for refusals where the user did hold a window on the destination (MV1b). Naming the window that was considered would help an auditor.
5. Turning change control off (MV6 arrangement) closed every active window, and they are listed as "Revoked by admin" at that moment. If this is the intended kill-switch behaviour, a reason such as "change control turned off" would be clearer than "Revoked by admin".
6. After the admin moved `prod/y`, `team/y` appeared in the monitor as "changed under a temporary permission window". This is the S-27-03 rule: another user's window covered `prod/y`. The monitor text suggests the item was changed under a window, which surprises the admin who made the change without one.
7. Confirm dialogs use the core default "Yes" / "Cancel". In "Cancel this run request?" the "Cancel" button is ambiguous. Suggest `okText` such as "Cancel request" / "Revoke" / "Revert" (as the Install dialog already does with "Install").
8. The /batch-control/ Overview for an admin with nothing pending is just "Use the tabs to open a screen". Counts per section could make it useful. With all permissions the eight tabs wrap onto two lines at 1280 px (`S5d-dark-requests`).
9. The pagination caption "Page 1 (6 requests)" sits directly above the next section heading ("Active Grants"), so it reads as belonging to that section. "1 requests" needs singular handling.
10. The configuration page breadcrumb is "Batch Control / Batch Control configuration" while the page is reached from Manage Jenkins. Some users may expect "Manage Jenkins" in the trail.
11. Under the new job page, the "Request Run" app-bar button is not marked as current on the Request Run sub-page.
12. Third-party: with the `rebuild` plugin installed, "Rebuild Last" has a null URL on a job without builds. On the new job page this makes core's "More actions" menu throw `TypeError: Cannot read properties of null (reading 'startsWith')` on every job without builds, so the Batch Control menu entries cannot be reached there. This is not ours, but it hides "Request Change Permission". Worth an upstream issue for rebuild, and a mention in LIMITATIONS if it persists.
13. Console error on approval-required parameterized jobs under the new job page: `<script src="/jenkins/static/<hash>/">` from the "Direct Build" menu event (`javascriptUrl` = the bare static root, `dialog-opener`) leads to "Refused to execute script ... MIME type text/html". The menu event appears to be core's parameters dialog event (no Batch Control code builds it). It was seen on `batch-daily` and `plain-param`, both Batch Control controlled, and not on non-parameterized jobs. Should be checked on an instance without the plugin before filing it upstream.
