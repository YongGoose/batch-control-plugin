## 1. Gap analysis

Method:

1. I took every "Acceptance:"/수용 기준 line of `docs/SPEC.md` (lines cited by number) and the user-visible behaviours in
   `docs/LIMITATIONS.md`.
2. I held them against the steps `e2e/ci/shard.py` runs. These are the crawls and their content checks, jobui, actions,
   misc, round3, targeted, def07, r16, the multibranch unit, r17, r18 and role. I did not count the earlier Node and r6-r13
   drivers or the `scripts/rest-*.sh` evidence scripts, because CI does not run them.
3. I also used the e2e-16..18 "NOT covered" lists and the coverage inventory.
4. A grep of the CI drivers found no assertion on MARKER_REUSE_BLOCKED, TRIGGER_BLOCKED, REMOTE_RUN_BLOCKED, the CLI,
   naginator, customize-build-now, build-token-root, lockable-resources, authorize-project, jobConfigHistory,
   selfApproved, a timer or upstream trigger, a cancel/reject rule, an approved-run expiry, a CSV formula or the guard's
   403 page. Most of the core run-control loop was e2e-checked only by Phase 5 era scripts outside CI.

- **A**: should be e2e. It needs a real browser, a real Jenkins (restart, cron, CLI, queue), another plugin, or
  UI/mail wording.
- **B**: fine as integration-only. The logic is plugin-internal, a race, a fault or a time/rate limit, and the
  JenkinsRule rows cover it.
- **C**: not automatable as a CI step.

## G-27 follow-up: role naming strategy with a CREATE window

Added after the run above: step `role-naming` (`e2e/r19/naming.py`, profile `casc/profile-role-naming-window.yaml`) in
the `role` unit, after `role-endpoints` and before the crawl under the role profile (unit weight 7.2 -> 7.7). Local run
`BC_UNITS=role e2e/ci/run.sh 1/1` (prefix `bcg27`, ports 18380/18325, hpi built from the branch): every step of the unit
PASS, `role-naming` 5 PASS lines, 0 FAIL; the crawl after it still runs under the restored `profile-role.yaml`.

role-strategy 927 grants Item/Create on every folder to a user who holds any project role with Create while
`RoleBasedProjectNamingStrategy` is installed, and the strategy admits a name only through such a role. So "a name both
admit" is always native for the creator, and the step checks the two halves:

- requester (project role Create on `nf/teamA-.*`) with an approved CREATE window on `nf`: on the New Item page `zz-ui`
  shows "'nf/zz-ui' does not match the job name convention pattern [nf/teamA-.*]"; `teamA-ui` is created through the
  page (lands on its configure page). REST: `teamA-1` 302 and created; `zz-1` 400 with the same message, no item. The
  window does not loosen the strategy. No GRANT_VIOLATION for the strategy's refusal (SPEC asks for none).
- g27 (no Create role; no Create on `nf` of its own, asserted): with an unrestricted window `teamA-w1` gets 400 "No
  Create Permissions!", no item. With the restriction `/teamA-r.*/`: `teamA-r1` 400 "No Create Permissions!", no item;
  `teamA-x` 400 "'teamA-x' is not allowed here: your permission window for 'nf' ...", no item, one GRANT_VIOLATION,
  shown to approver-1 on the Changes screen. Screenshots `R19-NAMING-*`.
- Afterwards the default naming strategy, change control and `profile-role.yaml` are restored.

Observation (not a plugin defect, for human judgement): for a role holder, a D-40 restriction limits nothing, because
the Create the user uses is role-strategy's own. With `/teamA-r.*/`, requester created `nf/teamA-x` (seen in the first
attempt of this step, not asserted). The restriction only limits what the window adds. That is SPEC-conform but may
surprise an approver who reads the restriction as a limit on the user.

## Plugin defects found

None. No new step failed on 70277a3. Two expectations from the coverage inventory turned out to be wrong; the plugin
behaves as the SPEC says:

1. A credentials parameter value is displayed as `********`, not as the id. `ParameterDisplay` masks every value whose
   `isSensitive()` is true, which matches SPEC 5. See UX 1.
2. An approved run that waits in the queue (no free executor) is not expired by `approvedRunTimeoutMinutes`. SPEC 7
   l.141 expires only a run that was *not* queued (`RunRequestService#expireOverdue` skips queued markers).
   `lifecycle.py` E therefore cancels the queue item the way an operator would, by disabling the job.

### O-1 (e2e fixture, owner e2e-tester; not fixed here, not a plugin defect)

`e2e/r14/seed.py` seeds `req_expired` ("Will expire in the queue") by approving with zero executors. By point 2 above,
that request never expires. It stays APPROVED in the queue and runs once the seed restores the executors, so the crawls
never render an approved-run EXPIRED request. The comment and the fixture should change: disable the job after the
approval, as `r19/lifecycle.py` E does. This is left for a separate change, because the brief was not to rewrite the
existing drivers.

## UX observations (for human judgement; nothing was changed)

1. **The credentials parameter is masked on the request page** (and in every text surface derived from the same map), so the approver cannot see which
   credential the run will use. The id is not a secret, but the value type reports itself sensitive.
   `R19-KIND-r19-cred-form`, request page.
2. **The Replay refusal page is the generic "Approval required ... This build was not started"** page. The
   Replay-specific sentence in the code ("a replay would run changed code without one") is not shown. The page still
   explains the cause and links the request form. `R19-GATE-R-02-replay-refused`.
3. **customize-build-now's relabelled entry disappears** on an approval-required job. Request Run takes its place, so a
   team that relabelled "Build Now" sees the plugin's wording instead. `R19-PLUG-C-01-cbn-job`.
4. **A naginator retry refusal is recorded under SYSTEM**, with "(repeats within an hour are merged into this ...)".
   This is correct per D-47, but the requester gets no notice: the failed approved run simply does not retry. The
   build page notice ("Rebuilding or retrying this build ... is refused") is the only hint.
5. **The cancel confirmation and the disabled-job decision form are clear.** The expiry reason names the minutes and
   that the queued run was cancelled. The rejection page shows the decider, the time and the comment together.
