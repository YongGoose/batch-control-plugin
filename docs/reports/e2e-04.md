## FAIL details

### FD-01 — Medium — "Revert to the plain strategy" is shown to a BatchControl/Manage holder, who then gets a bare Access Denied
- Steps: log in as `manager` (Overall/Read, Job/Read, BatchControl/Manage). Batch Control → Configuration. Click **Revert to the plain strategy** → Yes.
- Expected (SPEC 6 usability, SPEC 2 #31): a control is shown only to users who may use it; no bare Access Denied.
- Actual: the link is rendered for the manager. It posts to `/manage/administrativeMonitor/batch-control-strategy/revert`, which answers 403 "manager is missing the Overall/Administer permission" on the stock page. The strategy is unchanged, so this is correct but misleading.
- Screenshots: FD-revert-01-manager-sees-button, FD-revert-02-access-denied (also S1-04-manager-*).

### FD-02 — Medium — The configuration page says "Changes are recorded in the change history", but only the two switches are recorded
- Steps: as `manager`, change *Pending request timeout* 1 → 2 and save. Separately, replace the Approvers list and save. Open Change Records / History (Changes).
- Expected: the page's own sentence ("Changes are recorded in the change history") holds. At minimum the approver list, which decides who may authorise production runs and permissions, leaves an audit trace.
- Actual: no record at all. Only CONFIG_TOGGLE records exist, for the switches (SPEC 1 requires only those). The page text over-promises, and an approver-list change by a non-administrator leaves no trail. Changing the authorization strategy (revert/install) is not recorded either.
- Screenshots: FD-config-claim-01-text, S1-02-manager-saved, S1-01-toggle-records (the table has no other record).

### FD-03 — Medium — The Approvers field accepts an unknown user id without a word and replaces the whole list
- Steps: as `manager`, on `/batch-control-configuration/`, set Approvers to `no-such-user` and save.
- Expected: invalid input is refused with a message next to the field (SPEC 6 usability), or at least a warning that the id is unknown.
- Actual: no inline check and no message. The list is stored as `[no-such-user]`, which silently leaves the instance with no usable approver: every request form then offers only a non-existent id. It was restored by the tester right after.
- Screenshots: S1-03-invalid-approversText-inline (no validation message), S1-03-invalid-approversText-submit.

### FD-04 — Low — Cancel, EXPIRED and INVALIDATED end a request without telling anyone
- Steps: requester cancels a pending request (S2-05). An approved request on a disabled job expires (S2-09). Pending requests expire after 1 hour (S2-11). A pending request's job is renamed (S8-05).
- Expected (brief): the requester gets an email and a clear status for a rejection, an expiry and a cancel. The approver whose inbox held the request should learn that it is gone.
- Actual: the status on screen is clear (CANCELLED "Cancelled by requester", EXPIRED, INVALIDATED "Target job renamed or moved: 'fresh-fail' -> 'fresh-fail-renamed'"), but mailpit shows no message for any of the four (searched by request id at 10:30). Only "expires soon" (EXPIRING) exists for pending requests, sent before the expiry. Note that SPEC 13 lists no CANCELLED/EXPIRED/INVALIDATED event, so this is a spec gap to decide, not a deviation from SPEC.
- Evidence: mailpit listing in the S2/S8 logs; S2-05-cancelled, S8-05-invalidated.

### FD-05 — Low — An expired request never says why it expired
- Steps: (a) requester requests `fresh-token`. Admin disables the job. approver-1 approves. Wait 1 minute (approvedRunTimeoutMinutes=1). (b) Leave a run request pending for more than 1 hour (pendingTimeoutHours=1): `20260930-081053-30kg3q`, `20260930-083056-cuim56`.
- Expected: the EXPIRED status comes with the reason (approved but not queued within 1 minute; no decision within 1 hour). The INVALIDATED page does give its reason ("Why it was invalidated: Target job renamed or moved …").
- Actual: (a) the row "Why it expired" is present and blank. (b) there is no reason row at all, and "Decided" is blank. The controller log does give the reason (`expired (pending timeout)`), but the requester and the History screen do not.
- Screenshots: FD-expired-01-empty-reason, S2-09-approved-not-run-expired, S2-11-20260930-081053-30kg3q-pending-expired, S2-11-20260930-083056-cuim56-pending-expired.

### FD-06 — Low — Approving on a disabled job says "the run starts shortly"
- Steps: as FD-05, look at the page right after approval.
- Expected: the page says the job is disabled and the approval will expire unless it is enabled within the timeout.
- Actual: "This request is approved and the run starts shortly. Reload this page to see the status change to EXECUTED". It never runs, and the request expires a minute later.
- Screenshot: S8-06-approve-disabled-job.

### FD-07 — Low — After a HOLD, the first refusal is recorded up to an hour later, because it is merged into a record written before the activation
- Steps: `fresh-cron` (every minute) is blocked at 08:08 (record written), ACTIVATED at 08:14 (ran 08:15 and 08:16), HELD at 08:16:52.
- Expected: the history shows that the cron was refused after the hold.
- Actual (re-checked at 10:40): the refusals from 08:17 onwards were merged into the 08:08 record, which is dated before the activation. The next record of its own appeared only when the hour window rolled over (the first cron after the host woke, 09:19:33; then 10:20:19). For about an hour the trail read TRIGGER_BLOCKED 08:08 → ACTIVATED 08:14 → HELD 08:16 and nothing after, so it did not show that the hold stopped anything. The per-job/cause hour window ignores the activation state changing in between. A controller restart also starts a new window: two records 6 minutes apart at 07:46 and 07:52. This is related to D-51, but D-51 covers only person-initiated re-runs, so it is not pending part 4.
- Evidence: `history/?kind=changes&job=fresh-cron` (S5-hist-03-changes-fresh-cron, taken at 08:2x), builds API at 10:40 (`#1`, `#2` only).

### FD-08 — Medium — The grant request form sits about 7,000 px below an unpaginated history, and neither the sidebar link nor a validation error brings the user to it
- Steps: requester, job page → **Request Change Permission**. Separately, submit the form with an error.
- Expected: README says it "opens the window request form with that job filled in". The user should see the form, or the error.
- Actual: the page opens at the top of *Grant Requests* (every request the user can see, 45+ rows here), then *Active Grants* and *Ended Grants*. The prefilled form starts at y = 7,018 px on a 900 px viewport. After an invalid submit the page again opens at scrollY = 0 while the error banner is at y = 7,009, so a user sees an apparently unchanged list and does not know that nothing was submitted. The validation text itself is good. The list grows without bound (no paging on *Grant Requests*).
- Screenshots: FD-grants-01-landing-viewport (what the user sees), S4-inv-no-action (the error, far down).

### FD-09 — Low — Runs started by an approved request show no user on the Dashboard, History and runs.csv

- Expected: "shows what was done and who did it" (brief); SPEC 10 lists a user column.
- Actual: for every `APPROVED_REQUEST` run the User cell is empty, and only the request id is shown. - Screenshots: FD-user-01-dashboard-empty-user, S5-dash-01-approved-row.

### FD-10 — Medium — The incident "Request Rerun" guidance sends users to a page the typical requester cannot open
- Steps: approver-1 or auditor opens an incident. requester (the README's typical requester: Overall/Read, Item/Read, Item/Build, Request, RequestGrant) opens the same incident URL.
- Expected: a Request+Build holder can request the rerun, as the page says.
- Actual: the page tells approvers "It is made by a user with the Batch Control/Request permission and Job/Build on the job; ask one of them … to request it from this page". - Screenshots: FD-rerun-01-guidance, FD-rerun-02-requester-403, S5-inc-05-rerun-form.

- Expected: a message next to the date fields (SPEC 6 usability).

- Screenshot: S5-hist-04-bad-dates.

### FD-12 — Medium — "Direct Build (needs approval)" on a job without parameters ends in a generic toast
- Steps: requester (or nobc) opens `fresh-token` (approval required, no parameters) and clicks **Direct Build (needs approval)**.
- Expected (README "A person refused at Build Now … gets an 'approval required' page"; SPEC 6 "조용한 실패 금지"; brief: a generic toast is a FAIL).
- Actual: Jenkins' own Build Now script posts in the background and shows a red toast: "Failed to schedule build. Reload the page and try again." That wording also suggests a retry. Nothing is queued. The "approval required" page appears only on a parameterised job, because there the link opens the parameters page first. On the same job, REST `POST /build` returns the proper "Approval required" page. None of these manual refusals (UI Direct Build, REST build/buildWithParameters, CLI) writes a change record: History → Changes for `fresh-daily` and `fresh-token` contains no TRIGGER_BLOCKED from them, only the token attempt's REMOTE_RUN_BLOCKED. README promises a record only for refusals that have no screen, but the toast case is effectively one of them.
- Screenshots: S6-01-requester-fresh-token-after-direct-build, S6-01-nobc-fresh-token-after-direct-build, S6-01-requester-fresh-token-direct-build-link.

### FD-13 — Low (needs human judgement) — "Direct Build (needs approval)" is shown to every Item/Build holder, including administrators, but it can never succeed
