## Summary: BLOCKER 3 / HIGH 3 / MEDIUM 2 / LOW 4 / INFO 4

The fix closes the reported DEF-38 path: a Pipeline `properties` step that writes an entry naming the grant holder, or `authenticated`, is reverted. But D-58 promises that grant holders' entries are guarded "whoever saves them", and that promise is not yet kept. Three independent gaps let a CONFIGURE window holder keep a permanent entry for themself. Each needs only what the window already gives, so all three are BLOCKER. Three more gaps depend on the instance's configuration and are HIGH.

## BLOCKER

- **[S-27-01] `GuardedPrincipals.java:71-77`, `GrantViolationGuard.java:314-324`: the automatic `anonymous` sid is not guarded.** Core's `SidACL._hasPermission` (l.90-97) checks `ACL.AUTOMATIC_SIDS = {EVERYONE, ANONYMOUS}` for every caller. `ANONYMOUS` is a `PrincipalSid("anonymous")`, and matrix-auth's `AuthorizationContainer#hasPermission(sid, p, principal=true)` matches it against `USER:anonymous` and `EITHER:anonymous`. So an entry for `anonymous` grants the permission to every user, logged in or not, the holder included. Only `authenticated` and the realm groups are added to the guarded set, so such an entry is kept. This is the same class as the `authenticated` entry that T-02-53 covers. Basis: B (privilege escalation; the guard is the fix for DEF-38). Fix direction: whenever the guarded set is not empty, always count `anonymous` as guarded, for USER, GROUP and EITHER. Test: *Given* bob holds a CONFIGURE window on a Pipeline job; *when* the script's `properties` step gives Job/Configure to `anonymous`; *then* the entry is gone after the build and one GRANT_VIOLATION names it.

- **[S-27-02] `GrantViolationGuard.java:507-550` (`propertyXml`/`property`/`apply`): a second authorization property of the same type is never examined, and the revert moves it into first place.** `Job.getProperty(Class)` returns the first match, and matrix-auth's `ProjectMatrixAuthorizationStrategy#getACL(Job)` uses it (l.55). `Job.removeProperty(Class)` removes only the first match (core l.596-604), and `addProperty` appends to the end (l.573-577). `JobPropertyStep` has no duplicate check, and a `config.xml` payload can also carry two elements. So when a save leaves two `AuthorizationMatrixProperty` instances on the item, the guard compares and rewrites only the first, and its own `apply` then makes the unexamined second instance the effective one. The next snapshot records it as the baseline. The same `apply` is used by D-35b (`revertGrantOnlySave`) and by D-35c `stripPayload` (`apply(item, "")` removes only the first property of a created item). So this also reopens D-35b/D-35c. The folder path (`DescribableList` first-match) behaves the same. Basis: B (privilege escalation). Fix direction: read the union of *all* instances as `now` (or treat more than one instance as a violation), and make `apply` remove every instance before it adds the single result. Test: *Given* a guarded job; *when* a save leaves two authorization properties, the later one naming the holder; *then* afterwards the job has exactly one authorization property, it has no entry for the holder, and GRANT_VIOLATION is recorded. Add the same row for a `createItem` payload by a Create-grant holder (D-35c).

- **[S-27-03] `GrantService.java:239-262` (`recentHolders`): guarded principals are looked up by the item's *current* name, but grant scopes do not follow a rename or move.** `GrantScope` is a full name, and only the D-35c created-items list is relocated (`CreatedItemGrantListener#onLocationChanged`). Core allows a rename with Item/Configure alone (`AbstractItem#doCheckNewName` l.283-288). The D-40 restriction applies only to items created through a restricted Create grant, and for plain CONFIGURE grants this is unconfirmed. So once a covered item is under a new name, no grant covers it, the guarded set is empty, and the guard lets through any entry saved in that state, for example by a build that was already running. The holder can then rename it back, and the entry is now in the baseline. Basis: B (privilege escalation). Fix direction: make guarded principals follow item identity rather than name. For example, record previous full names on the grant in `onLocationChanged` (covering folder children) and match `recentHolders` against them for the D-58 window. `ItemIdentity` already exists for this. Another option: refuse renames and moves through a CONFIGURE grant. Test: *Given* bob holds a CONFIGURE window on `J`; *when* `J` is renamed to `K` and a save of `K` adds an entry for bob; *then* the entry is removed and GRANT_VIOLATION names `K`.

## HIGH

- **[S-27-04] `GrantViolationGuard.java:295-298, 270-273`: widening through the inheritance strategy is not guarded.** `withoutGuardedAdditions` keeps the saved inheritance strategy and returns early when the property was removed (`parse(now) == null`). A job or folder set to `nonInheriting` is how a sensitive item opts out of a broad parent's grants. Switching it to an inheriting strategy, or removing the property, restores the parent's grants on that item. That can include Configure for the holder or one of the holder's groups, and it adds no entry. D-58's text speaks only of "entries", so this is also a spec gap. Basis: B (privilege escalation, conditional on a non-inheriting item under a parent that grants the holder more). Fix direction: while the guarded set is not empty, treat any change of inheritance strategy, and any removal of a property whose strategy was not "inherit parent", as a widening. Restore the baseline's strategy, as `withoutAdditions` already does for D-35b. Proposal for DECISIONS below. Test: *Given* a `nonInheriting` job under a folder that grants `authenticated` Job/Configure, and bob holds a window on it; *when* a build switches it to `inheriting()` (or removes the property); *then* the job is non-inheriting again and GRANT_VIOLATION is recorded.

- **[S-27-05] `GrantViolationGuard.java:601-621` (`Baseline#onCreated`): item creation is not covered by D-58.** `ItemGroupMixIn#createProjectFromXML` writes and loads the file without `save()`, so no `SaveableListener` event fires, and `onCreated` applies only the D-35c check (creator's own Create grant, never SYSTEM). This is the path used by Job DSL (seed job, `jobDsl` step) and by `createItem` or copy from a non-holder identity. A new item inside a folder the holder's grant covers is guarded by definition, but its creation payload is never compared. Updates are covered (`updateByXml` fires `onChange`, core l.953). Basis: B (privilege escalation, conditional on a creating identity with Item/Create: a SYSTEM seed, or a build account that has Create). Fix direction: in `onCreated`, apply `withoutGuardedAdditions` against an empty baseline to every created job and folder (and the children of a created folder). The only exemption is the D-58 administrator-over-HTTP one. Test: *Given* bob holds a CONFIGURE window on folder `F`; *when* a Job DSL seed creates `F/new` with an entry for bob; *then* `F/new` has no entry for bob and GRANT_VIOLATION is recorded.

- **[S-27-06] `GuardedPrincipals.java:118-146`: group lookup fails open, and the failure is cached.** Groups come only from `SecurityRealm#loadUserByUsername2`. Realms that cannot look up other users (common for SSO realms, which throw `UserMayOrMayNotExistException2` or `UsernameNotFoundException`) leave the user with `authenticated` only. The exception is logged at FINE and the empty result is cached for 5 minutes. So on such instances every GROUP entry for the holder's real groups is unguarded, and nothing warns about it. Basis: B (privilege escalation, conditional on the realm). Fix direction: use the union of the realm lookup (through `User#getUserDetailsForImpersonation2`, which falls back to `LastGrantedAuthoritiesProperty` for realms that cannot look up) and the user's `LastGrantedAuthoritiesProperty#getAuthorities2()`. Do not cache failures. Log a failed lookup at WARNING. Test: *Given* a realm whose `loadUserByUsername2` throws `UserMayOrMayNotExistException2` and bob last logged in with group `team-a`; *when* a save adds `GROUP:team-a`; *then* it is reverted.

## MEDIUM

- **[S-27-07] D-58 30-day window: a planted script keeps retrying and succeeds once the window lapses.** The Pipeline script edited during the window is not reverted, and the guard releases the holder 30 days after the grant ends. A script that keeps writing the entry is reverted, and recorded, only until then. A script that waits writes it once, later, with no violation. Basis: B (privilege escalation that is delayed and visible in the CONFIGURE diff). Fix direction: renew the holder's guarded status for an item whenever a D-58 revert for that holder happens there, or keep it until an administrator acknowledges the GRANT_VIOLATION. Document it in LIMITATIONS 35. Test: *Given* a revert for bob on day 29 after his window; *when* the same entry is written on day 31; *then* it is still reverted.

- **[S-27-08] Unguarded principals the holder controls: groups joined after the save, and self-signup accounts.** Groups are those "the realm reports now", so an entry for a group the holder joins later (self-service directory groups, SCM team membership) is kept. If `HudsonPrivateSecurityRealm` allows sign-up, an entry for a user id that does not exist yet is an account the holder can create themself. LIMITATIONS 35 counts accomplices as out of scope, but these need no second person. Basis: B (documentation of residual risk). Fix direction: say so in LIMITATIONS 35. Optionally, when sign-up is enabled, guard entries for user ids unknown to the realm, or warn in the `batch-control-strategy` monitor. Test (if the code option is taken): *Given* sign-up is enabled; *when* a save adds an entry for a non-existent id; *then* it is reverted.

## LOW

- **[S-27-09] `GuardedPrincipals.java:130` under `GrantViolationGuard.LOCK`: realm round-trips (for example LDAP) run while the instance-wide guard lock is held.** One slow directory stalls every job and folder save. The lookups happen only for authorization-property changes on guarded items, and they are cached, so the cost is bounded. Fix: compute `GuardedPrincipals.of` before entering `LOCK`, or with a timeout.
- **[S-27-10] `BuildLogNotice.java:42-44, 111-134`: the fallback writes to up to three running builds of the saved job.** When the save does not run on that job's own CPS thread (for example a seed job saving it), the line goes to builds that did not cause it. It is always the same job, never another one (the `getParent() != job` check). A reader with only Item/Read on the job learns the reverted sids and permission ids, which config.xml would otherwise hide from them. Fix: print only from `cpsListener`, and drop the fallback, or print without sids.
- **[S-27-11] `GrantViolationGuard.java:254-259, 282`: sids from the saved property go unfiltered into the build log line, the server log and the record detail.** Control characters can forge log lines. `ConsoleNote` is MAC-protected, so no console markup can be injected. Fix: strip or escape characters below 0x20 and cap the length of the list. Test: a sid containing `\n` appears escaped in the build log.
- **[S-27-12] Administrator exception vs. the CLI transport.** A WebSocket CLI command runs on a new thread (`CLIAction` l.207, "CLI handler for ..."), so an administrator's `update-job` over `-webSocket` or SSH has no Stapler request and is reverted. `-http` runs on the request thread and is exempt. LIMITATIONS 35 says "CLI over HTTP", which is only half true. Fix: correct LIMITATIONS, or recognise the CLI authentication explicitly.

## INFO

- **[S-27-13] The administrator exception could not be spoofed on any path reviewed.** Builds, CPS threads and WebSocket CLI threads have no Stapler request (a ThreadLocal, not inherited), so an administrator triggering a build does not exempt what the build saves. The check asks for native Administer with the grant layer off (`GrantLayer.hasPermissionWithoutGrants`). The exception depends on no plugin running holder-controlled code synchronously inside an administrator's request, which is not proven for every plugin.
- **[S-27-14] BuildLogNotice reflection is safe.** The class is loaded with `initialize=false` through `uberClassLoader`, only public no-argument getters are invoked on objects the listener already holds, every failure is caught, and the parent check stops writes to other jobs. `JobPropertyStep.Execution` is a `SynchronousStepExecution`, so `CpsThread.current()` is set for the DEF-38 path.
- **[S-27-15] Legitimate administrator use is changed by design (D-58).** For 30 days, Jenkinsfile, Job DSL, JCasC (after S-27-05) and non-HTTP CLI entries for guarded principals are reverted. That includes `authenticated` and *every realm group of every recent holder*, on the item and on each ancestor folder. For group-heavy instances this is broad, and the release notes should say so. Entries for non-holders are unaffected (T-02-54).
- **[S-27-16]** `holdsActiveGrant` (l.406-412) compares user ids with `String#equals`, not `IdStrategy`. D-58 now catches what D-35b misses there, so this has no effect beyond the record's wording.

- Web methods (B-1/2): this diff adds no `do*` method.
- Raw output (B-4): no Jelly change in 8824ef8. The D-48 refusal text is ui-dev's (f8b57a6, not in scope).
- `ACL.SYSTEM2` (B-5): no new switch.
- Secrets (B-6): no secret reaches the new log line or record, which hold only sids and permission ids.
- File paths (B-7): no new path built from input.
- CSV (B-8): not touched.
- XStream (B-9/10): the guard reparses only XML it serialised itself with `Items.XSTREAM2`. The snapshot is read with `XMLUtils.parse` (XXE-safe).
- Delegating strategy (B-13): unchanged. Role-based strategy: `guardApplies` is off, and item roles can be edited only by administrators, so no item-level property confers permissions there.
- EITHER entries: guarded as user or group (`isGuarded` default branch), using the same id strategies as matrix-auth.
- Folder property: covered, including ancestors of any grant scope (`recentHolders` prefix check).
- Two-step widening for a guarded sid: every addition is compared with the snapshot baseline, so a later widening is reverted too (except S-27-07/08).
- A save the baseline does not see: `updateByXml` fires `onChange`. `load()`/`doReload` need Configure plus a changed file on disk, which only a build on the controller could write. That is a general Jenkins exposure, not new here.
- Grant retention: `retentionMonths >= 1` with whole-month cut-off keeps ended grants for more than 30 days.
- Concurrency: compare, revert and baseline update all run under `LOCK`. The recursion guard is `RESTORING`.
