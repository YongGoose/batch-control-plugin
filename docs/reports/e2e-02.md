## T-E2E-06 — still FAIL, and now judged on real evidence

The same run, after waiting 69 s:

```
GET  /job/batch-daily/configure  as requester, AFTER expiry -> 403
POST /job/batch-daily/config.xml as requester, AFTER expiry -> 403
description after the refused save: unchanged (still the value written inside the window)
refusal body contains 'expired'              NO
refusal body contains 'grant'                NO
refusal body contains 'batch-control/grants' NO
```

**What is correct:** the window closes on the first permission check after the
expiry instant, with no timer involved, and the refused save changes nothing.
That half of SPEC item 8 holds.

**What fails:** the user is handed the stock Jenkins
"Access Denied — requester is missing the Job/Configure permission" page. Nothing
says the permission window expired, and there is no link back to
`/batch-control/grants/` to ask again. T-E2E-06 requires
"권한 창 만료 안내가 표시되고 권한 재요청 링크가 보인다".

Two things changed since e2e-01 and both matter for how this should be read:

1. **The verdict is now meaningful.** In e2e-01 this row could not be judged: the
   same 403 appeared *inside* the window because of E2E-D1, so an after-expiry
   403 proved nothing. That is why V-11 was deferred. With E2E-D1 fixed the two
   states are distinguishable — 200 inside, 403 after — and the refusal is
   demonstrably the expiry.
2. **This is an unimplemented decision, not a broken implementation.** SPEC item 8
   lists five acceptance criteria for grants and none of them mentions what the
   user is told when the window has closed; `docs/SPEC.md` has not changed since
   e2e-01, and the request raised there (*요청: docs/SPEC.md*) is still open. The
   run path does have such guidance (`ApprovalQueueDecisionHandler` throws a
   `Failure` with a link-bearing sentence), so the asymmetry is visible to users
   and is the argument for implementing it — but the decision is the owner's, not
   this agent's, and it is re-raised below rather than treated as a code defect.

All four points the delegation asked for hold: ① blocked, ② recorded as

approval), ④ readable on the history screen. `grantId` is empty and `detail` is
comma-free, exactly as P-12 specifies, so `changes.csv` keeps one cell per column.

core-owned"):

|---|---|---|

| `?kind=changes` | present | present |
| `?user=approver` | present | n/a (Runs tab) |
| `?user=approver&kind=changes` | present | present |
| `?job=batch-pipeline` | present | n/a (Runs tab) |

The block carries the heading, an "Attempted by" column, the attempt count and
the consumed request id, and names both `approver` and `admin`. The `?user=`
default-tab gap P-12 described is therefore closed by `545f9cb`.

**Observation (not a defect):** of the two refusals that qualify for a record,
only one is reachable in a live system. The spent-ticket check now runs before the
job-binding check, and consumption happens atomically at submission, so by the
time anyone can replay a marker it is always already spent — both of the attempts
above were recorded with the reason "its single submission ticket was already
claimed", including the cross-job one. The "the approval is bound to job X" reason
therefore only appears for an *unspent* marker on the wrong job, a state no
external actor can reach. It is correct defensive code and the integration suite
can construct that state directly; it just cannot be produced end to end, which is
worth knowing before someone treats the missing message as evidence of a gap.

## Incident lifecycle (PASS) — new scenario

`e2e/scripts/rest-incident-flow.sh`, on the new `batch-failing` seed job, driven
by `approver` (the account that holds ViewHistory, which every incident endpoint
checks):

```
POST /job/batch-failing/build (requester)                    -> 201, build #1 FAILURE
incidents: 1 -> 2 without anyone touching the plugin         <- auto-registration
GET  /batch-control/incidents/<id>/                          -> 200, status OPEN, links /job/batch-failing/1/
POST .../resolve while still OPEN                            -> 400
     "Incident ... is OPEN; only ACKNOWLEDGED incidents can be resolved
      (OPEN -> ACKNOWLEDGED -> RESOLVED, no skips, no reverse)."
POST .../acknowledge?comment=Cause: the upstream feed ...    -> 302
POST .../comment?comment=Action: asked the provider ...      -> 302
POST .../comment with an empty comment                       -> 400
POST .../resolve?comment=Resolved: the redelivered file ...  -> 302
GET  .../                                                    -> 200, RESOLVED, all three comments kept verbatim
incidents.csv: 20260926-192106-w7edhy,batch-failing#1,batch-failing,FAILURE,RESOLVED,2026-09-26T10:21:06.105Z,,
POST .../acknowledge on the RESOLVED incident                -> 400
GET  .../            as requester (no ViewHistory)           -> 403
POST .../comment     as requester                            -> 403
```

The whole flow the delegation asked for works on a real Jenkins: automatic
registration from a FAILURE result, the cause captured on acknowledgement, the
action captured as a comment, resolution, and a state machine that refuses both
the shortcut and the reverse. Suggested matrix rows are listed in the request to
test-author at the end.

**Observation:** `resolvedByRunId` stays empty for an incident resolved this way
(it is filled by `linkResolvedBy` when a rerun succeeds). So in `incidents.csv`,
"what fixed it" is only in the comment text, not in a column. That is consistent
with the model but means a spreadsheet reader cannot answer it. The `rerun`
endpoint was not exercised in this pass — it creates a new run request linked back
to the incident, and on this always-failing job it would loop; it is the one
incident path still only covered by integration tests.

## UX observations (for human judgement — not defects)

* **UX-13: the history warning block does not link its own rows.** The blocked
  attempts name a job and an account as plain text; from the warning an operator
  cannot click through to the job, the request whose marker was replayed, or the
  Changes tab filtered to that job. The overflow line does link the Changes tab,
  so the affordance exists only when there are more attempts than the block lists.
* **UX-14: `resolvedByRunId` is invisible for hand-resolved incidents.** Column
  present, always empty unless a rerun resolved it (see §incident). Either fill it
  when a resolution comment mentions a build, or say in the screen that "resolved
  by" only applies to reruns.
* **UX-15: the incident state machine's refusal is precise but late.** "Only
  ACKNOWLEDGED incidents can be resolved (OPEN → ACKNOWLEDGED → RESOLVED, no
  skips, no reverse)" is an excellent message, but it arrives as an error page
  after the click. If the screen only offers the transitions that are legal for
  the current status, the message becomes unreachable for honest users.
* **UX-16: an empty comment is refused with a 400 error page** rather than inline
  validation on the incident form ("A comment must not be empty."). Same shape as
  UX-15: correct, but the user pays with a round trip and a back button.
* **UX-17: `Remaining` is a snapshot.** The column says so honestly, but a user
  watching a 1-minute window will see a stale value; a relative countdown would
  match how the number is actually used.

## Environment change worth keeping

**D-31 now applies to the environment's own seed jobs.** `10-batch-control-config.groovy`
turns run control on before `20-sample-jobs.groovy` creates the jobs, so on a
fresh `reset.sh` every seed job — including the ones whose whole purpose is to run
unattended — is created `approvalRequired=true`. Left alone, `batch-cron` stops
feeding the dashboard and `batch-failing` can never fail on demand, and the
breakage is silent (the jobs simply never build). `20-sample-jobs.groovy` now
removes the property explicitly right after creating those two jobs, and the boot
log shows both halves:

```
INFO ItemChangeListener#applyApprovalRequiredDefault: New job 'batch-failing' starts with approvalRequired=true while run control is on (D-31)
INFO e2e: removed the D-31 approvalRequired default from 'batch-failing'
```

Other environment facts as this report closes: `batch-failing` is a new seed job;
`numExecutors` is back to 2; approvers are `[approver, admin]`; the authorization
strategy is the wrapper over matrix-auth; the four `batch-e2e-d31-*` jobs created
by the D-31 scenario were deleted; `batch-reconcile` (created by the orchestrator
before D-31 landed) is still uncontrolled and left as it is — it is a useful
reminder that D-31 is a creation-time default and does not retrofit existing jobs.
