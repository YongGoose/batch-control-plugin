## FAIL details

**F-1 `r16-durable` in shard 5 (driver defect, fixed; not a plugin defect).** Reproduction: run the units of shard 5
(`e2e/ci/run.sh 5/5` at ad4a132). `r16/durable.py` restarts Jenkins and then runs `r16/arrange.py` again to restore the
permissions JCasC resets at boot. Between the dev runs and the shard run, `r16/arrange.py` had been changed to revoke
the r16 accounts' leftover windows before its fixture check, so the post-restart arrangement revoked the check's own
control window (`ff371cd3...`, "Could not save grant ... as ended (revoked)" in `out/5/jenkins.log`, the grants
directory being read-only at that moment). Expected: control window still confers (200) after the restart. Actual: 403,
hence the two FAIL lines (`out/5/logs/29-r16-durable-r16-durable.log`). The plugin behaved correctly throughout: the
deleted job's window stayed ended across the restart (403, listed as Ended), and the unintended revocation during the
fault took effect at once (403) although its file could not be written. Fix 0a68f5c: `R16_KEEP_WINDOWS=1` for the
post-restart arrangement. Re-run `supp2`: 4/4 PASS (`out/supp2/logs/13-r16-durable-r16-durable.log`, screenshots
`out/supp2/driver/screenshots/run-16/R16-DUR-1-after-delete-list.png`, `R16-DUR-2-after-restart-list.png`).

Found earlier in this round and already fixed (no action): **DEF-E16-01** (HIGH, security). At the pre-D-74 tip
3fdc634 a CONFIGURE-window holder could rename through a trailing path segment: `POST
/job/r16/job/ren-job/confirmRename/extra?newName=byp1` answered 302 and renamed the job, without GRANT_VIOLATION
(also `confirm%52ename/extra`, `confirmRename/a/b`, and the folder `r16-renf`). Cause: the rename detection took the
last path token while Stapler dispatched the first. c50c98a ("rename detection by the dispatched method", D-74,
security-38) closed it; rename E/G/C assert all three spellings on job and folder on every run (PASS here).
