## Defects

**DEF-05 (medium, known, D-38b).** A user with BatchControl/Request only on a folder (`folderreq`) submits a run request and is redirected to `/batch-control/requests/<id>/`, which answers 404 to them ("Oops! Not Found"), so they cannot see or cancel it (`B4-03-after-submit`). The request itself is created correctly and the approver is notified. Fix in progress (D-38b), to be verified in E2E-3.

**DEF-06 (medium): with the rebuild plugin installed, the new job page's "More actions" menu fails on every approval-required job, not only on jobs without builds.**
- Steps: requester (or admin) opens `/jenkins/job/batch-daily/` (approval-required, builds #1 and #2 exist) on the new job page and clicks "...".
- Expected (LIMITATIONS 45): the menu fails only on a job with no builds.
- Actual: the menu stays empty and the console shows `TypeError: Cannot read properties of null (reading 'startsWith')`. The job's `contextMenu` returns "Rebuild Last" with event url `null` on batch-daily and team/sub/deep-job (both approval-required, both with builds), even for admin. On the uncontrolled `batch-failing` it is `lastCompletedBuild/rebuild/parameterized`. `/job/batch-daily/1/rebuild/` answers 404 to requester. With rebuild disabled, the menu works and DEF-01 passes. As a result, "Request Change Permission", "Delete Project" and "Rename" cannot be reached from the new job page on every controlled job of an instance with rebuild installed.
- Suspected owner: whatever makes the rebuild action unavailable for approved runs on approval-required jobs (ui-dev `action/**` or core-dev `queue/**`; to be confirmed). A fix could keep Rebuild Last with a real URL (the gate refuses the run anyway), or make sure no null-URL entry is produced. `docs/LIMITATIONS.md` 45 (release-manager) needs to describe the real trigger if this is left as is.

**DOC-01 (low): LIMITATIONS 47 is missing.** The brief says DEF-02 is accepted as LIMITATIONS 47, but `docs/LIMITATIONS.md` on this branch has items 40, 41, 45, 42, 43, 44, 46 and nothing about the app-bar order of Request Run vs Direct Build. The numbering is also out of order (45 between 41 and 42, as already noted in the request queue).

## UX observations (judgement calls)

1. Submitting a grant request returns to the Grants page with the new row in the table, but with no confirmation and without opening the request. A run or activation request opens its detail page instead. Consistency would help.
2. The strategy monitor links "Change Records", while the tab is now called "Changes". "Mark as reviewed" renders as plain black text next to the item and does not look clickable (`A3-01-monitor`).
3. The Move refusal says "Request a permission window for Delete on 'prod/x'", but that is not a link to the prefilled grant form. The item link is a bare "prod/x".
4. A D-38a requester (`reqonly`) who calls POST `/job/X/build` gets core's bare "Access Denied - reqonly is missing the Job/Build permission" (403), because core checks Build before our gate. The job page does not offer them a build button, so this only affects scripted users. A README line could mention it.
5. At 1280 px the Grants requests table wraps the IDs onto two lines and "APPROVED (window revoked)" touches the right edge (`E-dark-grants`).
6. The two green app-bar buttons (E2E-1 UX-1) are unchanged.
7. After change control is turned off and on again, every earlier window is gone as "revoked" (E2E-1 UX-5, backlog).
