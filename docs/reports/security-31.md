## Legitimate use of "refuse when unresolved"

- Replay and Pipeline Rebuild: the new `ReplayCause` names the run the user is on, so the source exists at submission time.
- Restart from Stage: the cause names the run being restarted, through a persisted number.
- rebuild-plugin Rebuild: `RebuildAction` copies the old causes (an old `ReplayCause` or `RebuildCause` whose run may have been deleted by log rotation), then appends `UserIdCause` and a new `RebuildCause(current)` last (`javap`, l.381-402). `sourceRun` uses the last re-run cause, so an old deleted source is never consulted.
- naginator copies causes, but only for `AbstractBuild` (Freestyle), which never carries a Pipeline re-run cause.
- Timers, upstream triggers, Build Now and SCM carry no re-run cause or flow action, so they get `Source.NONE`.
- Administrators and SYSTEM are exempt before the refusal.
- The residual is S-31-05.

## LOW

- **[S-31-01] `ApprovalQueueDecisionHandler#markReplayUnderGrant`: while change control is off, a re-run of a marked run is neither refused nor marked, so the script is laundered once the switch is turned back on.** Both `refuseMarkedSource` and `markReplayUnderGrant` return early when change control is off. With the switch off, any Item/Build holder can re-run marked `J#2` as `J#3`. `J#3` carries no marker, so after the switch goes back on it can be re-run by anyone. Turning the switch off needs an administrator, and the refusal being off is by design. But the marker is meant to be permanent (D-58c "before and after the review"). Basis: B (privilege escalation that needs an administrator's switch toggle; D-58c). Fix direction: propagate an inherited marker regardless of the switch. It is an `InvisibleAction`, so existing Jenkins behaviour does not change, which is consistent with the CLAUDE.md global-switch rule. Keep the refusal gated on the switch. Test: *Given* `J#2` is marked and change control is turned off; *when* alice (Item/Build) uses Pipeline Rebuild of `J#2` (giving `J#3`), change control is turned on, and alice rebuilds `J#3`; *then* `J#3` carries the marker and the second submission is refused and recorded.
- **[S-31-02] Propagated marker: the audit trail names the propagating user as the grant-only replayer.** The inherited `ReplayUnderGrantAction` is created with `auth.getName()`, for example an administrator or `SYSTEM`. `ReplayUnderGrantListener` then writes a `REPLAY_UNDER_GRANT` record whose user is the administrator and whose text says "by 'admin' whose permission came only from a permission window". That is false, and the original replayer disappears from the new run's marker (only the grant id links back). Basis: B (audit integrity). Fix direction: carry the original user in the inherited marker and add a `propagatedBy` field (a new optional `String`, XStream-safe). Give the record a distinct wording such as "re-run of marked run #n by '<user>'; originally replayed by '<orig>' under grant <id>". Test: *Given* `J#2` is marked for bob; *when* an administrator restarts a stage of `J#2`; *then* the `J#3` record names bob as the original replayer and the administrator as the re-runner, and does not say that the administrator's permission came from a window.
- **[S-31-03] `GrantService#loadMarkedRunsOnce`: after a restart the index is rebuilt under the job names recorded at the time, so renamed jobs lose their listing and a re-created job with a recycled name lists another job's run ids.** Relocation and deletion are applied only in-session. Records keep the old target. On the next start, `J` renamed to `K` lists nothing under `K`. A new `J` shows "J#2 was replayed under a permission window", linked to an innocent `J#2`. The refusal is unaffected, because it reads the run's own marker. This affects only the review listing, which Configure and Administer holders see. Fix direction: in `ReplayedRuns.of`, resolve each of the at most 50 ids (a bounded number of loads) and drop rows whose run is missing or has no `ReplayUnderGrantAction`. Optionally, also index under the current name when a marked run is loaded. Test: *Given* `J#2` is marked, `J` is deleted, a new `J` is created with a build `#2`, and Jenkins restarts; *when* an administrator opens the monitor or the job page; *then* the new `J#2` is not listed.
- **[S-31-04] (= S-30-06, still open) `BatchControlStrategyMonitor/message.jelly`: a listed name that no longer resolves has no "Mark as reviewed" button.** `doMarkReviewed` accepts it through `clearStaleEntry`, but only a hand-made POST can reach it. Fix direction: render the same POST form in the `<j:otherwise>` branch (ui-dev).

## INFO

- **[S-31-05]** Over-block residual of the unresolved rule. A non-administrator's submission is refused as unresolved if (a) its last re-run cause names a run that cannot be loaded (a deleted run, or a corrupt `build.xml`), or (b) it carries a `ReplayFlowFactoryAction` without a `ReplayCause`. No such path was found in workflow-cps, pipeline-model-definition, rebuild or naginator. The one other case would be a plugin that copies a Pipeline run's causes into a submission without appending its own re-run cause. This fails closed, the message says "Ask an administrator", and the refusal is recorded. That is acceptable.
- **[S-31-06]** Fail-open corners. Any `RuntimeException` in `refuseMarkedSource` returns "do not refuse" (logged at WARNING). The `RestartFlowFactoryAction` fallback resolves with `Run.fromExternalizableId`, which goes through the caller's ACL, and `Jenkins#getItem` throws `AccessDeniedException` for a Discover-only caller. That fallback is reached only when the restart cause is missing, which upstream never submits. Suggest reading the fallback through `itemForPolicy` for consistency.
- **[S-31-07]** `loadMarkedRunsOnce` sets `markedRunsLoaded = true` before it loads. A concurrent first render can therefore see a partial list once per session. This affects the listing only.
- **[S-31-08]** `markReviewed` now names uncleared descendants (`kept`) that the reviewer may not be able to read in the `GUARD_REVIEWED` record. This cannot be reached today: the non-admin entry point (`JobRequestAction#doMarkReviewed`) is attached to `Job`s only (`JobRequestActionFactory extends TransientActionFactory<Job>`), so `changedAtOrBelow(job)` holds only the job itself. The admin path sees every item anyway.
- **[S-31-09]** Carried-forward residuals from earlier rounds, none changed in this diff: S-28-06 (a lost mark is logged SEVERE and not reconciled), S-28-07 (rename race), S-28-09 (delete and re-create drops the state), S-28-14 (D-58a CLI wording), S-28-16 (grant scopes stay on the old name), S-29-03 residual (a store failure is swallowed), S-29-07/S-30-10 (work under the Queue lock; `sourceRun` is now evaluated twice for accepted re-runs), S-30-07 (grant-inclusive Administer test, safe), S-30-08 (anonymous refusal is quiet).
