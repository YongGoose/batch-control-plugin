## MEDIUM

- **[S-29-01] `ApprovalQueueDecisionHandler.java:138-177`, `GrantService#markReviewed`: a Replay under a grant is marked silently, and the review does not have to look at the replayed runs, which stay re-runnable afterwards.** The marking writes no change record. The monitor and the job page tell the reviewer to "check what was changed under the permission window (see Change Records) and the Pipeline script". Neither names the replayed run, and Change Records has no entry for it. Once the job is marked as reviewed, anyone with Item/Build can use Pipeline Rebuild or Restart from Stage on that run, including the former holder through native Build. Both re-run the stored replayed script, so a `properties([authorizationMatrix(...)])` planted there is then kept. A replayed run still running or queued at review time behaves the same way. LIMITATIONS 35 says "any replayed runs included", but the plugin gives the reviewer nothing to find them with. Basis: B (privilege escalation that depends on an uninformed review; D-58b (2)/(3)). Fix direction: at marking time, append a change record that names the job, the source run, the queued run, the user and the grant id. Better, keep the replayed run ids with the grant (an ARCHITECTURE 5 field, so a DECISIONS proposal first), list them on both review surfaces, and have the queue gate refuse Pipeline Rebuild and Restart from Stage of those runs even after the review, recording the refusal. Test: *Given* bob holds a CONFIGURE window on Pipeline job `J` without `approvalRequired`, replays `J#1` as `J#2` with a script that writes `USER:bob` Job/Configure only when a parameter is set, the window ends and an administrator marks `J` as reviewed; *when* alice (Item/Build) clicks Rebuild on `J#2` with that parameter; *then* the submission is refused and recorded, or at minimum a change record written at replay time names `J#2` and the monitor listed it before the review.

## LOW

- **[S-29-02] `GrantService#markReviewed` (l.391-405) clears every descendant, but checks permission on the reviewed item only.** A native Configure holder on folder `F` could clear the mark of `F/J` even when they have no native Configure on `F/J`, for example because `F/J` does not inherit or a role-strategy pattern matches `F` only. If they changed `F/J` under a grant, that is a self-review. This cannot be reached today. The only entry point for non-administrators is `JobRequestAction`, which is attached to `Job`s only. The descendants of a job are matrix configurations, which take their ACL from the parent. Fix direction: for a reviewer who is not an administrator, clear only the exact item, or only the entries on which `hasPermissionWithoutGrants(entry, CONFIGURE)` holds. Test: *Given* `F/J` does not inherit, carol has native Configure on `F` only, and bob changed `F/J` under a grant; *when* carol's `markReviewed(F)` runs; *then* `F/J` stays guarded.
- **[S-29-03] The `GUARD_REVIEWED` record is unconditional and can be misleading.** `markReviewed` appends it even when nothing was cleared, when `rewriteChanged` swallowed a store failure (it logs WARNING and continues), or when the job is still guarded through a changed ancestor or an active grant. The record text then says "no longer guarded". Any native Configure holder with BatchControl/Request can POST `markReviewed` on jobs that are not in the state and fill the history with such records. `isShowMarkReviewed` uses the grant-inclusive `job.hasPermission(CONFIGURE)`, so the button is shown to a grant-only holder (the click then gets 403). It is also shown to a native holder whose job is guarded only through its ancestor, where the click changes nothing. Fix direction: `rewriteChanged` returns how many entries it removed and rethrows a store failure. Refuse (400) when the item has no own entry. Write the record only after a successful removal, saying whether the item is still guarded and why. Use `GrantLayer.hasPermissionWithoutGrants` and the item's own mark in `isShowMarkReviewed`.
- **[S-29-04] A stale entry cannot be reviewed.** The monitor shows a listed name that no longer resolves without a button, and `doMarkReviewed` answers 404 for it. Such entries are possible because `onLoaded` prunes `createdItems` but not `changedItems`, for example after an item is removed on disk and then reloaded, or after a missed `onDeleted`. The monitor then stays active and retention keeps the grant file forever. This is fail-safe, but there is no way out without editing files by hand. The list is capped at 50, so entries past the cap have no button until earlier ones are cleared. Fix direction: let the administrator endpoint accept a name that exactly matches a listed entry even when no item resolves (keep the 404 for anything not listed). Show the button for such names too.
- **[S-29-05] Every item created below a changed item gets its own redundant mark, and each costs a grant-file rewrite.** `guardCreationInGuardedFolder` calls `markChanged` for each new item whose ancestor is marked, including SYSTEM creations such as branch or PR jobs from indexing a changed multibranch project. Each call rewrites the whole grant file while holding the `GrantService` monitor, which every grant-layer permission check also needs, and `changedItems` grows without bound until the review. Fix direction: in `markChanged`, skip the write when `changedAtOrAbove(grant, item)` already holds for that grant. The ancestor's entry already guards the item, and review, rename and delete of the ancestor handle descendants. Mark a created folder and its contents in one write.

## Answers to the caller's questions

- **Self-review:** `markReviewed` requires native Item/Configure on the item or native Overall/Administer, both asked with every grant layer off (`GrantAwareACL.withoutGrants` also switches off the parent/inherited evaluation). A FOLDER-scope holder's Configure on `F/J` comes from the grant, so they are refused. A holder with native Configure on `F/J` whose changed item is `F` can clear only `F/J`'s own entry, and `F/J` stays guarded through `F`. The monitor needs Administer, which no grant confers (it is not grantable, and it is rechecked natively). The only latent path is S-29-02.
- **Endpoints:** `BatchControlStrategyMonitor#doMarkReviewed` has `@RequirePOST` and `Jenkins.checkPermission(ADMINISTER)` as its first two lines, and the monitor's `getTarget` also checks ADMINISTER. `JobRequestAction#doMarkReviewed` has `@RequirePOST` and `job.checkPermission(CONFIGURE)`, then the native recheck. Its URL exists only for BatchControl/Request holders, and the job is bound by the URL (Item/Read). For the `item` parameter: `null` or an unknown name gives 404. `Jenkins#getItemByFullName` resolves segment by segment, and `..` and `.` are not valid item names, so traversal cannot resolve. The name never reaches a file path: the state is a string list inside the grant file, whose path comes from the grant id. The canonical `getFullName()` of the resolved item is what gets cleared. An administrator can see every item, so there is no hidden-item case. The job page has no name parameter. Both Jelly files are `escape-by-default`, and the hidden `item` value is escaped.
- **Replay bypasses:** web `doRun` and `doRebuild`, REST and CLI `replay-pipeline` over every transport all end in `ReplayAction.run2`. It always adds a `ReplayCause` and calls `ParameterizedJobMixIn.scheduleBuild2` synchronously in the caller's thread, under the caller's authentication (the CLI runs as the CLI user), so `Jenkins.getAuthentication2()` is the holder. A Pipeline `build` step creates an `UpstreamCause` and cannot carry `ReplayFlowFactoryAction`, so it runs the target's saved configuration, which is guarded if the holder saved it. Calling `ReplayAction.run2` from a script needs script approval by an administrator. The grant lookup (`findActiveGrant`, exact scope) is the one `GrantAwareACL` uses to confer Replay, so a Replay that a grant made possible is always found. Items created through a grant are marked at creation (`recordCreatedItemIn`). A Rebuild copying a `ReplayCause` over-marks, which is harmless. The only residual is S-29-01.
- **Descendant cost per save:** `isGuardedItem` loops the cached grants once, doing a `startsWith` per changed entry and, for active grants, per created entry. It takes no lock beyond the `GrantService` monitor, which the permission path already takes per check, and does no I/O. That is below the snapshot file read that each guarded save already does. `guardingGrantOf` on creation costs depth x grants. The growth issue is S-29-05.
