## HIGH
- [S-21-01] `security/SystemBuildCheck.java:77-92` (`runsAsSystem`), and the remedy text in `action/GrantRequestItem/index.jelly:100-107` and `ops/BatchControlStrategyMonitor/message.jelly` (the "or give each job its own build authorization" paragraph): the check asks the wrong question. It asks whether a build a person clicks *today* runs as SYSTEM. D-50 needs to know whether the Configure window holder can *make* a build run as SYSTEM. The check misses two cases, both confirmed from the authorize-project bytecode:
  - Case 1, a strategy that answers only for a user cause. `TriggeringUsersAuthorizationStrategy.authenticate(Job, Item)` returns `null` when the item has no root `UserIdCause`. `ProjectQueueItemAuthenticator` then returns `null`. With no global default authenticator, `Queue.Item#authenticate2()` falls through to `getDefaultAuthentication2`, which is SYSTEM. The probe always carries `UserIdCause(PROBE_USER)`, so it gets `ANONYMOUS2` back and reports "not SYSTEM". The holder only has to add a cron or SCM trigger (a Configure change) for the next build to run as SYSTEM.
  - Case 2, the job's own strategy can be removed by the holder. `AuthorizeProjectProperty$AuthorizationAction#doAuthorize` checks only `Job.CONFIGURE`, then calls `removeProperty` and adds the property only if the form carries one. Any Configure holder can therefore delete the job's build authorization. `ProjectQueueItemAuthenticator.authenticate2` returns `null` for a job without the property, so in "per-project" mode with no global default, every job in a CONFIGURE scope can be made to run as SYSTEM. That includes jobs that the probe correctly reports as running as a specific user today.
  - Effect: the approver and the administrator are told nothing, or told "fixed", in exactly the DEF-37 escalation class. A build running as SYSTEM writes a permanent authorization entry that the D-35b guard does not revert (D-35d (2), LIMITATIONS 35). This is rated HIGH rather than BLOCKER because the exposure is Jenkins' own and D-35d accepted it. The finding is that the D-50 mitigation the approver relies on is silent where the exposure exists, and its advice ("give each job its own build authorization") does not close it.
  - Basis: SPEC line 151 ("jobs ... whose builds would run as SYSTEM under the configured build authenticators"); D-50 (a)-(c); D-35d (2); checklist B (`ACL.SYSTEM2` / permission reasoning).
  - Fix direction:
    - (1) Treat a job as exposed when *either* of two probes yields SYSTEM (or null): the current user-cause probe, or a probe with no user cause (for example `TimerTrigger.TimerTriggerCause`, or an empty `CauseAction`).
    - (2) Separately, detect whether the authenticator chain has a fallback that answers for a job *without* its own property. That means a configured `QueueItemAuthenticator` other than `ProjectQueueItemAuthenticator` that yields a non-SYSTEM identity: authorize-project's `GlobalQueueItemAuthenticator`, matched by class name, since authorize-project is not a dependency, or a probe of a synthetic property-less `Queue.Task`. If there is no such fallback, every job in a CONFIGURE scope is exposed. The monitor and the detail page should then say so as a single instance-wide warning, not per job.
    - (3) Drop the "or give each job its own build authorization" remedy from both views and from LIMITATIONS 35. Only a global default build authorization is effective against a Configure holder.
    - (3) goes beyond D-50 (c) as written, so see the Request below.
  - Regression test (two rows):
    - (a) Given authorize-project in per-project mode with no global default, and job J with `TriggeringUsersAuthorizationStrategy`, and a pending CONFIGURE grant request on J; When an administrator opens `/manage/`; Then the `batch-control-strategy` monitor lists J, and the request's detail page shows the SYSTEM warning.
    - (b) Given the same mode, and job K with `SpecificUsersAuthorizationStrategy(alice)`, and a pending CONFIGURE request on K; When the approver opens the detail page; Then a warning says that K's build authorization can be removed by the window holder, so its builds can be made to run as SYSTEM.
    - (c) Control row: Given a `GlobalQueueItemAuthenticator` default of "run as triggering user" and a job with no property; When the monitor is rendered; Then only the timer-cause exposure is reported (or nothing, if the global default also answers without a user cause).

- [S-21-02] `action/GrantRequestItem.java:144-185` and `action/GrantRequestItem/index.jelly:85-107`: the D-50 block tells viewers things that SPEC's visibility rules withhold. It also shows the warning to the requester, while D-50 addresses it to the approver.
  - (a) Folder scope: `getSystemBuildHiddenCount()` prints "N more job(s) in this folder that you cannot see". This tells the viewer that jobs they cannot read exist, how many there are, and one fact about their configuration: their build authorization runs as SYSTEM. In core that setting is visible only with Configure/Extended Read, through the Authorization action.
  - (b) Job scope: `systemBuildJobs` names the scope whenever it runs as SYSTEM, "whatever the viewer may read" (line 151). This includes the fallback at line 173, which runs the unfiltered SYSTEM2 list for a job the viewer cannot see. The warning therefore appears only if the job still exists and runs as SYSTEM, so it acts as an oracle for existence and configuration. The viewer set is the requester, the designated approvers and Manage holders (`Visibility.canSeeGrantRequest`). A designated approver may hold only Item/Discover or nothing (SPEC line 89), and a requester may have lost Item/Read since filing.
  - (c) The block renders for every viewer, including the requester. SPEC line 151 and D-50 (b) say "warns the approver". The requester is the D-50 threat actor. Before approval, the block tells them which jobs in their scope can be made to run as SYSTEM and how to use that ("they can change such a job so that its next build changes the job's permissions permanently"). A Read-only requester cannot otherwise see a job's build authorization.
  - Basis: P-09 and `Visibility` ("a non-visible object renders exactly like a nonexistent one ... to hide its existence"); SPEC line 124 (security-14: an ancestor's "name and state are shown only to viewers with Item/Read on it"); SPEC line 151; checklist B item 3 (information exposure). Rated HIGH per the advisory convention for information disclosure. The disclosure is limited to a count or a yes/no per job, and only to the parties of the request. The human may downgrade it with that in mind.
  - Fix direction:
    - Render the block only when `canDecide` or when the viewer holds Manage/Administer. The requester sees nothing, or a neutral line such as "an administrator will review the build authorization of the jobs in this scope".
    - For an approver, name only the jobs they can read, and replace the count with a constant sentence that is independent of the data. For a folder scope, always show "jobs you cannot read are not checked here; the administrator's batch-control-strategy monitor lists them". For a job scope the approver cannot read, always show "the build authorization of this job cannot be shown to you".
    - The approver who cannot read is still told to ask, and nothing distinguishes "exists and runs as SYSTEM" from anything else.
  - Regression test:
    - Given folder F that the requester and the approver can read, and job `F/secret` they cannot read, whose builds run as SYSTEM, and a pending CONFIGURE request on F by the requester.
    - When the requester opens the request; Then the page contains no SYSTEM-build block and no job count.
    - When the approver opens it; Then no number of hidden jobs appears. The constant sentence appears identically after `F/secret` is deleted or given a user strategy, so the page bytes of the block do not change.

## MEDIUM
- [S-21-03] `action/GrantRequestItem.java:144-185` together with `security/SystemBuildCheck.java:100-146`: one GET of a grant request detail page by an unprivileged viewer can cost up to about 1,000 authenticator calls, with no cache and no rate limit.
  - For a folder scope, `getSystemBuildJobs()` and `getSystemBuildHiddenCount()` each call `SystemBuildCheck.jobsRunningAsSystem()`.
  - That call does not scan only this request's scope. It scans the scopes of *every* active CONFIGURE grant and pending CONFIGURE request: up to 500 probes, plus one store read per open grant request (`FileStore.listOpenGrantRequests` loads each open request from disk).
  - A job scope the viewer cannot read also triggers the full scan (line 173).
  - Each probe runs every `QueueItemAuthenticator`. For authorize-project's specific-user and triggering-user strategies that includes `User.impersonate2()`, a security-realm lookup (LDAP or AD round trip, depending on the realm's cache). An unknown user also produces a WARNING log line from authorize-project.
  - A requester who holds only `BatchControl/RequestGrant` can file CONFIGURE requests on large folders they can read, which raises the scan to the 500 bound. They can then reload their own request page in a loop.
  - No lock is held during the probes (checked: `GrantService.listActive` returns a copy, and the probes run after it). The cost is CPU, realm traffic and log volume, not a global stall.
  - The scan runs only while the request is PENDING and includes CONFIGURE (line 163), so closed requests cost nothing.
  - Basis: checklist B (information exposure / `doCheck*`-style read paths must not be an amplifier); SPEC item 13 bounded-scan practice ("bounded like the other monitor scans", D-50).
  - Fix direction: on the detail page, scan only this request's scope, in a single pass that returns both the readable names and the "not checked" indication, with its own bound. Memoise the result per scope for a short time (for example 60 s) in a small bounded cache that drops an entry when a grant or request on that scope changes. Never expand to other requests' scopes on this page.
  - Regression test: Given three pending CONFIGURE requests on folders of 400 jobs each, and a test `QueueItemAuthenticator` extension that counts its calls; When the requester of the first request GETs its detail page twice within the cache window; Then the authenticator is called at most 400 times in total (and 0 times on the second GET).

- [S-21-04] `security/SystemBuildCheck.java:120-146`, `action/GrantRequestItem.java:176-183` and `ops/BatchControlStrategyMonitor/message.jelly`: the global bounds, and the handling of failures, make the warning go silent without saying so.
  - `MAX_SCANNED` is one budget shared by all scopes, in `LinkedHashSet` order (active grants first, then pending requests). A pending request whose scope comes after 500 jobs of other scopes is never probed.
  - `MAX_RESULTS` truncates the *sorted global* list to 50 *before* the detail page filters by prefix. A folder that sorts after 50 SYSTEM jobs elsewhere shows no warning.
  - An authenticator that throws counts as "not SYSTEM" (line 88, logged at FINE).
  - In all three cases the approver sees a page with no warning, which reads as "safe". The monitor also lists 50 names with no "and more".
  - The only trace is one WARNING in the controller log, which the approver cannot see.
  - Basis: D-50 (b) (the approver is told before deciding); SPEC line 151; S-21-03 of #21 (a cap must not silently drop new facts).
  - Fix direction: a per-scope scan on the detail page (see S-21-03). Report "not all jobs in this scope could be checked (checked n of m; k could not be determined)" whenever the bound is hit or an authenticator failed, and make "cannot tell" visible rather than equal to "not SYSTEM". The monitor should add "and K more" when it truncates.
  - Regression test: Given active CONFIGURE grants whose scopes hold 500 jobs, and a pending CONFIGURE request on folder `zz` containing one job that runs as SYSTEM; When the approver opens that request; Then the page names the `zz` job, or states that the check was incomplete.

- [S-21-05] `queue/ApprovalQueueDecisionHandler.java:236-253, 490-503` (D-51): the per-attempt record has no bound that a user with Item/Build cannot defeat, and every record is appended under the global queue lock.
  - The key is (job, kind, source build, user), in `BlockedAttemptAudit.record`. That method tracks at most `MAX_TRACKED_KEYS` = 512 keys (LRU), and this map is shared with the `MARKER_REUSE_BLOCKED` and `REMOTE_RUN_BLOCKED` callers.
  - Before this change the key was per user in `recordCoalesced`: one hour, 10,000 keys, so at most 1 record per hour per (job, kind, user).
  - Now a user who may click Retry can POST naginator's retry for each retained build of a job. That gives one record per build per minute. With more than 512 distinct builds (common for batch jobs that keep long histories), or a handful of jobs, the LRU evicts the oldest keys and each HTTP request writes a record.
  - `BlockedAttemptAudit`'s own Javadoc says this append runs inside `Queue#schedule2` with the queue lock held, which is the self-inflicted DoS that #21/S-21 introduced the bound for.
  - The records name the user, so an auditor can see the flood, but the history screens and exports grow without limit.
  - Whether naginator's `retry` endpoint requires POST was not checked: unconfirmed.
  - Basis: SPEC line 107 / D-51 (per attempt, with a one-minute merge); `BlockedAttemptAudit` design (#21, S-21); SPEC item 9 audit goals (every distinct attempt kept, but a history an auditor can read).
  - Fix direction (suggested bound): keep D-51's per-attempt record for the first N distinct attempts per user per window, for example 20 per user per 10 minutes across all jobs. After that, merge that user's further person refusals into one coalesced record per user and window: "U: K further refused re-runs of J1, J2, ... between t1 and t2 (builds #..)". Track the person keys in a map sized like the coalesced one (10,000, configurable), so that LRU eviction is not reachable by cycling builds.
    - Optionally, move the append out of the queue lock: queue the record and write it after `schedule2` returns.
    - This amends D-51, so see the Request below.
  - Regression test: Given an approval-required job with 600 retained builds and naginator, and a user with Item/Build; When the user POSTs Retry on each of the 600 builds within one minute; Then at most the budgeted number of per-attempt `TRIGGER_BLOCKED` records plus one summary record exist, and a Retry by a second user in the same minute still writes its own record.

## LOW
- [S-21-06] `ops/BatchControlStrategyMonitor.java:77-81`: `isActivated()` runs the full uncached scan on every page an Administer holder renders.
  - Path: `ManageJenkinsAction#getBadge` in the header, then `isActive(m)`, then `isActivated()`. `Jenkins#getActiveAdministrativeMonitors` and `message.jelly` (`getJobsRunningAsSystem`) run it again on `/manage`.
  - In the normal steady state (a Batch Control strategy installed and an authenticator configured) the two cheap conditions are false, so the scan is not short-circuited.
  - When the 500 bound is hit, `LOGGER.warning` (line 142) writes one WARNING per admin page view. Authorize-project writes "Invalid User ..." at WARNING for each probe of a job whose specific user no longer exists.
  - The trigger is admin-only (`hasRequiredPermission`, default Administer), so this is a cost and log-noise issue, not an exposure.
  - Fix direction: compute in an `AsyncPeriodicWork` (for example every 5 min) and when a CONFIGURE grant or request is created or ends. Have `isActivated()` and the view read the cached result. Rate-limit the bound warning, as `logRateLimited` does in the queue handler.
  - Regression test: Given change control on, a Batch Control strategy, an authenticator configured, and a counting test authenticator; When an administrator loads 10 pages; Then the authenticator is called no more than once per job per refresh period.

- [S-21-07] `security/SystemBuildCheck.java:81-92, 123-139`: side effects and the execution context of the probe.
  - Confirmed harmless: `new Queue.WaitingItem(...)` does not touch the queue (`Queue.Item` constructor: fields and `addAction` only; `FutureImpl(Task)` only stores the task). No `QueueListener`, `QueueTaskDispatcher` or `QueueDecisionHandler` fires, so no Batch Control record is written. `CauseAction`/`UserIdCause(String)` do no lookup. `User.get(PROBE_USER, false, ...)` in authorize-project does not create a user.
  - Side effect 1: each probe consumes a queue id through `QueueIdStrategy.get().generateIdFor(...)`. This is a public extension point; the default increments the counter that `Queue` persists. That is up to about 1,000 ids per detail GET (S-21-03). A third-party `QueueIdStrategy` may do more than count.
  - Side effect 2: the probes of the monitor path run inside `ACL.as2(ACL.SYSTEM2)` (line 123), but the reason comment covers only "a read-only walk of item names". Third-party authenticators therefore execute as SYSTEM. On the detail page's job-scope path (`GrantRequestItem.java:172`) the same probe runs as the viewer. An authenticator that consults the current authentication would answer differently on the two paths.
  - A slow authenticator stalls only the rendering thread (no lock held), and there is no timeout.
  - Fix direction: collect the jobs under SYSTEM2, close the context, and then probe in one fixed context (for example `ACL.as2(Jenkins.ANONYMOUS2)` or SYSTEM2 on both paths, stated in the comment). Extend the SYSTEM2 reason comment to say that third-party authenticators run inside it. With S-21-03's cache, the queue-id consumption becomes negligible. Document it in the class Javadoc.
  - Regression test: Given a test `QueueItemAuthenticator` that records `Jenkins.getAuthentication2()` at each call; When the monitor and the job-scope detail page are rendered; Then both record the same identity.

## INFO
- [S-21-08] `security/GrantAwareACL.java:168-172` (CLI) and `:402-413` (Rename notice): neither message confirms that an item or name exists to a user who cannot see it.
  - CLI: core's `CopyJobCommand.run`/`CreateJobCommand.run` do their own "already exists" check first, under the caller's ACL, which is core behaviour and unchanged. The Create check is reached only after that. `Decision.explain()` is built from the caller's own argument, the target group (the scope of the caller's own grant) and the caller's own grant id and pattern. None of these depend on whether some other item exists.
  - The refusal is recorded (line 158) before the throw. The `IllegalStateException` thrown from `hasPermission2` fails closed, and it is thrown only for `Item.CREATE`, for the current user, under the `cli:` operation (whose context `CliCreateContext` binds to user and folder, S-13).
  - Rename notice: it is sent only on `checkNewName`, only when the field holds the current name, only to the holder of the creating grant, and only as a warning. Nothing is conferred or refused by it, and it repeats the holder's own pattern.
  - The existing observation stands that throwing from `hasPermission2` is fragile for a plugin that calls `hasPermission(Item.CREATE)` expecting a boolean during `create-job`/`copy-job`. It fails closed, so no action is needed.

- [S-21-09] `queue/ApprovalQueueDecisionHandler.java:161, 507-521`: D-51 coverage gaps. These are not security findings; they are for spec-guardian/core-dev.
  - SPEC line 107 lists Retry, Rebuild and Replay. A refused Replay still uses `recordTriggerBlocked`: hourly, per job, no user in the key.
  - `sourceBuild` reads only naginator's cause. A refused Rebuild records no re-run build, and all Rebuilds of one job by one user within a minute merge, whereas SPEC says the record names "the re-run build".
