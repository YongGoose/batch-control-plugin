## FAIL details

### EX-01 — Low — A stale "change approvers" submit says "Correct the fields marked below", but no field is marked and the real reason is not given
- Steps:
  1. As `requester`, file a run request on `fresh-daily` designating approver-1 and approver-2, and keep its page open.
  2. In another browser session, as `approver-1`, reject (or approve) it.
  3. Back on the requester's page, untick approver-2 in "Change approvers" and submit.
- The same happens for a grant request (X1c-grants-*) and for an activation/hold request (X1c-activations-*).
- Expected: a plain statement like the ones the other stale actions give, for example "Request … is REJECTED; the approvers can only be changed while it is PENDING." (Cancel says "… is EXECUTED; only PENDING requests can be cancelled.")
- Actual: HTTP 400. The only message is the generic banner "Nothing was submitted. Correct the fields marked below and submit again; what you entered has been kept." No field is marked, and the change-approvers form is gone from the page because the request is no longer pending. So the user is told to correct fields that do not exist, and "what you entered has been kept" is not true either. The Status row (REJECTED/EXECUTED) further down is the only clue. Nothing was changed on the server (the designation is kept), so this is a message defect, not a state defect.
- Screenshot: X1b-01-stale-change-approvers-full (banner and details table boxed), X1-06-requester-stale-change-approvers.

## Documentation defects
- **DD-07 — README "Configuration §1", the Approvers row** ("The user IDs allowed to be designated as an approver") does not say what D-53 does: an id that names no Jenkins user and that the realm does not resolve is refused. If the realm cannot be asked (a directory outage), the id is accepted with a warning. An administrator of an LDAP or AD instance needs both halves, and especially the second, because a typo saved during an outage is accepted. This is not a blocker: the on-screen messages are clear.

The README procedure itself (install, matrix strategy, the five permissions, `/batch-control-configuration/`) worked unchanged with the LDAP realm and group entries. Nothing in it assumes the Jenkins user database.

## UX observations (for human judgement)
- UX-1 The configuration page's error banner repeats itself: "Nothing was saved. Approvers: 'nosuch-e2e05' is not a known Jenkins user. … Nothing was saved." The inline message under the field, shown while typing and before any save, also ends with "Nothing was saved." (T-dark-admin-config-invalid-submit-main, L-01-validate-unknown-inline).
- UX-2 The unknown-id message says "is not a known Jenkins user" under LDAP too. It is correct (neither Jenkins nor the directory knows the id), but "not known to Jenkins or the security realm" would say what was asked.
- UX-3 A Back-and-resubmit, or two parallel submits (D-07), of a run or grant request files a second identical PENDING request, and the approver gets two mails. It is harmless for safety, because each needs its own decision, but an approver may approve both and start two runs with the same parameters and reason. A per-requester "identical pending request exists" notice, or a one-time form token, would prevent it. The browser's own double click sends only one POST.
- UX-4 After Back, the grant form comes back half restored: the action checkbox ticked, the reason and approvers empty (B3-01). The run-request form comes back fully empty (B1-01). Either is fine, but the half-restored state is easy to submit without noticing a missing field. The validation then catches it.
- UX-5 The approver checkboxes offer every listed id, including one who holds no Approve (`lnobody`) and one the directory does not know (`lnever-seen-2`, saved through the outage warning). A request designating only such ids waits until it expires. This is allowed by SPEC item 3 and was seen for `approver-disc` in e2e-04 UX-1. With an external realm, the list goes stale more easily (people leave groups).
- UX-6 With the directory down, the approver check takes about 3 s, so the warning appears only after a pause. An administrator who saves at once sees no warning at all before saving. Reopening the configuration page shows the warning again for the stored id.
- UX-7 In the light theme, the core `jenkins-label--tertiary` label ("no grant" in Change Records) is 2.43:1, which is hard to read. The dark theme is better at 4.05:1. The label is core's, but the plugin chose to use it for information that matters in an audit ("made without an active grant").
- UX-8 Change-record diffs have no +/- colouring in either theme. That is theme-proof, but on a long diff it is harder to see what changed than in core's or jobConfigHistory's diff views.
- UX-9 The two JCasC applies (to the LDAP profile and back) changed the approver list and wrote no `CONFIG_CHANGE` record. Only the three saves made on the configuration page are recorded. README promises a record for a save "whichever page it was saved from", and JCasC is not a page, so this is not a contradiction. But an approver-list change made through configuration as code leaves no trace in Batch Control's own history.

## Not observed
- A user-level theme choice (the user's own Appearance page) and the "Dark (System)" variant. Only the global **Dark** setting was checked. The theme is applied by CSS variables, so the result should be the same, but it was not captured.
- Other roles in the dark theme (approver-1, auditor, manager). Only admin and requester were asked for. Admin saw every screen, including the Decision section as a designated approver.
- LDAP with `memberOf`-based group membership, nested groups, a manager DN with restricted search rights, LDAP caching (the profile has no cache, so an outage is seen at once), and Active Directory. Only a flat `groupOfNames` directory was used.
- An LDAP user who is renamed or removed from `bc-approvers` while a request designating them is pending. Approve is re-checked at decision (SPEC item 3), but this pass did not remove anyone from a group.
- Mail for EXPIRED / CANCELLED to LDAP addresses. Only REQUEST_CREATED, APPROVED and GRANT_EXPIRING were read. The pending LDAP requests of L-10 expire after this report, 1 hour after creation.
- The Back button after a **rejection**, and Back after a cancel. The approve paths were covered; reject and cancel use the same stale handling as X-01/X-03.
- The Back button with the browser's back-forward cache serving the old page without a reload. Chrome re-fetched each page in these runs (the pages are not bfcache-eligible), so a stale form was never shown from the cache. X-01..X-06 cover what happens if it were.
