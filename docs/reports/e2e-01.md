## FAIL detail

### E2E-D1 (T-E2E-03) — an active CONFIGURE grant does not open the job configuration screen

**Severity: high.** This breaks the acceptance criterion of SPEC item 8 for the
path a human actually takes ("승인되면 그 시간 동안 본인 계정으로 직접 작업하며").
The integration tests miss it because they assert on `hasPermission(Item.CONFIGURE)`
or on the `config.xml` POST, both of which pass.

Reproduction (`e2e/scripts/rest-grant-configure.sh`):

1. `requester` has no `Job/Configure`. `GET /job/batch-daily/configure` -> **403** (correct baseline).
2. `requester` POSTs `/batch-control/grants/create` with `scopeType=JOB`,
   `scopeFullName=batch-daily`, `actions=CONFIGURE`, `durationMinutes=1` -> **302**.
3. `approver` POSTs `/batch-control/grants/<id>/approve` -> **302**. The grant is now active.
4. `GET /job/batch-daily/configure` as `requester` -> **403**
   `requester is missing the Job/Configure permission`  <- **expected 200**
5. `POST /job/batch-daily/config.xml` as `requester` -> **200**, the change is
   applied and recorded (`changes.csv`:
   `20260926-140503-ds891c,CONFIGURE,batch-daily,requester,...,20260926-140503-cz7hy3,` —
   the `grantId` column is correctly linked).
6. `GET /job/batch-daily/config.xml` as `requester` -> **403** as well.

Expected: inside the window the requester can open and save the job
configuration. Actual: only the raw `config.xml` POST works; every read path of
the configuration UI is refused, so a browser user cannot use the grant at all.

**The browser pass makes this worse than the HTTP evidence suggested**
(`e2e/screenshots/T-E2E-03.jpg`): inside the window the job sidebar **does show
the "Configure" link** — correctly, because `Item.CONFIGURE` is true for the
requester under the grant — and clicking it lands on
"requester is missing the Job/Configure permission". The product therefore
advertises a permission on one code path and denies it on another, and hands the
user a dead link at exactly the moment the feature is supposed to work. Any fix
has to make the two agree, not just unblock the page.

Follow-up already in flight: test-author committed the failing regression suite
`GrantConfigureAccessTest` (matrix rows T-08-14..18) in `2fd36e4`, covering the
window's read paths. Those tests are expected to stay red until the
`GrantAwareACL` fix lands.

**Root cause, confirmed on the running instance** (admin script console,
`e2e/out/probe2.groovy` / `probe3.groovy`):

```
hasActiveGrant(requester, batch-pipeline, Item.CONFIGURE) = true
as requester: batch-pipeline ACL=GrantAwareACL CONFIGURE=true EXTENDED_READ=false READ=true
Item.EXTENDED_READ.enabled  = false
Item.EXTENDED_READ.impliedBy = Permission[interface hudson.model.Item,Configure]
checkPermission(EXTENDED_READ) threw: AccessDeniedException3: requester is missing the Job/Configure permission
checkPermission(CONFIGURE): OK
```

`Item.EXTENDED_READ` is disabled by default in core, so core resolves a check
for it through its `impliedBy` chain (and reports the failure under the name of
the implying permission, which is why the 403 says "Job/Configure" and hid the
real cause). That resolution happens **inside the delegate's `SidACL`**, where
the grant is invisible: `GrantAwareACL.hasPermission2` only consults
`GrantService` when `GrantAction.fromPermission(permission) != null`, which is
true for the three literal grantable permissions and false for everything
implied by them. The configuration screen and `GET config.xml` check
`Item.EXTENDED_READ`, so they never reach the grant.

Suggested direction (not applied — `src/main` is not this agent's path): in
`GrantAwareACL.hasPermission2`, walk the `impliedBy` chain the way core does —
for `p = permission; p != null; p = p.impliedBy`, skip disabled permissions and
consult the grant whenever `GrantAction.fromPermission(p) != null`. A regression
test should assert `job.hasPermission(Item.EXTENDED_READ)` under an active
CONFIGURE grant, and an HTTP-level test should assert `GET /job/<name>/configure`
is 200 inside the window.

### E2E-D4 (browser pass) — the "Enable run control" label and its description collide

**Severity: low (cosmetic), but it is the first field of the plugin's own
configuration screen.** Found in V-14, evidence
`e2e/screenshots/global-config-label-collision.png` (zoomed).

The checkbox renders as one run-together string with no separator:

```
Enable run controlWhen enabled, protected jobs require an approved run request before they can run.
```

Cause, confirmed in the source:
`src/main/resources/io/jenkins/plugins/batchcontrol/config/BatchControlGlobalConfiguration/config.jelly:6`
puts `<f:description>` inside the `<f:entry>` as a *sibling* of `<f:checkbox>`;
for a checkbox the description has to hang off the checkbox itself, so it is laid
out on the same line as the title. It is also the only `<f:description>` in the
file — the other nine fields rely solely on their `?` help icon (and
`help-runControlEnabled.html` exists for this field too), so the screen is
inconsistent as well as broken. Routed to ui-dev below.

## Documentation defects

1. **`README.md` is the development-kit README, not the plugin's.** It describes
   the agent kit ("빈 디렉터리를 만들고 이 키트의 내용을 그대로 복사합니다") and
   contains no installation or configuration procedure, so the instruction to
   "follow README and verify the document is right" could not be executed —
   there is nothing to follow. It is also in Korean, against the English-artifact
   rule for repository output.
2. **Nothing documents that JIT change control needs the plugin's authorization
   strategy to be selected.** With Matrix Authorization left as the strategy,
   every grant is approved and then has no effect whatsoever; the only statement
   of this requirement lives in a Javadoc comment and in
   `docs/ARCHITECTURE.md` section 4. An administrator following the (missing)
   setup documentation would conclude the feature is broken. This needs a
   "Setup" section: install, enable the switches, select
   `Batch Control (wrapping)` with the real strategy as delegate, assign the five
   permissions.
3. **Dependencies for a working installation are undocumented.** The `.hpi`
   manifest requires only `structs` and `cloudbees-folder`, but the five
   permissions cannot be assigned at all without a matrix/role-style
   authorization strategy (`matrix-auth` here). Worth stating, together with the
   `RoleStrategyNoticeMonitor` limitation.
4. **SPEC item 8 does not say what a user sees when the window has expired.**
   T-E2E-06 expects an expiry notice and a re-request link, which is a
   reasonable product decision but is not in the SPEC acceptance criteria. Either
   the SPEC gains that criterion (and E2E-D2 is a real defect) or the matrix row
   is relaxed. This is a human decision, not an agent one.

* **UX-1: two sidebar entries labelled "Request Run" that go to different
  places.** On a controlled job the requester sees the plugin's "Request Run"
  action *and* core's build link, which `RequestRunUiDecorator` relabels to the

## Environment notes worth keeping

Two traps cost time here and are recorded in the environment files so they are
not rediscovered:

1. **Do not bind-mount the `.hpi` into `/var/jenkins_home/plugins/`.** Docker
   creates the parent directory as `root`, and Jenkins (running as `jenkins`)
   then aborts the whole init reactor:
   `SEVERE Failed Inspecting plugin /var/jenkins_home/plugins/batch-control.jpi`
   / `java.nio.file.AccessDeniedException: /var/jenkins_home/plugins/batch-control`,
   which also cascades into a misleading
   `ClassNotFoundException: …BatchControlGlobalConfiguration` from the init
   scripts (no plugin was started, so the uber class loader had nothing). The
   mount target is `/usr/share/jenkins/ref/plugins/batch-control.jpi.override`
   instead; the `.override` suffix makes `jenkins.sh` copy it over an existing
   plugin on every boot.
2. **A trigger added programmatically never fires until it is started.**
   `job.addTrigger(new TimerTrigger('* * * * *')); job.save()` leaves the trigger
   registered but dead (`builds: []` forever). `timer.start(job, true)` after the
   save fixes it.
3. **Rewriting `<description>` in a job's `config.xml` must be anchored to the
   first match.** `rest-grant-configure.sh` edited the description to prove that
   a save under a grant takes effect, with an unanchored
   `sed s#<description>…#`. A job's `config.xml` contains one description per
   parameter as well, so the substitution overwrote `batch-daily`'s job
   description *and* both parameter descriptions with
   "Changed by requester under grant …". That is worse than untidy: the parameter
   descriptions are part of what an approver reads on the decision screen, so the
   pollution distorts exactly the judgement V-04 has to make. The orchestrator
   restored them by hand as admin (job: "Daily batch job for the nightly data
   load.", `DATE`: "Target business date (YYYY-MM-DD).", `MODE`: "full = reload
   everything, partial = deltas only."), and the script now uses
   `sed -i "0,/<description>…/s#…#"` so only the job's own description is
   touched. Verified on a three-description fixture.

## 요청: src/main/java/io/jenkins/plugins/batchcontrol/security/GrantAwareACL.java (core-dev)

E2E-D1. `hasPermission2` consults `GrantService` only when
`GrantAction.fromPermission(permission) != null`, so permissions *implied by*
`Item.CONFIGURE`/`CREATE`/`DELETE` are never granted. Because `Item.EXTENDED_READ`
is disabled in core and is resolved through its `impliedBy` chain inside the
delegate's `SidACL`, the job configuration screen and `GET config.xml` are 403
for a user holding an active CONFIGURE grant, while `POST config.xml` succeeds.
Suggested fix: walk the `impliedBy` chain (skipping disabled permissions) and
consult the grant for each grantable permission on the way up. Evidence and
reproduction are in the FAIL detail above.
