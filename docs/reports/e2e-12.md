## How the check was made (scripted, not ad hoc)

1. **Crawl** (`r12/crawl.py`, `run_crawl.sh`): for each of the 6 roles x 2 job UIs, BFS from 35 entry points plus every
   seeded detail page, following every Batch Control link (2 pages per URL pattern). On every page it records the
   status, JS console errors and failed sub-requests. For every control in the main panel, side panel and
   breadcrumbs it does the following. Links are fetched in the same browser context (status after redirects).
   For POST forms, the action is probed with GET (405 expected, 404 = dead). Anchors without an `href` are flagged.
   Every non-submit button, dialog opener and confirmation link is clicked on a fresh load and classified: dialog
   (closed with Escape, reopened, closed with Cancel), navigation, menu, DOM change, or **nothing**.
   785 page loads and 15,018 control checks.
2. **State-changing controls** (`r12/actions.py`): for run request, reqonly's run request, activation, hold, grant
   request, window and incident, a fresh item is made per control. The detail page's visible POST controls are
   listed per role, and each one is clicked on its own fresh item. Confirmation links are tested in order:
   Cancel (server state must not change), Escape, then OK. The State row is compared before and after, and so is
   the server's view.
3. **Entry points** (`r12/jobui.py`): every visible Batch Control entry on job, folder, multibranch, view and build
   pages (new page: app bar and "More actions" menu; classic: side panel) is clicked. Dialogs: Escape, Cancel, the
   X button, an empty submit (it must stay in the dialog with field errors), Enter in a text field, then a full
   submit that must land on the new item's detail page (server 200). Navigating entries: landing status, and every
   link on the landing page.
4. **Targeted**: `misc.py` (C configuration, H history/filters/CSV, P paging, B breadcrumbs and menu, T tab badges,
   R refusal pages, M Mark as reviewed and Request again, K dark theme). `errpages.py` (pages re-rendered after a
   refused submit). `helpcheck*.py` (all help "?" buttons). `s_incident.py`, `s_listpager.py`, `s_monitor.py`.

## Defects

**DEF-07 (low-medium): the History Filter, Changes Show and Incidents Show forms put the CSRF crumb and a `json`
blob into the URL.**
Steps: as approver-1, open `/jenkins/batch-control/history/?kind=runs`, type `fast` in Job, press **Filter** (the
same happens with **Show** on `/batch-control/changes/` and `/batch-control/incidents/`).
Expected: a clean bookmarkable URL such as `?kind=runs&from=...&to=...&job=fast`.
Actual: `/batch-control/history/?kind=runs&from=2026-09-05&to=2026-10-04&job=fast&user=&result=&status=&Jenkins-Crumb=d218edbf...&json=%7B%22kind%22...%22Jenkins-Crumb%22%3A%22d218edbf...%22%7D`.
The page still works, but the session's crumb now sits in the address bar, the browser history, bookmarks,
every proxy or access log, and the Referer of the next request. A user who shares the URL hands out the crumb.
Cause: core's `hudson-behavior.js` adds the crumb and the `json` field to every `<form>`. `RequestItem/index.jelly`
(lines 164-173) already documents this and uses links for its own selector, but these three GET forms remain.
Suspected owner: ui-dev, `src/main/resources/io/jenkins/plugins/batchcontrol/action/HistorySection/index.jelly`
(line 14), `ChangesSection/index.jelly` (line 13), `IncidentsSection/index.jelly` (line 13). Options: drop the
`Jenkins-Crumb`/`json` inputs before submit (a small adjunct), or build the query in JS and navigate.

## Known, core or third-party (not Batch Control defects)

1. **Direct Build (needs approval) on a parameterless approval-required job** (`ops/job-a`, `team/sub/deep-job`,
   `side/job-b`, both UIs, every role with Build) answers only with core's toast "Failed to schedule build.
   Reload the page and try again." (POST 400). This is documented in `docs/LIMITATIONS.md` (around line 590). It
   is still the least helpful message in the product: the user is not told that Request Run is the way.
2. **"More actions" on a job with no completed build** throws core's `TypeError ... reading 'startsWith'`
   (rebuild's "Rebuild Last" with a null URL, LIMITATIONS 45, e2e-11 UX 1). Seen on `ops/job-a`, `deep-job`, `job-b`.
3. **Rebuild Last on a parameterless job, new job page** (`batch-cron`): the menu item GETs
   `/lastCompletedBuild/rebuild/` and lands on core's "This URL requires POST" (405). The rebuild plugin's
   menu entry should POST. On the classic side panel the same entry works ("Done.").
4. Core links that answer 4xx to a GET by design: list view "Schedule a Build" (405), `toggleCollapse` (404 on GET),
   Workspace before the first build (404). The classic parameterized build link lands on core's parameters page,
   which core serves with status 405.
5. Core's admin-monitor **Dismiss** button disables the Batch Control strategy monitor for good, until
   `AdministrativeMonitor#disable(false)`. That is core behaviour, but once dismissed the "Install the Batch
   Control variant" control is gone too, and the instance shows only the second monitor's "Review authorization
   strategy" with no install path. Consider whether this monitor should refuse dismissal while
   `strategyUnsupported` holds (as security monitors do).

## UX observations (for human judgement)

1. **Pager labels differ**: list pages say **Previous/Next**, while History and Changes say **Newer/Older**.
   Both work. Choose one pair.
2. **Mixed refusal codes for sections**: a user without access gets 403 on `/batch-control/history/` and
   `/grants/<id>` (requester, reqonly) but 404 on detail pages of other kinds (activation detail for reqonly) and
   on the whole tree for nobc. This is consistent with "no Batch Control permission → the URL space does not
   exist". Mentioned only because a crawl makes it visible.
3. **Request again** opens with reason and approvers blank. The dialog says why, but a returning user may expect
   the previous approvers to be ticked.
4. **Expired pending requests disappear from the lists after `pendingTimeoutHours`** (1 h here). During this run the
   seeded pending items expired mid-way. This is correct behaviour, but the overview gives no hint that items
   expired since the last visit.
