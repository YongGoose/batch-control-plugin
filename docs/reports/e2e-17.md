## FAIL details

**F-1 D-75 (1) not implemented (R17-07, `r17-visibility`, shards 1 and `cifs`).** This is not a new finding: it is the
pending fix behind the red T-SEC-96/97. The gate run on bd449cd (`scratchpad/g21-bd449cd.log`) had 1018 tests and 3
failures: T-SEC-96, T-SEC-97 and T-SEC-100.

- *Reproduction:* `BC_UNITS=r17-s39 e2e/ci/run.sh 1/1`, step `r17-visibility`, or by hand:
  1. Window holder w17 has an approved CONFIGURE window on `r17/vis-x`.
  2. admin moves `r17/vis-x` into folder `r17-vault`. That folder has a matrix property with
     `NonInheritingStrategy` and no entries, so only administrators can read it.
  3. w17 opens `/batch-control/grants/` and `/batch-control/grants/<id>/`, and approver-1 opens the same page.
- *Expected (D-75 (1), SPEC 8 line 171, LIMITATIONS 11):* neither w17 nor approver-1 sees `r17-vault`. They see
  `r17/vis-x` with a fixed "moved" note.
- *Actual:* both see `Freestyle project r17-vault/vis-x` on the window page, and w17 also sees it in the Active row.
- *Screenshots:* `out/1/driver/screenshots/run-17/R17-H-holder-detail.png`, `R17-H-approver-detail.png`,
  `R17-H-holder-list.png`.
- `src/main` has no such note or check (`GrantRequestItem#getScope` returns the followed scope to every viewer).
- The precondition and the administrator control passed.

**F-2 DEF-E17-01 (LOW, correctness; owner core-dev): after a restart, a new item under another letter case ends a
window whose item still exists (R17-12, `r17-case`, shard 5).**

- *Reproduction* (shard 5 step `r17-case`, after `r17-disk` restarted Jenkins; the same by hand on any Jenkins with a
  folder created before the last restart):
  1. w17 holds an approved CONFIGURE window on `r17/ctl` (200 on its configure page).
  2. admin opens `/job/r17/newJob`, enters `CTL`, chooses Freestyle project and presses OK.
- *Expected:* `r17/ctl` still exists, so the window is still about it. It stays open and confers Configure on `r17/ctl`.
  LIMITATIONS 11 ends a window on a creation only "since its own item must have disappeared without a deletion event".
- *Actual:*
  - Core creates `r17/CTL` next to `r17/ctl`. The folder lists `CTL, ctl, dc-job, ...`.
  - The window ends, revoked by admin with "its item was deleted". The record says "Grant f4d9a211-... for user 'w17'
    (ITEM:r17/ctl) ended: 'r17/CTL' is now the name of a new item".
  - w17 gets 403 on `r17/ctl`, and the Ended list says "Revoked (its item was deleted) by admin", which is not true.
- *Screenshots:* `out/5/driver/screenshots/run-17/R17-C-1-new-item.png`, `R17-C-case-list.png`. Rows:
  `out/5/driver/r17/out/disk.jsonl` (sec C).
- *Cause (observed):*
  - The folders plugin loads a folder's children into a case-sensitive map. It creates them case-insensitively, but
    loads them case-sensitively at startup and on reload. In the dev stack after a restart,
    `getItem('r17').@items.comparator()` was `null`, `getItemByFullName('r17/CTL')` was `null` while `r17/ctl` existed,
    and the top level stayed case-insensitive.
  - So core lets a case variant be created, and then a case-only rename inside a folder succeeds too (R17-05 note).
  - `GrantService.endWindowsOnNewItem` and the first step of `followItem` compare names with
    `String.CASE_INSENSITIVE_ORDER` (S-39-02 fix (4)). The javadoc of `sameName` says "core keeps the items of
    `Jenkins` and of folders in case-insensitive maps", which does not hold for folders after a restart.
  - The same mechanism makes a rename onto a case variant end an unrelated window with "it could not follow its item"
    (analysis, same code path as R17-08).
  - The D-35c records (`forgetStaleCreatedItem`, `relocateCreatedItem`) use the same comparison (analysis).
- *Impact:*
  - No permission is gained: the behaviour is fail-closed. An approved window is lost, and its holder sees a false
    reason and has to request it again.
  - It needs a user with standing Create or an administrator to create or rename an item whose name differs from the
    windowed one only in letter case, in the same folder, after a restart. It can be steered against someone else's
    window.
- *Fix direction (for core-dev, not applied):* end a window on a creation or rename only when the window's own item
  (exact full name, looked up as SYSTEM) no longer exists, or is the created or renamed object itself. Otherwise
  compare names the way the parent actually looks them up, for example `parent.getItem(windowName) == newItem`.

## UX observations (for human judgement; nothing was changed)

1. **"Revoked (it could not follow its item) by admin" does not tell the holder what happened.** The specifics are only
   in the GRANT_REVOKE record, which needs ViewHistory: "'R17-GONE' is now the name of another item" or "its file could
   not be updated to its item's new name". The Ended row offers "Request again", which pre-fills the old name. In
   R17-08 that name no longer exists; in R17-09 the item is now `nf-b`. The pre-filled form was not opened in this run.
   `R17-G-notfollowed-list`, `R17-F-notfollowed-list`.
2. **Startup ends name SYSTEM:** "Revoked (its item was deleted) by SYSTEM" and "Revoked (its state could not be
   confirmed at startup) by SYSTEM". The reason is clear, and "Request again" is the obvious next step. For holders,
   "SYSTEM" may read like an account. The Ended time is the restart time. `R17-B-startup-list`, `R17-U-unconfirmed-list`.
3. **DEF-E17-01's wording:** "its item was deleted" is shown although the item exists. Beyond the defect itself, the
   holder has no way to tell.
4. **The 404 page for a malformed or aliased id** is core's "Not Found: This page may not exist, or you may not have
   permission to see it". It is the same for every role and every shape, and tells nothing about the record. Good.
   `R17-P-*-values-404`.
5. **Pending Run Requests are listed oldest first with paging.** On a busy instance (the seeded one has 57 pending
   requests), a request just submitted is on the last page of Pending. The submit lands on the request's own page, so
   this matters only when someone looks for it in the list. Default sort order, for the owner.
6. **Raw enum values** (UX-4/UX-5, deferred): see the list above. `ITEM:` still appears in the GRANT_REVOKE details on
   Changes and History, for example "Grant ... for user 'w17' (ITEM:r17/ctl) ended: ...", and in the new "not followed"
   and "revoked: its state could not be confirmed at startup" details.
