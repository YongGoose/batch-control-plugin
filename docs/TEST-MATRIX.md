# 테스트 매트릭스

test-author가 소유한다. Phase 2에서 SPEC의 모든 수용 기준을 행으로 옮기고, red-team 시나리오를 병합한다.

## 형식

| ID | SPEC | 계층 | 우선순위 | Given | When | Then | 테스트 파일 |
|---|---|---|---|---|---|---|---|

- ID: `T-<SPEC번호>-<일련>` (예: T-06-03). red-team 출신은 `T-RT-<일련>`. 전역 설정(5절)은 `T-CFG-*`, 비기능 보안(6절)·교차 보안은 `T-SEC-*`, 브라우저 E2E는 `T-E2E-*`, 소유자가 직접 제시한 운영 시나리오(S-1..S-6) 출신은 `T-OS-<일련>` (note 32).
- 계층: `unit`(Jenkins 불필요) / `integration`(JenkinsRule) / `e2e`(브라우저·REST, Phase 5)
- 우선순위: P0(릴리스 차단) / P1(릴리스 전 수정) / P2(다음 릴리스)
- 차단 단언 공통 기준: 큐 비어 있음 + `getNextBuildNumber()` 불변 + `waitUntilNoActivity()` 후 빌드 없음.

## 비고 (전제와 요청 사항)

1. **Clock 주입 API 필요.** T-07-01/03/04, T-08-03/07/12, T-12-02는 시간 경과를 실제 대기 없이 검증해야 한다(`Thread.sleep` 금지). SPEC의 "타이머 의존 없음, 검사 시점 시각 비교" 문장을 근거로, 플러그인이 `java.time.Clock`을 주입받고 테스트에서 고정/이동 가능한 교체 진입점을 제공한다고 전제한다. → 요청: core-dev에 테스트용 Clock 교체 API.
2. **PeriodicWork 수동 트리거.** 만료 판정(ExpiryPeriodicWork)·보관 정리(RetentionPeriodicWork)는 테스트에서 `doRun()` 상당을 직접 호출할 수 있다고 전제한다(1분/1일 주기 대기 불가).
3. **재시작 + 시간 경과 조합**(T-07-04, T-08-07)은 JenkinsSessionRule 두 세션 사이에서 Clock을 미래로 설정할 수 있어야 성립한다(1번 전제의 연장).
4. **cron 발화**(T-06-06/07)는 실제 crontab 대기 대신 TimerTrigger Cause를 실은 스케줄 호출로 발화를 재현한다.
5. **테스트 의존성 필요** (pom.xml은 release-manager 소유): `org.jenkins-ci.plugins:pipeline-build-step` (T-06-05/10/11/12, PoC 보고서에서 기요청), `job-dsl` (T-09-06), `role-strategy` (T-08-08), `cloudbees-folder` (T-08-11, T-09-08), `matrix-auth` (권한 시나리오 전반), `workflow-multibranch` 또는 `branch-api` (T-10-07).
6. **T-06-12 부수 효과**: build 스텝 차단 시 상위 잡이 FAILURE로 끝나는 것은 PoC에서 확인된 Jenkins 동작이며, 이 행은 그 동작을 회귀 고정한다(문서화 대상).
7. **성능 요구**(6절: 하루 5,000 실행 규모에서 최근 7일 조회 2초 이내)는 자동 회귀 매트릭스에서 제외하고 Phase 5에서 로컬 수동 측정으로 확인한다.
8. **T-RT-\* 확정 (R-1~R-8 SPEC 채택 완료).** `T-RT-<nn>`의 `<nn>`은 `docs/reports/red-team-01.md`의 RT 번호와 일치시켰다(추적성). 번호가 비는 곳(04, 08, 09, 12)은 아래 "red-team 시나리오 제외 사유" 절에 있다. 사람이 red-team 제안 R-1~R-8을 전부 SPEC에 채택했다(D-16~D-23으로 SPEC v1.0 수용 기준에 반영됨). 따라서 **모든 T-RT 행의 Then은 이제 현행 SPEC 수용 기준에서 직접 도출된 확정 행이다.** 행 안에 남아 있는 `(SPEC 보강 필요: R-n)` 표기는 채택 이전의 이력 주석이며, 해당 R-n이 D-16~D-23으로 SPEC에 반영되었다는 근거 표시로 읽는다(행 문언은 추적성을 위해 유지). Observed at run time: Jelly's default expression escaping neutralizes `<` (as `&lt;`) and `&` but leaves `>` raw — that is safe (no element can open without a live `<`), so the test accepts both `&lt;script&gt;alert` and `&lt;script>alert` as the escaped form; the no-raw-payload, DOM and alert-handler assertions are unconditional.
28. **P-09 visibility reconciliation audit (Phase 4)**: after the S-01/P-09 visibility model landed, every existing web test was audited against it. NO existing row's Then changed meaning and no fixture needed an extra permission: every actor that reads a request/grant is its requester, its designated approver, a MANAGE/ADMINISTER holder, or holds Item/Read on the target job (e.g. RunRequestWebTest's u2 holds Item/Read everywhere, so T-SEC-02's 403 still isolates the missing Approve permission; GrantWebTest's readers are the requester u1, approver a1, m1 or admin; IncidentTest's rerun caller u1 holds Item/Read; QueueBlockTest's job-page fetches run unsecured or as Request holders). The new visibility rules themselves are covered by T-SEC-08/09 (and S-06/S-07 by T-SEC-10/11).
29. **T-SEC-14 strengthened with a lookup-counting realm (Phase 4, security-02)**: the original row asserted only consistency and post-toggle correctness, which a build with the cache entirely removed would also satisfy. The test now installs a `SecurityRealm` (an `AbstractPasswordBasedSecurityRealm` equivalent to `JenkinsRule.createDummySecurityRealm()`) that increments an `AtomicInteger` on every `loadUserByUsername2`, and measures: (a) the first `isActivated()` does consult the realm (fixture assertion — if it ever stops doing so the row can no longer measure anything and fails loudly rather than silently passing), (b) the second call adds **zero** lookups, (c) after the off/on toggle the next call performs lookups again, (d) and is then cached again. (b) and (c) are the same code path measured with the cache valid and invalid, so the row is falsifiable in both directions. Priority raised P2→P1: this is the /manage page-load DoS against LDAP-backed instances (S-05), not a cosmetic caching detail.
30. **T-SEC-17 fixture route (Phase 4, P-10)**: the empty-scope grant request cannot be produced through the public creation API any more (T-SEC-12 pins that refusal), so the row builds the request with the model factory and writes it to the store directly (`FileStore.saveGrantRequest`) — exactly the "persisted by an older build / hand-edited store file" precondition security-02 S-13c describes. The test asserts the request is loadable and PENDING before approving, so the refusal that follows is the scope re-validation and not a missing record.
31. **Change-window READ paths were uncovered until Phase 5 (T-08-14..18, note for T-08-01 / T-E2E-03)**: SPEC 8 promises that inside an approved window the requester "본인 계정으로 직접 작업"한다 on the target job. The suite asserted only the *write* half of that: T-08-01 (`POST job/X/config.xml` → 200 + persisted), T-09-02/03 (the resulting ChangeRecord and its `grantId`), and the negative rows T-08-02/03/05 (which are denials, so a too-narrow permission answer cannot fail them). Nothing asserted the path a human actually takes — `GET job/X/configure` to open the screen, or `GET job/X/config.xml` to read it. Jenkins core gates **both reads** on `Item.EXTENDED_READ`, a permission core ships **disabled** (`hudson.security.ExtendedReadPermission` off by default) and treats as **implied by** `Item.CONFIGURE`; core's `Job/configure.jelly` layout and `doConfigDotXml`'s GET branch both check it. So an implementation that answers only the exact permission it was asked to confer passes the whole T-08/T-09 block while the change window is unusable in a browser: the user can save a configuration they cannot open. That is what Phase 5 hit against a real Jenkins with 159 green tests. T-08-14/15 pin the two read paths at the HTTP layer, T-08-16 pins the ACL rule itself (`hasPermission(Item.EXTENDED_READ)` must be true inside the window), and T-08-17/18 are the mandatory counterweights — the permission must disappear when the window closes (no permanent leak through the implication walk) and must not widen to another job or to an action the grant does not carry. T-08-16 also carries a **fixture control**: a user holding a plain `Item.CONFIGURE` from the delegate must report `EXTENDED_READ` true, so if core ever stops deriving it the row fails loudly instead of measuring nothing. `GrantConfigureAccessTest` additionally keeps that control as its own method (`directConfigurePermissionOpensAndReadsConfiguration`), which pins that 200 on `configure`/`config.xml` is reachable at all in the resolved Jenkins version — a T-08-14/15 failure is therefore a grant problem, never a broken expectation about core's screens.

32. **Owner scenario rows (`T-OS-*`) and the standing-approval model difference (S-4)**: the `T-OS-<nn>` rows come from six operating scenarios the product owner raised directly (S-1 rejection, S-2 approval↔run traceability, S-3 turning a control on mid-run, S-4 the uncontrolled control group, S-5 configuration change mid-run, S-6 handing a request to another approver) — the same provenance convention as `T-RT-*` for red-team rows, so the owner can trace a row back to the question that produced it. Most of these rows are **coverage confirmation** of behaviour believed to be implemented, not red tests. One model difference must be recorded: the owner described a *standing* approval ("approve once and it keeps running until we put it on hold"), while the current contract binds the approval marker to one requestId and consumes it with a single queue submission (SPEC 6, R-8/D-23) — one approval equals one run, and reuse is blocked (T-RT-02). T-OS-07/08 therefore assert the off→on transition of the control and never that one approval keeps later runs passing. Whether a standing-approval mode should exist is an **owner/SPEC decision**, not a test gap.
33. **S-6 delegation line is out of MVP scope (note for T-OS-10)**: an administrator-configured stand-in/delegation line ("대결") is SPEC item 15 (second release, 순차 결재선), so no test assumes it. The current contract is requester-driven approver change until the decision (SPEC item 3), covered by T-03-04 (change recorded), T-03-05 (no change after the decision) and T-RT-07 (multi-hop audit, superseded approvers refused). T-OS-10 adds the boundary that makes the hand-over safe: an approver on the global list who was never designated on this request cannot decide it.
34. **T-OS-03 asserts the substance of "final", not the wording**: the owner expects the screen to tell the requester that a rejection cannot be resumed. SPEC pins no wording, so the row asserts the rendered REJECTED status, the stored rejection reason visible to the requester, and the absence of an approve path for that request in the page. Confirming the literal wording/visual treatment stays with the Phase 5 e2e pass (same convention as notes 17 and 27).
35. **New API surface used by T-OS-01/02 (`decisionComment`, `decidedAt`)**: the rejection rows read `RunRequest.getDecisionComment()` and `getDecidedAt()`, derived from SPEC section 3's data model (`createdAt, decidedAt, decisionComment`); no earlier test used those two getters. Both were confirmed to exist by compiling the new classes against the plugin's built classes, so the rows are behavioural assertions, not API requests.
36. **In-flight preconditions are gated, not timed (T-OS-05/06/09)**: these rows need a build that is provably running while a setting changes. Each class carries a small test-local `Builder` that blocks on a latch keyed by a persisted gate id (only the id is serialized, so the step survives a job save and the `config.xml` round trip; the latches live in static maps). The gate turns "while running" into an assertion — `isBuilding()` is checked immediately before and after the change — so a timing miss fails loudly instead of passing vacuously, and no `Thread.sleep` is used to wait out a build.

37. **Where D-30's "감사 이력" was read to be, and what SPEC still leaves open (T-06-17/18/19)**: D-30 fixes *that* a blocked marker re-use is recorded and *that* it is queryable on the dashboard and in CSV, but not the record's shape. Derivation used by the rows, from SPEC only: the audit set that SPEC item 12 gives a screen and a CSV export to, and that is neither a run, an incident nor a request, is the change-record set — so the rows read the history through `FileStore.listChangeRecords(YearMonth)` and `batch-control/history/changes.csv`, and require the record to carry a **type of its own** (not one of the eight `ChangeRecord` types SPEC section 3 lists), which is what "별도 레코드" asks for and matches P-04 candidate (a) (`MARKER_REUSE_BLOCKED`-style type). Still undefined in SPEC, and therefore asserted only in substance (text of `target`/`detail`/`diff`, not a field layout): (a) the record's **type name**; (b) which field carries the consumed requestId and the target job — the rows search the record's text rather than naming a field, so any placement passes; (c) whether `ChangeRecord.grantId`/`diff` mean anything here (not asserted); (d) whether a **5th** dataset/CSV endpoint (e.g. `reuse.csv`) would be the intended home instead of `changes.csv` — if core-dev/ui-dev serve it elsewhere, these three rows are adjusted to that endpoint rather than the implementation being wrong about the location; (e) the **actor** attribution: the rows require `user` = the account that replayed the marker (u1's rebuild → u1, u2's revival → u2), reading "누가 시도했는지" as the actor, not the owner of the approval — SPEC does not say this in words. The **falsifiability** of the block hangs on T-06-18: T-06-17 alone is satisfied by an implementation that writes a record on every approved submission, so the clean-run row is mandatory, not decorative. The refusal itself is not re-asserted as a row (T-RT-02 owns it); it appears inside T-06-17/19 only as a fixture control, so the measured record is provably a record of a *blocked* attempt.
