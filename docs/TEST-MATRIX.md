# 테스트 매트릭스

test-author가 소유한다. Phase 2에서 SPEC의 모든 수용 기준을 행으로 옮기고, red-team 시나리오를 병합한다.

## 형식

| ID | SPEC | 계층 | 우선순위 | Given | When | Then | 테스트 파일 |
|---|---|---|---|---|---|---|---|

- ID: `T-<SPEC번호>-<일련>` (예: T-06-03). red-team 출신은 `T-RT-<일련>`. 전역 설정(5절)은 `T-CFG-*`, 비기능 보안(6절)·교차 보안은 `T-SEC-*`, 브라우저 E2E는 `T-E2E-*`, 소유자가 직접 제시한 운영 시나리오(S-1..S-6) 출신은 `T-OS-<일련>` (note 32). Screen contracts that the implementation defined rather than SPEC (no acceptance criterion behind them) are `T-UI-<serial>` (note 40).
- 계층: `unit`(Jenkins 불필요) / `integration`(JenkinsRule) / `e2e`(브라우저·REST, Phase 5)
- 우선순위: P0(릴리스 차단) / P1(릴리스 전 수정) / P2(다음 릴리스)
- 차단 단언 공통 기준: 큐 비어 있음 + `getNextBuildNumber()` 불변 + `waitUntilNoActivity()` 후 빌드 없음.

## 비고 (전제와 요청 사항)

1. **Clock 주입 API 필요.** T-07-01/03/04, T-08-03/07/12, T-12-02는 시간 경과를 실제 대기 없이 검증해야 한다(`Thread.sleep` 금지). SPEC의 "타이머 의존 없음, 검사 시점 시각 비교" 문장을 근거로, 플러그인이 `java.time.Clock`을 주입받고 테스트에서 고정/이동 가능한 교체 진입점을 제공한다고 전제한다. → 요청: core-dev에 테스트용 Clock 교체 API.
2. **PeriodicWork 수동 트리거.** 만료 판정(ExpiryPeriodicWork)·보관 정리(RetentionPeriodicWork)는 테스트에서 `doRun()` 상당을 직접 호출할 수 있다고 전제한다(1분/1일 주기 대기 불가).
3. **재시작 + 시간 경과 조합**(T-07-04, T-08-07)은 JenkinsSessionRule 두 세션 사이에서 Clock을 미래로 설정할 수 있어야 성립한다(1번 전제의 연장).

31. **Change-window READ paths were uncovered until Phase 5 (T-08-14..18, note for T-08-01 / T-E2E-03)**: SPEC 8 promises that inside an approved window the requester "본인 계정으로 직접 작업"한다 on the target job. 42. **D-31 makes fixture ORDER load-bearing: a job created while run control is on already carries a `BatchControlJobProperty`, so a later `addProperty` is silently shadowed.** Jenkins core `Job#addProperty` *appends* a property instead of replacing one of the same class, and `Job#getProperty(Class)` returns the **first** match. So the once-standard fixture — enable run control, create the job, then `addProperty(new BatchControlJobProperty(...))` — now installs a second property that the plugin never reads: `approvalRequired` still looks right (both copies say true), while `blockTimer`, `blockUpstream`, `allowedUpstreamJobs` and `jobApprovers` quietly have no effect and the row measures nothing. The same default also means a job created under run control is **not** an "uncontrolled job" fixture any more. Both traps were hit for real on 2026-09-26 (13 rows: T-06-05/07/12/16, T-RT-01, T-05-06, T-OS-05..09, T-10-01/03) — all fixture rot, no product defect. Fixtures therefore either create the job **before** `setRunControlEnabled(true)`, or go through `BatchControlFixtures` (src/test): `setBatchControl(job, property)` removes any existing copy before adding and then asserts the installed instance is the one `getProperty` returns, and `uncontrolled(job)` strips every copy for a "run control is on but this job is not controlled" premise. Prefer the creation-order variant when the fixture must not produce an extra save of the job (an extra save is an extra `CONFIGURE` record while change control is on — see `OwnerScenarioConfigChangeTest`). **The most valuable find of that repair: two rows were passing while measuring nothing.** `T-06-04` (Replay is blocked) and `T-06-11` (an allow-listed upstream job passes) install their settings the shadowed way, so the plugin read the D-31 default instead — `approvalRequired=true` happened to be the same in both copies, so the row still went green, while the setting the row exists to exercise (`blockUpstream` + `allowedUpstreamJobs`, and "the job was uncontrolled for its first build") had no effect at all. **Green is therefore not evidence that a fixture took effect here:** whenever a row's premise is a job-level setting other than plain `approvalRequired`, assert that the property the plugin reads back is the one the fixture installed — which is what `BatchControlFixtures.setBatchControl` now does for every call site, so the trap cannot reappear silently.
 **Extended by D-34 (note 46):** the property a job created under run control carries now also says `blockTimer=true` and `blockUpstream=true`, so the trap is no longer limited to settings a fixture wanted to *add* — a fixture that creates a job while run control is on and then relies on a **timer or upstream cause passing** measures a blocked job unless it states the switches through `BatchControlFixtures.setBatchControl` (or takes the job out of control with `uncontrolled`). Four fixtures were hardened for this ahead of the implementation: `IncidentTest` t_11_01 (`uncontrolled`), t_11_02 and t_11_06 (stated property), `HistoryWebTest` t_12_04 and `OwnerScenarioApprovalTraceTest` t_os_04. No Then changed — each row keeps measuring what it measured; only the job state it measures on is now stated rather than inherited.

43. **A `<form>` on a read-only screen leaks the crumb into the URL, and core gives no opt-out (T-UI-06)**: while the approval screen's recent-run size control was a `<select>` inside a `<form>`, Jenkins core's own JavaScript added a crumb to **every** form on the page, so choosing a size navigated to `…/?runs=20&Jenkins-Crumb=41855d…&json=%7B…%7D` — reproduced in a browser against a real Jenkins in Phase 5, not inferred. A crumb in a GET query is a CSRF token written into browser history, proxy logs and `Referer` headers, and there is no core flag to suppress the injection, so the fix was structural: ui-dev replaced the form with a group of `<a href="?runs=10">` links (`e98d211`). T-UI-06 therefore pins the **structure and the outcome together** — a plain link per allowed size, a working navigation (HTTP 200 + the chosen window rendered, so a dead link cannot pass), and a landing URL free of `Jenkins-Crumb` and `json=`. Deliberately independent of HtmlUnit: the row does not rely on the test browser reproducing core's injection, because a reverted implementation has no per-size links at all and fails on the first assertion. The property the removed `<select>` used to carry — "the size in effect is visible" — is not dropped with it: the row asserts that exactly one link is marked `aria-current` and that it is the one just followed. Note that no test ever asserted `selected="selected"`, so nothing had to be migrated; the property was only ever covered inside ui-dev's own markup until this row.

44. **P-03 is resolved (owner ruling, Phase 5): the masked-storage behaviour stays, and the limitation it costs is now a pinned acceptance criterion (T-SEC-07, T-SEC-19).** The owner chose option ① of P-03 — a secret parameter's value is masked *before* it is handed to the request store, so no plaintext is persisted anywhere, and the price is that **a job with a secret parameter cannot reproduce the original secret when the approved run executes**. That is an accepted limitation stated in the README, not a defect, and T-SEC-07 asserts it explicitly (the build receives `********`) so that a later "convenience" change which starts persisting a recoverable secret fails the row instead of quietly passing it. The owner's reasoning is worth keeping next to the row: the approver decides by reading the raw parameters on the request screen, and showing secrets in clear there would be the larger problem. **Why the row drives the browser form instead of the service API**: P-03 states the masking happens where the submitted `ParameterValue`s are converted into the stored `Map<String,String>` — the service API receives strings and can no longer tell which of them was sensitive, so a row that called `RunRequestService.create(job, plaintextMap, …)` would be asserting against a layer that has no way to comply. Two consequences follow for anyone adding a new request-creation path later (SPEC item 14's REST API, a CLI command, an automated re-run): the caller must mask before calling, because the store will not do it for them, and such a path needs its own T-SEC-07-shaped row. **Why the row is falsifiable in both directions**: every "no plaintext" assertion has a positive twin on the same surface using a second, non-sensitive parameter of the same job, whose typed value must be present verbatim (stored, rendered, exported, passed to the build) — so "store nothing" fails; the secret parameter's *name* must be present wherever the plain one is — so "drop the secret parameter" fails; and the store scan additionally asserts that the non-sensitive value really is found in a file under `$JENKINS_HOME/batch-control/`, so it cannot pass by scanning an empty or wrong directory. The row also forbids the Password parameter's **definition default** as a second plaintext: Jenkins core renders a concealed password control with the `<DEFAULT>` sentinel rather than the stored value, so the submission either carries the value the test typed or resolves to the definition default, and both are non-empty and both are forbidden — the row therefore cannot be satisfied by an empty submission whichever path core takes. Verified by mutation: submitting a different value for the non-sensitive parameter reddens the row at the "stored verbatim" assertion, which proves the typed values really travel form → store.

45. **T-E2E-06 moved the acceptance criterion to where D-33 puts it, without lowering it, and stays at the e2e layer.** The old row demanded an expiry notice *in the denial screen itself* plus a re-request link there; D-33 rules that screen out (Jenkins core hardcodes the 403 handler in `SecurityRealm#createFilterImpl`, so it is not an extension point, and the work-arounds — overriding core's `accessDenied.jelly` from plugin resources, or filtering 403s in a `PluginServletFilter` — would make this plugin intercept **every** permission denial on the instance, a jenkinsci hosting review rejection). The requirement therefore moves to the grants screen (`/batch-control/grants/`: remaining time of an active window, history of expired windows, re-request link), and the row now checks **both** halves: that the denial screen is core's own and untouched (including no restoration of the values being edited, which D-33 excludes because keeping a change that failed the permission check contradicts change control), and that the guidance is reachable where D-33 puts it. **Layer decision — it stays `e2e`**: half (a) is an assertion about what the plugin does *not* install into an instance-wide screen, which is only meaningfully observed in a browser against a real Jenkins; its automatable core (denial from the first permission check after expiry, no active grant, no leak through implied permissions) is already pinned deterministically by T-08-17/18 in `GrantConfigureAccessTest`, so moving the row to `integration` would duplicate that and add nothing. Half (b) is the content of a plugin screen for which SPEC fixes only the three items D-33 names and no markup; pinning exact markup at the integration layer would freeze a screen contract SPEC does not state (the `T-UI-*` rows exist precisely for contracts the implementation defined, and this one has not been reported yet). If ui-dev reports the grants-screen contract, half (b) should become an integration row (`T-UI-*`) and this row keeps only half (a). **The existing e2e harness already reaches both halves, so only the expectation moves** (e2e/** is e2e-tester's path, so this is a request, not an edit): `e2e/scripts/rest-grant-configure.sh` step 6 currently greps the post-expiry refusal body for `expired` / `grant` / `batch-control/grants` / `Request` / `permission` and treats their absence as the failure — under D-33 that body is core's screen and those needles are *expected* to be absent there, while the same needles belong on `/batch-control/grants/`, which `e2e/scripts/rest-screens-v2.sh` already fetches and already checks for the `Remaining` column. Step 6 should therefore assert core's untouched denial (and that the refused save left the configuration unchanged, which step 5 already prints) and hand the guidance needles to the grants-screen script.
46. **D-34 separates creating a job from operating it, and what SPEC still leaves open (T-08-30..36, the rewrites of T-08-26/27 and T-RT-05)**: D-34 adds `blockTimer=true` and `blockUpstream=true` to the new-job default D-31 established, so that *the act of creating a job starts nothing*. Reading used for the rows, from SPEC item 8 / D-34 only: (1) the default applies to the same set of creations D-31 applies to — every path, every creator, while **run control** is on (hence the same path coverage: New Item form, REST `createItem`, CLI `create-job`, copy, Job DSL seed) — and D-32's computed children stay excluded (T-10-07); (2) the substance is asserted twice, as the stored switches and as the refused cause, because SPEC item 6's queue gate is where a switch becomes observable: T-08-31 for the timer door and T-08-33 for the upstream door; (3) the way out D-34 names ("turn the switch off in the job configuration") is asserted as its own pair of rows — T-08-26/27 — because a control that cannot be released would make every generated job permanently dead; the unlock is expressed through the job property, the same convention T-OS-05/06 use for an administrator flipping a job switch, and the ChangeRecord it produces is SPEC item 9's and is covered by T-09-01/02, so it is not re-asserted here. **Two rows were rewritten rather than relaxed.** T-08-26/27 asserted that a *newly created* job still builds from a timer and from an upstream call — that was the D-31 safety net, and D-34 deliberately reverses it. (b) **The unlock is change-controlled only while change control is on.** D-34 justifies the lock by saying the release "goes through a permission window and a record", but the lock is conditioned on **run** control; with run control on and change control off there is no grant window at all, so anyone holding Item/Configure releases the job freely (the change is still recorded — SPEC item 9 — but not gated).
