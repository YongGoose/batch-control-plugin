# 설계 결정 기록

형식: `D-번호 | 결정 | 이유 | 대안과 기각 사유`. 에이전트는 이 파일을 수정하지 않고, 변경 제안은 맨 아래 "제안" 절에 추가만 한다.

## 확정

**D-01 | 대상은 CI가 아니라 배치 실행 관리** | Jenkins를 Spring Batch 등 배치 실행기로 쓰는 환경이 국내에 많고, 그 영역의 승인·감사 대안이 상용(Control-M 등)뿐이라 빈틈이 명확함. | CI 배포 승인: `input` 스텝, GitHub Environments, ServiceNow와 중복.

**D-02 | 신규 플러그인으로 신청, Job StrongAuthSimple은 입양하지 않음** | 13년 미관리, Jenkins 1.x 코드, Pipeline·감사·JIT 없음. 이어받을 코드가 없음. | 입양: 심사는 쉬우나 실질적 이점 없음. 요청서에 차이점 명시로 대응.

**D-03 | 실행 통제는 큐 진입 차단(QueueDecisionHandler)** | 모든 실행 경로가 큐를 거쳐 한 지점에서 차단 가능. 문서화된 확장 포인트. | Pipeline `input` 스텝 방식: Freestyle 미지원, 잡 실행 자체를 막지 못함.

**D-04 | 결재자는 그룹 정의가 아니라 명시적 사용자 목록 + 요청자가 1명 선택** | LDAP/AD 환경에서 "권한 있는 사용자 전체 목록"을 뽑는 표준 API가 없음. 목록 등재 + 결재 시점 권한 확인으로 이중 검증. | 그룹 기반 자동 목록: 구현 불가능한 환경이 있음. 다단계 결재선: 2차.

**D-05 | 관리자 자가 결재 허용(기본값)** | 관리자는 어차피 우회 가능하므로 막는 대신 기록한다. 직무 분리가 필수인 조직을 위해 옵션으로 끌 수 있게 함. | 관리자도 강제 분리: 소규모 팀 사용성 저하.

**D-06 | 변경 통제는 대행이 아니라 JIT 임시 권한** | 수정·생성은 거부 훅이 없어 대행이 필요했으나, 대행은 권한 상승(SYSTEM 적용 시 스크립트 자동 승인 등) 위험과 초안 폴더·diff 화면 등 복잡도가 큼. JIT는 사용자가 자기 계정으로 직접 작업하므로 기존 안전장치가 그대로 동작. | 대행(초안 폴더): 복잡·위험. 사전 내용 검토는 포기하고 사후 diff 추적으로 보완.

**D-07 | 상태 변경(활성/비활성)은 수정과 한 묶음** | Jenkins 코어에서 enable/disable이 Item/Configure 권한에 묶여 있고 분리 요청(JENKINS-27051)이 미해결. | 별도 행위로 정의: 권한 체계상 불가.

**D-08 | 시간 만료는 검사 시점 시각 비교** | 타이머 불필요, 재시작에 강함, 즉시성 보장. 주기 작업은 상태 갱신·알림용 보조. | 스케줄러로 회수: 재시작·지연 시 취약.

**D-09 | 오류 등록 기본값은 FAILURE + UNSTABLE, ABORTED 제외** | ABORTED는 대부분 의도적 중단이라 노이즈. 대시보드에는 중단자 표시로 충분. 설정으로 추가 가능. | 셋 다 포함: 월말 집계 오염.

**D-10 | 오류 건은 자동 등록, 사람은 처리만** | 수동 등록은 누락을 만들어 월말 집계 신뢰성을 해침. | 수동 등록: 기각.

**D-11 | 저장소는 JENKINS_HOME 파일, 월별 분할** | 의존성 없음, 백업 자동 포함, 심사 무난. 월 단위 조회 요구와 맞음. 저장소 인터페이스를 두어 2차에 외부 DB 구현체 추가. | H2: 드라이버 플러그인 미관리, 파일 호환 이력. 외부 DB 필수: 소규모 팀 진입장벽.

**D-12 | 설치만으로 동작 변경 없음(전역 스위치 기본 off)** | Jenkins 생태계 관례, 심사 기준, cron 배치 중단 사고 방지. | 기본 on: 기각.

**D-13 | 기록은 통제와 독립** | 통제를 끄더라도 감사 기록은 가치가 있음. 어느 스위치든 켜지면 모든 기록 활성. | 스위치별 기록: 기각.

**D-14 | 코드·테스트 작성 세션 분리** | 같은 세션이 코드와 테스트를 짜면 같은 오해를 공유해 잘못된 코드가 통과함. 테스트는 SPEC에서만 도출. | 단일 에이전트: 기각.

**D-15 | 이름 `batch-control`** | 목적(배치 실행 관리)을 드러내 검색성 좋음. CI용 승인과 구분. | ops-approval, job-gatekeeper: 후보였음.

**D-16 | Upstream 정책 명확화 (R-1)** | `blockUpstream=true` + `allowedUpstreamJobs` 빈/미설정 = 모든 상위 잡 차단(빈 목록은 미설정과 동일), 목록 있으면 그 잡만 통과. `blockUpstream=false` = 전부 통과. 빈 목록의 해석 모호성이 red-team RT-01에서 우회 경로로 지적됨. | 빈 목록을 blockUpstream과 무관하게 전부 차단으로 해석: 기본 개방 원칙(D-12)과 기존 잡 호환성 훼손으로 기각.

**D-17 | 권한 창 내 생성 잡은 approvalRequired 기본 true (R-2 경량)** | 실행 통제 on일 때 활성 Grant 안에서 생성된 잡에 자동 적용. 권한 창에 cron 잡을 심어 만료 후 무승인 실행하는 우회(RT-05) 차단. | 권한 창 내 트리거 설정 자체 금지: 정상 업무(배치 잡 생성) 저해로 기각. 완전 방치: 우회 허용으로 기각.

**D-18 | 출력 무해화 수용 기준 명문화 (R-3)** | CSV 셀 `= + - @` 선행 시 `'` 프리픽스, 모든 화면에서 사용자 입력 이스케이프. HOSTING-CHECKLIST 규약을 SPEC 수용 기준으로 승격해 테스트 근거 확보(RT-10/11). | 체크리스트 규약만 유지: 매트릭스 행의 SPEC 근거 부재로 기각.

**D-19 | logTail 마스킹은 비밀 파라미터·Secret 평문 한정 (R-4)** | Incident logTail 저장 시 해당 빌드의 비밀 파라미터 값과 Secret 평문만 마스킹, 그 외 콘솔 노출 비밀은 한계로 문서화(RT-13). | 범용 비밀 패턴 탐지: 오탐·누락 불가피, 잘못된 안전감 유발로 기각.

**D-20 | 상태 전이 원자성 + check-at-submit + idempotency (R-5)** | 요청 상태 전이는 CAS, 동시 승인·승인/취소 경합은 1건만 성립, 큐 투입 직전 만료 재확인, 복구 재투입은 requestId 기반 중복 제거(RT-14~17). | 파일 락 없는 낙관 재작성: 경합 시 상태 파손으로 기각.

**D-21 | 대상 잡 rename/move 시 요청 INVALIDATED (R-6)** | PENDING/APPROVED 요청의 대상 잡이 rename/move되면 INVALIDATED로 종료하고 이력에 남김. 결재자가 검토한 잡과 다른 잡이 실행되는 스왑 공격(RT-03) 차단. | 잡 신원(UUID) 추적으로 계속 유효 유지: 결재 시점과 다른 맥락(경로·상위 폴더 권한)에서 실행될 위험으로 기각.

**D-22 | 크기 상한만 MVP, rate limit은 2차 (R-7 부분)** | 사유 4,000자, 문자열 파라미터 값 개당 10,000자 초과 시 요청 생성 거부(RT-19). 요청 rate limit·PENDING 상한은 2차. | 즉시 rate limit 도입: 정책 튜닝 비용 대비 MVP 가치 낮아 연기.

**D-23 | 승인 마커는 requestId 바인딩 + 1회 소비 (R-8)** | 마커는 요청 ID에 묶이고 큐 투입 1회로 소비, 재사용(재큐·rebuild)은 차단·기록(RT-02/17). | 무상태 마커: 재사용·재큐 공격 허용으로 기각.

**D-24 | 별도의 hold 상태를 두지 않는다 (소유자 결정, Phase 5)** | 잡을 "이제 실행되지 않게" 만드는 수단은 기존 토글(`approvalRequired`, `blockTimer`, 잡 비활성화)로 충분하다. 이 토글 자체가 변경 통제 대상이라 CONFIGURE 권한 창을 거쳐야 바꿀 수 있고 변경 이력에 남으므로, hold를 켜고 끄는 행위도 이미 결재와 기록을 거친다. | 전용 HOLD 상태 + 해제 결재 흐름: 기존 토글과 의미가 겹치고 상태 머신만 늘어나 기각.

**D-25 | 상시 승인으로 전환하지 않는다 — 정기 실행은 이미 통제 대상이 아니다 (소유자 결정, Phase 5)** | "배치 잡은 한 번만 실행되는 게 아니라 계속 실행되어야 한다"는 요구는 이미 충족되어 있다. 1회 소비(D-23)는 **사람이 올린 실행 요청**에만 적용되고, cron 정기 실행은 `blockTimer=true`가 아닌 한 요청·승인 없이 통과한다. 실환경(Jenkins 2.568.3, Docker)에서 `approvalRequired=true`인 잡의 타이머 실행이 관측 창 동안 3회 연속 성공함을 확인했다(nextBuildNumber 94→97, 전부 "Started by timer"). 따라서 새 기능 없이 SPEC 6절 문구를 명확히 하고 동작을 테스트로 고정하는 것으로 종결한다(T-OS-07/08). | ① 승인 마커를 재사용 가능하게 변경: 오래된 승인을 재큐·rebuild로 되살리는 경로가 열려 D-23이 막으려던 문제를 재도입하므로 기각. ② 잡 단위 상시 승인 객체 신설: 정기 실행이 이미 통과하므로 추가 이득이 없고, 끄는 수단도 토글로 이미 존재해 기각(무인 실행만 허용 / 실행 영향 변경 시 무효화 / 무기한+재확인이라는 설계 답변은 필요해질 경우를 위해 P 절에 보존).

**D-26 | 위임 라인(대결)은 MVP 밖, 요청자 주도 결재자 변경만 지원 (소유자 결정, Phase 5)** | 지정 결재자 부재 시 처리는 결재 전까지 요청자가 결재자를 바꾸는 경로 하나로 한다(SPEC 3절). 관리자가 미리 대리 결재선을 설정하는 기능은 넣지 않는다. | 순차 결재선: SPEC 15절(2차 확장)로 유지.

**D-27 | 진행 중인 빌드는 어떤 통제 변경으로도 중단되지 않는다 (소유자 결정, Phase 5)** | 전역 스위치·잡 속성 토글 변경, 대상 잡의 설정 변경, 권한 창 만료 중 어느 것도 이미 실행 중인 빌드에 영향을 주지 않는다. 차단은 큐 진입 단계에서만 일어난다. 지금까지 이 성질은 Jenkins 코어 구조에 의존할 뿐 명세가 약속한 적이 없어, 누가 깨뜨려도 계약 위반이라 말할 근거가 없었다. T-OS-05/06/09가 회귀로 고정한다(래치 기반으로 실제 실행 중 상태를 만들고 변경 전후 `isBuilding()`을 단언해 타이밍을 놓치면 조용히 통과하지 않는다). | 토글 변경만 보장: 운영자가 실제로 겪는 사고는 "야간 배치 도중 설정을 건드려 작업이 날아가는" 쪽이라 범위를 좁힐 이유가 없어 기각.

**D-28 | 반려 사유는 요청자에게 사유·결재자·시각까지 보인다 (소유자 결정, Phase 5)** | 반려된 요청 화면에서 요청자가 무엇을 왜 누가 언제 반려했는지 확인할 수 있다. 구현은 이미 그렇게 동작하고 있었으나 수용 기준이 없어 고정되지 않은 상태였다(T-OS-03). | 사유만 표시: 누가 반려했는지 확인하려 별도 화면을 찾아야 해 기각.

**D-29 | 지정 결재자만 결재할 수 있다 (소유자 결정, Phase 5)** | 결재자 목록에 등재된 다른 사용자도, 관리자도 대신 결재할 수 없다. 부재 시 경로는 D-26(요청자 주도 변경)이다. 문맥상 함의되던 배타성을 명문화한다(T-OS-10). | 관리자 예외 허용: 관리자 계정이 결재선을 우회하는 경로가 생겨 직무 분리가 약해지므로 기각.

**D-30 | 승인 마커 재사용 시도는 감사 이력에 별도 레코드로 남는다 (소유자 결정, Phase 5)** | D-23이 "차단되고 기록된다"고만 하고 기록 위치를 정하지 않아 note 15에 미정의로 남아 있던 항목. 재사용 시도는 감사 이력에 독립 레코드로 적재되어 대시보드·CSV에서 조회된다. 승인된 건을 되살려 돌리려는 시도는 우발적이지 않을 수 있으므로 사람이 볼 수 있는 곳에 쌓여야 한다. | ① 해당 요청 이력에만 기록: 여러 요청에 걸친 반복 시도가 한눈에 보이지 않아 기각. ② 로그만: 운영자가 사실상 보지 못해 기각.

## 제안 (에이전트가 추가, 사람이 판정)

**P-12 | Field layout and trigger set of the `MARKER_REUSE_BLOCKED` record (core-dev, D-30 implementation — implemented, awaiting ratification)** | *What SPEC left open (matrix note 37 (a)(b)(c)(e)) and how it is now filled:* (1) **type name** `MARKER_REUSE_BLOCKED`, the ninth `ChangeType`; (2) **`target` = the job the marker was presented on**, not the job the approval was bound to and not the request id. Reason: `target` is the only `ChangeRecord` field the history screen and CSV filter treat as a job (`HistorySection#getChangeItems` applies `matchesJob(c.getTarget())`), so putting the attempted job there is what makes "which of my jobs is someone trying to replay" answerable with the job filter operators already use for `CREATE`/`CONFIGURE`. For a cross-job replay the *bound* job is the secondary fact and goes into `detail`; (3) **the consumed request id lives in `detail`**, together with the attempted job and the refusal reason, as one comma-free English sentence. Reason: `changes.csv` exports `id,type,target,user,at,grantId,detail` and deliberately omits `diff`, so `detail` is the only free-text column an operator actually receives in the export; keeping it comma-free keeps one CSV cell per column for naive spreadsheet and `cut`-style readers. A dedicated `requestId` column was rejected: it would widen the `ChangeRecord` model (and the JSONL schema, and all four CSV headers) for a single record type, whereas SPEC section 3 keeps `ChangeRecord` to one shape for all types; (4) **`user` = the account that attempted the re-use**, read from `Jenkins.getAuthentication2()` inside the queue gate, which runs on the submitting thread. This is SPEC's own wording for D-30 and is what makes the record actionable — the requester of the original approval is already discoverable from the request itself; (5) **`grantId` and `diff` are meaningless here and stay `null`.** `grantId` links a change to the change-control window that authorized it (SPEC item 8/9); a blocked *run* submission is never authorized by a grant, so a non-null value could only be a coincidental window of the same actor and would read as "this grant permitted the attempt", which is false. `diff` is a before/after configuration patch stored as `changes/diff/<id>.patch`; a refused submission changes no configuration, so a `diff` would create an empty patch file per attempt. *Trigger set (not pinned by SPEC either):* `RunRequestService#consumeMarker` records the record for exactly two of its five refusals — the single submission ticket is already claimed (`queuedAt`/`executedRunId` set, or status `EXECUTED`), and the marker is presented on a job it was not issued for. The `queuedAt` check was moved **above** the status check for this reason: consumption sets `queuedAt` and the started build then moves the request to `EXECUTED`, so before the reorder every real-world replay of an executed approval was attributed to "wrong status" instead of "spent ticket". **P-11 | A grant answers the permissions its action implies, walking `Permission.impliedBy` exactly as Jenkins does (core-dev, Phase 5 browser finding — implemented, awaiting ratification)** | *What:* `GrantAwareACL.hasPermission2` no longer consults `GrantService` only when the checked permission **is** one of the three grantable ones.
