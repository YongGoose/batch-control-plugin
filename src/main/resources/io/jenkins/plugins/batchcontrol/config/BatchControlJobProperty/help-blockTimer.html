If checked, cron (timer) triggered builds of this job are blocked; by default they pass through.

A job created while run control is on does not start at that default. Every newly created job starts locked — Require approval to run, Block cron (timer) triggers and Block upstream triggers all on and the allowed-upstream list empty — whoever created it and however. Creating a job therefore does not put it into service. Bringing it into service means turning a switch off here, and that change is recorded and, with change control on, needs a permission window. Jobs that already existed when run control was turned on are untouched.

A value supplied when the job was created does not survive the lock: a blockTimer=false in a config.xml POST, a CLI create-job, a Job DSL seed or the job this one was copied from is overwritten. Only the job-level approver list is carried over, because it can only narrow who may approve. So a definition that pins blockTimer: false is not idempotent against a fresh creation and appears simply to have been ignored; a later run of the same seed is an update rather than a creation and does restore it.

If this job's cron did not fire, read this first. A blocked timer run is refused quietly, because an unattended trigger has nobody to show a message to. A locked job therefore looks exactly like a job whose cron never fired, and three things tell those two cases apart:

  • this screen — if Block cron (timer) triggers is checked while your definition says otherwise, the lock is the reason;
  • the controller log — a refused timer run logs one "Blocked timer-triggered run of job" line per attempt, and a cron that never fired logs nothing at all;
  • the change history — the job has a CREATE record and no later CONFIGURE record clearing the switches, which is positive evidence that nothing has unlocked it since.
