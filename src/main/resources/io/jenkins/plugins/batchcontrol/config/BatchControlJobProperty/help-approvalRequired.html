If checked — and while Enable run control is on globally — a person cannot start this job directly. The build button, /build, /buildWithParameters, the CLI build command and Pipeline Replay are all refused unless an approved run request is being used; the request screen is on this job's sidebar as Request Run.

Automatic triggers still pass by default, so checking this does not by itself stop a scheduled job: cron (timer) runs pass unless Block cron (timer) triggers below is checked, upstream-triggered runs pass unless Block upstream triggers is checked (and then only the jobs listed in Allowed upstream jobs pass), and SCM-triggered runs pass.

A job created while run control is on is not at those defaults. Every newly created job starts locked, with this box and both trigger overrides on and the allowed-upstream list empty, whoever created it and however — and any value the creation payload supplied for them is overwritten, so a config.xml POST, a CLI create-job, a Job DSL seed or a copied job cannot opt out. Creating a job therefore does not put it into service; turning a switch off here is what does, and that change is recorded. Jobs that already existed when run control was turned on are untouched.

Plan for that, because it fails quietly: a generated nightly job does not run its first night, and since an unattended refusal is silent by contract that looks exactly like a cron that never fired. The help on Block cron (timer) triggers lists the three ways to tell the two apart.

A build that is already running is never interrupted; refusal happens when a run is queued.
