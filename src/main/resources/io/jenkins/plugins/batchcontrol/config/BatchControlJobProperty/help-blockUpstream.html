If checked, builds triggered by upstream jobs are blocked unless the upstream job is listed below; by default they pass through.

A job created while run control is on does not start at that default. Every newly created job starts locked — Require approval to run, Block cron (timer) triggers and Block upstream triggers all on and Allowed upstream jobs empty — whoever created it and however. Creating a job therefore does not put it into service. Bringing it into service means turning a switch off here, and that change is recorded and, with change control on, needs a permission window. Jobs that already existed when run control was turned on are untouched.

A value supplied when the job was created does not survive the lock: a blockUpstream=false in a config.xml POST, a CLI create-job, a Job DSL seed or the job this one was copied from is overwritten, and the allowed-upstream list is emptied rather than carried over. The list is emptied because while Block upstream triggers is on it is precisely the set of upstream jobs exempt from the block, so honouring a supplied one would leave the upstream door open and make the lock cosmetic. The case that makes it concrete is name squatting: an existing pipeline runs build job: 'X' where X does not exist yet, and whoever may create items creates X with the calling pipeline in its exempt list — the pipeline's next run would then execute their job with no approval and no window.

A blocked upstream run is refused without a message at the time, because the trigger has nobody to show one to, although the upstream job surfaces the failure. It is not invisible afterwards: while run control is on and this switch is checked, the job's main page shows a notice naming Block upstream triggers and saying it is cleared here; each refusal writes a TRIGGER_BLOCKED change record (at most one per job and cause kind per hour, listed under Change Records and History and exported in changes.csv); and the controller log carries a "Blocked upstream-triggered run of job" line at most once an hour per job (repeats are logged at FINE). Unchecking this switch is itself a recorded configuration change and, with change control on, needs a permission window.
